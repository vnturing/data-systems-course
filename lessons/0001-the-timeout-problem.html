Module 0 · Lesson 1

The timeout problem

The first thing that separates a distributed system from a single machine: sometimes you ask a question and the answer is silence.

~35 min2 interactives4-question checkReference sheet includedOptional work task
What you can do after this lesson Look at any "call another service and retry on failure" code path and say, with a precise argument, whether a retry can duplicate or lose work, and which fix applies.

1. A story you have probably already lived

Your checkout service calls a payment API: charge(customer, $50). Two seconds pass. Your HTTP client raises a timeout exception. What does your code do next?

On a single machine, a function call returns a value or throws an error, and you know the function either ran or didn't. Across a network, there is a third outcome: you don't know. Production incidents that involve double charges, duplicate emails, and "ghost" orders overwhelmingly start with someone treating that third outcome as if it were the second.

2. What a timeout actually tells you

A timeout carries exactly one fact: no reply arrived within the time you were willing to wait. It says nothing about whether the request arrived, whether the server did the work, or whether the reply is still on its way. Courses on remote procedure calls make this the starting point: a retry after a timeout fixes a lost request, but it is exactly the wrong move if the server already did the work and only the reply was lost.[1]

The network is only one suspect. A server paused by garbage collection or a saturated queue looks identical from outside. Module 8 returns to this: you cannot distinguish "dead" from "slow" by waiting.

Try it. Commit to a prediction first; the learning comes from being wrong in a place where it's cheap.

The design consequence

Because the client cannot distinguish these worlds, no client-side logic alone can make a non-idempotent operation safe to retry. The fix has to involve the server remembering what it did. That's the whole lesson in one sentence; the rest is how to do it correctly and where it breaks.

3. Three postures when you hit a timeout

PostureWhat you do on timeoutFailure it risks
At-most-onceDon't retry; report an errorWork may have happened while you report failure. Work may be silently lost.
At-least-onceRetry until you get an answerWork may happen several times. A retried "debit $10" debits twice.[1]
Exactly-once effectRetry, but make repeats harmlessNeeds server-side memory, which has its own failure modes (section 5).

"Exactly-once delivery" is not something a network gives you. What you can build is at-least-once delivery plus duplicate suppression, which yields exactly-once effect. The lecture material on RPC states the recipe plainly: retransmission, plus duplicate filtering keyed by a unique request ID, plus a server that survives crashes without forgetting, and it flags that this breaks down when the operation has external side effects outside the system's control.[1]

Spend a few minutes on the matrix. Find the one row where every cell is green, then find the row that looks nearly as good but contains a red cell. That second row is the subject of section 5.

4. How idempotency keys work in production

Stripe's API is the best-documented example in industry. The client generates a unique key per logical operation and sends it as an Idempotency-Key header. The server saves the status code and body of the first request made with that key and returns the saved result for any later request with the same key, including errors such as 500.[2] Several details in their documentation are worth studying because each encodes a lesson about the design:

  • The key identifies the operation, not the attempt. One logical charge, one key, reused across retries. A fresh key per attempt gives you no protection at all (it is just a blind retry with extra steps).
  • Parameters are compared. If a retry arrives with the same key but different parameters, the server errors instead of guessing; this catches a caller bug where a key gets reused for a different request.[2]
  • Keys can expire. Keys may be pruned after at least 24 hours, so a retry after that window would be treated as a new request. Retry windows must be shorter than key retention.[2]
  • Concurrent duplicates need a story. If the original request is still executing when the retry arrives, the server must wait, reject, or otherwise avoid running the handler twice. The Princeton lecture calls this out as a distinct problem and suggests a "pending" marker per in-flight request.[1] Stripe's docs note that results are not saved when a request conflicts with another one executing concurrently, and that such requests can be retried.[2]
  • Safe verbs need no key. GET and DELETE are idempotent by definition in their API; keys matter for POST.[2]

5. The part almost everyone gets wrong

The fourth row of the lab, "key saved in a separate step before the charge", is the most instructive. The server records "I handled key K1", then crashes before charging. The retry finds the key, concludes the work is done, and tells the client success. The customer was never charged, the client believes they were, and no error was ever raised. A false success is strictly worse than a false failure, because nothing triggers an investigation.

The rule: the idempotency record and the effect it protects must commit atomically, typically in the same database transaction, so a crash leaves both or neither. The same lecture makes the underlying point with an ATM: if "log the operation" and "dispense the cash" are separate actions, a crash between them leaves you unable to know which happened, and exactly-once cannot be achieved in general when external actions are involved.[1]

The honest limit If your effect is outside your transaction boundary (an email sent, a card network call, a physical device), you cannot make key + effect atomic. The practical answer is to push idempotency to the downstream system (pass its idempotency key through), or to reconcile afterward by querying actual state. Module 7 (transactions) and Module 11 (exactly-once in stream processing) build on exactly this.

6. Check yourself

Optional: apply it to your own code (about 20 minutes)
  1. Grep your codebase for HTTP client retry configuration (library-level auto-retry counts). List every POST endpoint that is retried.
  2. For each, answer: if the first attempt succeeded and its reply was lost, what happens on the retry? Write the answer down; don't answer from memory of how you meant it to work.
  3. Pick the worst one. Check whether the downstream API accepts an idempotency key. If yes, generate the key once per logical operation (persisted before the first attempt) and reuse it on every retry.
  4. If you own the downstream service, check that its dedupe record and its effect commit in one transaction.

Nothing later in the course depends on you doing this. It simply turns the lesson into a habit.
