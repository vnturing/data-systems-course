Module 4 · Lesson 30

Deploy readers and writers in a safe order

Both releases can pass their own tests and still fail during deployment. The missing tests are the mixed-version pairs.

~35 min1 deployment labrollback and replay4-question check
What you can do after this lessonDraw the writer/reader matrix, choose a deployment order supported by it, and check the retained-data and rollback paths before switching writers.

1. Always write the arrows

Use compatibility terminology from the reader’s point of view. Confluent’s documentation defines backward, forward and full compatibility this way:[1]

PropertyPair that must workQuestion
Backwardold writer → new readerCan new code read existing data?
Forwardnew writer → old readerCan old code tolerate new data?
FullBoth cross-version pairsCan these versions coexist in either direction?

A release tested only against itself covers the diagonal: v1→v1 and v2→v2. A rolling deployment needs the off-diagonal cells too. A database also keeps old records after old processes disappear. A broker may serve an old event during replay long after every producer has upgraded.

2. The same change can work in one direction

Consider flat Avro payment records with id and amount. The actual writer schema accompanies each record in our experiment. These are Avro resolution rules, not universal rules for every format:

v1 → v2 schema changeOld writer → new readerNew writer → old reader
amount int → longWorks: promotionFails: no long-to-int resolution
Add currency without a defaultFails: missing reader fieldWorks: old reader ignores currency
Add currency with reader default USDWorks: default suppliedWorks: old reader ignores currency

Avro specifies type promotion and missing-field resolution.[2] Our real-library experiments check every pair. The long-to-int case fails even when this sample amount, 1,200, fits in an int: resolution checks the declared types. Do not transfer this result to Protobuf’s different integer-evolution rules.

A USD default is appropriate only under the declared historical assumption that old amounts were USD. A default cannot establish a fact that was never true. Compatibility of the representation does not prove the business interpretation.

3. Try the unsafe deployment first

Try: with int→long, deploy the writer first and observe the failure. Reset, deploy the reader first, then the writer. Roll the reader back. Next choose the forward-only change: producer-first works for the live old reader, but the new reader still fails on retained v1 data. Only remove that requirement if you have actually migrated or made all old data unavailable to that reader.

The widget changes role versions instantly; it does not model an entire fleet. A real rollout can contain multiple active readers and writers at once. Include every required pair, and both directions of a request/response service.

4. Separate accepting a representation from emitting it

A useful deployment sketch has distinct steps:

  1. Prepare readers. Deploy code that can accept old and new representations while writers keep emitting the old form.
  2. Verify coverage. Include background workers, rarely invoked jobs, historical data and the code version available for rollback.
  3. Activate writers. Start emitting the new form only when every required reader can handle it.
  4. Retire old handling deliberately. Account for retained records, backups, queued work and the rollback window before removing support.

This reader-first sketch needs backward-compatible new readers and a compatible rollback target. If the current change does not supply them, build a transitional representation, migrate old data or isolate a new versioned dataflow. Do not solve a missing matrix cell by assuming deployment is instantaneous.

Amazon’s rollback-safety article describes separating preparation from activation and testing transitions, not merely stable versions.[3] Our deployment steps apply that idea to this course’s examples.

5. Code rollback does not roll back bytes

If v2 has written records that v1 cannot read, replacing v2 binaries with v1 does not undo those records. That can turn a routine rollback into an outage. A rollback target may need to be a prepared release that reads both forms, while still writing the old form.

For a database column rename, the same reasoning suggests an expand/migrate/contract plan: add the new location, support both during transition, migrate with a consistent concurrent-write protocol, switch readers and writers, then remove the old location after the retention and rollback obligations end. This is a design sketch, not a claim that dual writes are automatically atomic; revisit Lesson 2 at every boundary.

Registration policies add another dimension: which schema versions are checked? Adjacent compatibility does not generally establish compatibility with all retained history. Lesson 32 gives a concrete three-version counterexample.

6. Check yourself

Optional: review a rollout (20 minutes)

For one schema change, draw all active and historical writer/reader pairs. Identify the first point new bytes can appear, the oldest retained writer schema and the rollback reader. State evidence for each required cell.

Ask the course agent to challenge a deployment order; include retention and the actual rollback target.
