Secondary, covering and composite indexes

An index can find the right rows and still do far too much work. Separate the entries it searches, the rows it fetches, and the values it returns.

~35 min1 interactivereal MySQL plans4-question check
What you can do after this lessonDesign one composite index for a concrete query, explain why column order matters, recognize a covering access path, and use actual plan rows to check the mechanism.

1. A secondary lookup can be two tree walks

Lesson 21 followed a key down one B-tree. In InnoDB, the primary-key tree holds the row. A secondary index holds its own key columns and the row’s primary key. Finding a secondary entry can therefore be followed by a primary-key lookup to obtain the rest of the row. A wide primary key also makes every secondary index wider.[1]

secondary leaf: (tenant=42, status=paid, date=90, primary_key=42091)
                                  |
                                  v
clustered leaf: (id=42091, tenant=42, status=paid, date=90, amount=..., payload=...)

Cached pages make these logical steps cheaper; they do not erase the access path. The unit in this lesson is entries or records examined, not physical disk reads.

2. Design for this query

SELECT SUM(amount) FROM orders
WHERE tenant_id = 42 AND status = 'paid' AND created_at >= 90;

Dates are integer buckets in this small experiment. There are 100,000 orders, 1,000 for this tenant, 200 paid, and 20 matching all predicates. A composite B-tree is ordered lexicographically: first column, then the next within each equal first value. Equality on tenant and status followed by a date range makes the twenty matching entries one contiguous interval. That suggests (tenant_id, status, created_at). Its leftmost prefixes also support tenant-only and tenant-plus-status lookups.[2]

With (tenant_id, created_at, status), dates 91 through 99 each contain both statuses. Paid entries across those dates do not form one narrow interval. My initial prediction was 100 entries. Real MySQL scanned 92. It tightened the lower boundary to (42,90,'paid'), skipping the eight open entries at date 90. Later columns can help at a boundary without eliminating unwanted entries in the interior. “Nothing after a range matters” is too strong.

Try: start at date 90 with pushdown off. Compare the first three indexes. Then choose the covering index. Predict what will change before enabling pushdown on the date-first index.

Read plans from the leaves upward. Compare estimates with actual rows, then consider loops: a small inner lookup repeated 100,000 times is substantial work. EXPLAIN ANALYZE executes the query; plain EXPLAIN estimates it. The displayed times here are warm, tiny-run observations, not a benchmark.[3]

4. Covering and pushdown save different work

Covering means all values this query needs are in the chosen index. Adding amount to the good-order index lets the engine compute the sum from its entries. The recorded plan says Covering index range scan; traditional EXPLAIN says Using index. Selecting the payload would remove coverage. InnoDB visibility checks can still require clustered records in some transactional circumstances; the simulator omits MVCC.

Index condition pushdown (ICP) tests predicates available in a secondary entry before fetching its clustered row.[4] On our date-first index, it tests status inside the engine and returns only twenty rows from the access node. The 92-entry search interval remains. Using index condition does not mean the query is covered. Turning pushdown on can hide rejected entries from that actual-row counter; it does not prove they were never inspected.

5. An index is a maintained copy

Covering costs space and write work. Inserting an order maintains every index; updating an indexed amount must maintain the covering index too. Wider entries reduce entries per page, increasing the tree and cache footprint. The useful review question is: which measured read does this copy save, and what write workload maintains it?

Equality columns before a range are a starting point for this query, not a universal rule. ORDER BY, LIMIT, other queries, skew, and selectivity can change the choice. The lab forces paths; it does not predict the optimizer’s free choice, skip scans, Index Merge, page reads, or latency.
