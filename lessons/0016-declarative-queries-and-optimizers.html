Declarative vs imperative: what the optimizer does for you

SQL says what you want, not how to get it. The “how” is a program written by someone else, and it is worth knowing when it is brilliant and when it is guessing.

~50 min1 interactivereal MySQL measurements4-question check
What you can do after this lesson Explain why declarative queries give an optimizer room to change plans, read a MySQL plan and compare estimated with actual rows, and recognize when a hard-coded access path (an ORM loop, an application-side join, a forced join order) gives that freedom away.

1. Declarative means someone else chooses the plan

An imperative program states steps: loop over orders, look up each customer, filter by region. A declarative query states properties of the result: orders that are open, whose customer is in the EU. The first fixes the access path. The second leaves it open.

That openness is the heart of Codd’s original argument. He wanted users and programs insulated from ordering, indexing and access-path dependence (Lesson 12), so that storage could change without breaking programs.[1] The mechanism that makes it practical is the cost-based optimizer from IBM’s System R: Selinger and colleagues described how the user specifies neither the access path nor the join order, and the system chooses, estimating the total access cost of candidate plans from statistics and searching join orders with dynamic programming restricted to left-deep plans.[2] Modern engines are far more elaborate, but the contract is unchanged.

2. Same SQL, different plan

To feel it, take one query and change only the indexes. The lab below is a small cost model I calibrated against measurements on a real MySQL 8.0.46 server with a scaled-down dataset: 1,000,000 orders, 100,000 customers, 50 regions, 2% of orders open. The model counts storage-engine rows read, charging each join step the cheaper of an index lookup or a hash join, as the real engine does.

What the real optimizer did (the lower table)

  1. No index on orders.status (B). The optimizer started from the 50-row regions table and walked outward to customers and orders: 24,054 rows read in all six statistics refreshes. Forcing the order as written (orders first) with STRAIGHT_JOIN read 1,020,004. Same SQL, 42× apart. A program that hard-codes “orders, then customers, then regions” pays that every time.
  2. Other configurations (C, D, E). The optimizer chose orders-first in all six refreshes, and the as-written order matched it. When the index you remove is not on the winning path, the winning path does not change.
  3. All indexes present (A) is a near tie. Across six statistics refreshes the optimizer chose regions-first twice (24,054 reads) and orders-first four times (40,002 reads). The two plans’ estimated costs were within a few percent of each other. The flips happened only when I re-ran ANALYZE TABLE, which re-samples statistics (my inference about the cause). In production, a plan that flips between a quick plan and a slower one when statistics refresh is a real operational phenomenon.
  4. The toy agrees with MySQL. It reproduces the as-written read counts to within 0.1% and the alternative plan to within 9%, and it picks the same join order as MySQL in B through E. Its tests pin these numbers (tools/test-planner.js).

3. Reading a MySQL plan

MySQL’s EXPLAIN can print a tree (FORMAT=TREE), and EXPLAIN ANALYZE, available since 8.0.18, actually runs the query and reports measured time, rows and loop counts beside the estimates.[3] The manual also notes that hash joins are used by default since 8.0.18, which is one reason a join into a tiny table costs so little in the lab.[4] The habit to build is comparing estimated rows with actual rows at each node.

CREATE TABLE regions   (id INT PRIMARY KEY, name VARCHAR(20) NOT NULL);
CREATE TABLE customers (id INT PRIMARY KEY, region_id INT NOT NULL, KEY idx_region (region_id));
CREATE TABLE orders    (id INT PRIMARY KEY, customer_id INT NOT NULL, status VARCHAR(10) NOT NULL,
                        KEY idx_status (status), KEY idx_customer (customer_id));

-- Declarative: say WHAT you want. The optimizer picks the join order and the access paths.
EXPLAIN FORMAT=TREE
SELECT COUNT(*) FROM orders o
  JOIN customers c ON c.id = o.customer_id
  JOIN regions r   ON r.id = c.region_id
WHERE r.name = 'EU' AND o.status = 'open';

-- EXPLAIN ANALYZE runs it and shows estimated vs actual rows, time and loops per node.
EXPLAIN ANALYZE
SELECT COUNT(*) FROM orders o
  JOIN customers c ON c.id = o.customer_id
  JOIN regions r   ON r.id = c.region_id
WHERE r.name = 'EU' AND o.status = 'open';

-- An imperative override: STRAIGHT_JOIN joins the tables in exactly the order written.
SELECT COUNT(*) FROM orders o
  STRAIGHT_JOIN customers c ON c.id = o.customer_id
  STRAIGHT_JOIN regions r   ON r.id = c.region_id
WHERE r.name = 'EU' AND o.status = 'open';

-- Refresh the statistics the optimizer's estimates come from.
ANALYZE TABLE orders, customers, regions;
An estimate that was wrong, and why In the measured dataset, EXPLAIN ANALYZE showed the join producing an actual 20,000 rows where the optimizer estimated 3,896. My synthetic data accidentally made every open order belong to an EU customer. The optimizer assumes the two filters are independent (as does my toy), so it multiplied selectivities and under-estimated. Real data is correlated like this constantly (country and currency, status and date). When estimated and actual rows diverge by a large factor at some node, suspect correlation or stale statistics before suspecting the algorithm.

4. What declarative buys, and what it costs

You gainYou pay
Plans adapt without code changes. Add an index and existing queries can use it (the 42× case). New join algorithms (hash join arrived in 8.0.18) can speed up old queries.You do not control the plan. A change in statistics or version can change it, and the new plan may be slower.
Data independence. You can reorganize storage without rewriting every program.Plans can be unstable near ties, as configuration A showed.
The query is shorter and states intent.Estimates can be wrong (correlated predicates), and wrong estimates produce wrong plans.

The escape hatches (hints, STRAIGHT_JOIN) make the plan imperative again. That is sometimes the right call for a critical query, but it freezes the plan: in configuration B the forced order was 42× worse, and it would stay that way if the data changed.

When you are the optimizer

Document and key-value stores tend to move this decision to you. DynamoDB’s guidance has you identify your access patterns first and design keys around them, because there is no join planner to rescue a model that was designed without them.[5] The same is true of an ORM loop that issues one query per row, or an application-side join in Lesson 13’s drift story: each hard-codes a plan, and each is only as good as the plan you chose when the data was small.

A short habit list (my synthesis): read EXPLAIN ANALYZE for the five slowest queries; check estimated against actual rows; keep statistics fresh; treat a hint as a code smell with an expiry date; and when you hand-write an access path, say in a comment what data shape you assumed.

5. Check yourself

Optional: compare a plan with and without an index (20 minutes)

On a scratch copy of a table you own, run EXPLAIN ANALYZE on one real query, add or drop one index, and run it again. Note whether the join order changed and how estimated rows compared with actual rows. The experiments/mysql/planner_run.sh script is a template.
