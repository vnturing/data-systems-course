Module 7 · Lesson 49

Snapshot isolation and MVCC internals

A snapshot is a visibility rule over versions. MVCC is the machinery that can supply those versions without making every ordinary reader wait behind a writer.

~35 min1 interactive4-question check
What you can do after this lessonWalk a version chain, identify the actual snapshot boundary, and explain why InnoDB repeatable read and formal snapshot isolation must not be treated as synonyms.

1. Keep history so the reader can choose

Suppose a writer replaces x=100 with 110, then another writer produces 120. A report whose view predates both changes can still need 100. A multi-version engine retains enough history to reconstruct the version visible to that report. The physical newest row and the logically visible row need not be the same version.

InnoDB stores transaction metadata and a rollback pointer with clustered records; update undo can reconstruct older versions. Deletion marks and purge coordinate physical removal with visibility. The version-chain widget models that choice, not the byte layout, buffer manager or full read-view implementation.

Try: hold the view at event 2 while newer versions exist. It selects 100. Advance to event 4 and it selects 120. Enable the reader’s own write and 130 becomes visible to that transaction even though another transaction cannot read it as committed. A wall-clock timestamp is not used to establish this ordering.

2. A boundary is more than “small transaction ID”

A transaction may start early and commit late. A view created while it is still active must exclude its new version even if its transaction ID is numerically small. An implementation needs enough information about active and committed transactions to distinguish that case. “Take the largest ID below mine” is not a valid general visibility algorithm.

The teaching model instead records explicit logical commit events and chooses a version committed by the view’s boundary, plus any own write. That is a compact way to expose the visibility decision; real InnoDB read views track transaction state rather than storing the widget’s commit-event numbers in row records.

3. When does MySQL establish the view?

For ordinary consistent reads in an InnoDB repeatable-read transaction, the first such read establishes the snapshot. START TRANSACTION alone is not necessarily that first read. A write committed by B after A begins but before A’s first SELECT can therefore be included.

-- A: repeatable read, START TRANSACTION (no data read yet)
-- B: UPDATE counter SET v=110 WHERE id=1; COMMIT
-- A: SELECT v FROM counter WHERE id=1;             -- 110
-- B: UPDATE counter SET v=120 WHERE id=1; COMMIT
-- A: SELECT v FROM counter WHERE id=1;             -- 110
-- A: SELECT v FROM counter WHERE id=1 FOR UPDATE;  -- 120

These are recorded server results. The last query uses a locking read of current data rather than the older nonlocking snapshot. Mixing the two forms can expose different views inside one transaction. START TRANSACTION WITH CONSISTENT SNAPSHOT deliberately establishes an initial consistent-read view at the supported level; it does not change the configured level.

4. Snapshot isolation includes a write rule

Formal snapshot isolation combines a stable committed view with protection against overlapping same-item writes. If A and B both read x=100, calculate 110 and attempt to commit their replacements, a same-row conflict rule prevents both stale computations from silently succeeding. An abort/retry can force the loser to recompute against the new state.

The crucial portability trap is calling every MVCC repeatable-read implementation “snapshot isolation.” In our MySQL repeatable-read experiment, both transactions read 100, both commit UPDATE v=110, and the final value is 110. PostgreSQL repeatable read rejects the corresponding stale write with SQLSTATE 40001 in our separate experiment. Name the read and conflict rules as well as the label.

5. Stable does not imply serializable

Even a full snapshot-isolation write-conflict rule only catches overlapping write sets. Two doctors each inspect the whole roster and then update different doctor rows. The shared decision can be invalid although the writes do not collide. Lesson 51 uses that example to show why snapshots alone cannot enforce every invariant.

A snapshot also need not be fresh enough for an external promise. A report can be internally consistent yet older than a user’s last acknowledged action if you chose a stale replica or historical boundary. Isolation and replica-read eligibility remain separate contracts.

6. History has a carrying cost

A long-lived reader can keep old versions necessary. New writes continue, but purge cannot simply delete history still required by a live view. Export duration, undo retention, vacuum/purge progress and space therefore matter operationally. “Readers do not block writers” is a statement about certain data locks, not a promise of zero resource interference.

Keep snapshots as short as the task allows, and bound report work. Inspect engine-specific retention evidence rather than guessing a byte cost from this model. DDL and metadata locking can still interfere with readers; MVCC is not a general escape from all locks.
