Two-phase locking and its costs

Two-phase locking constrains when a transaction may acquire and release locks. It can enforce a serializable order, but the locks that protect correctness also create waiting, deadlocks and contention.

~35 min1 interactive4-question check
What you can do after this lessonRead a wait graph, distinguish a wait from a deadlock, explain predicate/range protection, and design lock ordering and whole-transaction recovery.

1. Growing, then shrinking

In basic two-phase locking, a transaction first acquires locks and later releases them. Once it has released a lock, it does not acquire new ones. With the appropriate read and write locks, including predicate protection, this discipline constrains the history to a serializable ordering. “Two phases” describes lock acquisition and release, not a distributed commit vote.

Strict variants keep exclusive locks until commit/abort so that another transaction cannot consume an uncommitted write. A common stronger variant keeps both shared and exclusive locks to transaction end. We will use that end-held design when explaining the example below. It should not be confused with two-phase commit, which is covered in Module 9.

2. Compatibility creates the wait

Shared (S)CompatibleWait
Exclusive (X)WaitWait

Shared reads can coexist, while a writer needs exclusion. A snapshot reader can instead read an old committed version, so the table describes locking reads in this design, not every ordinary MVCC SELECT. Mixing MVCC and locks is normal; never infer an engine’s whole concurrency protocol from the presence of row locks.

Two transactions can both take shared locks and later need upgrades to exclusive locks. Each can then wait for the other’s shared lock. Lock upgrades, multiple records, foreign-key checks and index records can all participate in deadlocks. “We only lock one business entity” does not establish that the database touches one physical lock.

Try: opposite acquisition orders produce two wait edges. The common order leaves B waiting on A, but A can acquire y and finish. Changing read mechanism explains why nonlocking snapshot readers can bypass an uncommitted writer’s data lock without reading its uncommitted value.

3. Draw the wait-for graph

A holds x and wants y. B holds y and wants x. Draw an edge from each blocked transaction to the transaction whose lock it needs. A → B → A is a cycle: neither can proceed without an intervention. A single A → B edge is only a wait; B may commit normally.

InnoDB’s detector can choose a victim and roll that transaction back. The experiment deliberately observes the first lock-wait edge in performance_schema before issuing the opposite request. It records error 1213 when the cycle forms. Victim choice is not promised and is not used as a correctness assumption.

A lock-wait timeout is a different signal. Error 1205 can happen without a cycle, for example because somebody holds a row lock during a slow HTTP request. Under default InnoDB settings it rolls back the waiting statement rather than the entire transaction. Our lab explicitly rolls back afterward.

4. Rows alone do not protect an empty range

Serializable locking must protect reads whose results could change through insertion. An InnoDB next-key lock combines an index record with the preceding gap; gap locking can prevent insertion between records. Unique exact-key lookups and range scans have different coverage. Under read committed, search/index-scan gap locks are generally absent, with documented exceptions for duplicate and foreign-key checks.

The real range schedule locks the indexed room range [10,30) using FOR UPDATE, then tries to insert room 15 in another session. The insertion waits and hits the deliberately short timeout. The plain repeatable-read query merely retains a stable view: an insertion can commit while the old view continues returning the original count. Different mechanisms can produce similar repeated results but very different admission protection.

5. The physical plan changes contention

A broad scan can lock more index records or ranges than a precise indexed lookup. An index added for latency can therefore also change lock footprint. Inspect the predicate, access plan and lock evidence together. A SQL WHERE clause is not a diagram of physical locks.

Lock duration multiplies contention. Do network calls and expensive preparation outside the locked section where the contract permits, then revalidate necessary facts inside. Acquire multiple known resources in a common order across all paths. Keep transactions bounded, monitor waits and retries, and distinguish failed admissions from transient lock contention.

6. Retry the transaction that actually aborted

A deadlock victim needs a new whole transaction, with reads and decisions recomputed. Use bounded retries with backoff/jitter rather than an immediate unbounded loop. A unique business conflict is not automatically transient. A lost COMMIT reply is uncertain execution, so operation identity remains necessary even if every deadlock retry is correct.

Locks are released at transaction end; keeping a connection or an application object afterward does not extend the protection. Database data locks also are not a substitute for the external fencing problem in Lesson 34.
