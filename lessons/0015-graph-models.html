Module 2 · Lesson 15

Graph models: when the relationships are the data

If the interesting questions are about paths of unknown length, you are in graph territory. The hard part turns out to be arithmetic, not storage.

~50 min1 interactivecross-checked against MySQL4-question check
What you can do after this lesson Recognize a graph-shaped workload, write a multi-hop query with MySQL recursive CTEs without looping forever, predict how fast the work grows per hop, and say what a dedicated graph engine does and does not change.

1. When to think graph

Lesson 13 gave you many-to-many as a junction table. That works well while your questions are one or two hops: “the tags of this article”, “who worked at this company”. It strains when the question is variable-depth: friends within three hops, every service that transitively depends on this one, accounts connected to a fraudulent account through any chain of shared devices. A fixed number of joins cannot express “any number of hops”.

2. The property graph model

The most common graph data model for databases is the property graph: vertices (nodes) and directed edges, where both can carry labels and key-value properties. The standards agree on this model: ISO/IEC 39075 (GQL), published in 2024 as the first international standard for a graph query language, and part 16 of SQL:2023, SQL/PGQ, which adds graph pattern matching over ordinary tables.[1] In relational terms, vertices are rows in one or more tables and edges are rows in an edge table (src, dst, ...). The data you already have may already be a graph. What changes is the query language: path patterns instead of join chains.

In a Cypher-style language, three hops of “who does person 1 follow, transitively” is one pattern (syntax differs between engines, so treat this as a sketch):

MATCH (me:Person {id: 1})-[:FOLLOWS*1..3]->(other:Person)
RETURN DISTINCT other.id

MySQL has no graph pattern syntax that I verified. (I did not check whether your version supports SQL/PGQ; look it up.) It does have recursive common table expressions, which the manual describes as suited to traversing hierarchical or graph-shaped data.[2] Each iteration works only on the rows produced by the previous one, and UNION DISTINCT eliminates duplicate rows, which the manual notes is useful for computing transitive closure and avoiding infinite loops.[2]

CREATE TABLE follows (src INT NOT NULL, dst INT NOT NULL, PRIMARY KEY (src, dst), KEY (dst));
-- a small graph with a cycle 1 -> 2 -> 3 -> 1
INSERT INTO follows VALUES (1,2),(2,3),(3,1),(3,4),(4,5),(2,5);

-- Who can person 1 reach? No changing column is carried, so UNION DISTINCT stops on the cycle.
WITH RECURSIVE reach(node) AS (
  SELECT 1
  UNION DISTINCT
  SELECT f.dst FROM reach r JOIN follows f ON f.src = r.node
)
SELECT node FROM reach ORDER BY node;
-- Same question, but you want the number of hops: carry a counter AND cap it.
WITH RECURSIVE reach(node, hops) AS (
  SELECT 1, 0
  UNION DISTINCT
  SELECT f.dst, r.hops + 1 FROM reach r JOIN follows f ON f.src = r.node WHERE r.hops < 3
)
SELECT node, MIN(hops) AS fewest_hops FROM reach GROUP BY node ORDER BY node;
-- Walk enumeration (UNION ALL) counts paths, not people: 5 people, many more rows.
WITH RECURSIVE walks(node, hops) AS (
  SELECT 1, 0
  UNION ALL
  SELECT f.dst, w.hops + 1 FROM walks w JOIN follows f ON f.src = w.node WHERE w.hops < 10
)
SELECT COUNT(*) AS rows_produced, COUNT(DISTINCT node) AS distinct_people FROM walks;
-- The trap: carrying a counter and NO cap. Rows differ at every lap of the cycle, so
-- duplicate elimination never fires and MySQL aborts at the recursion limit (error 3636).
SET SESSION cte_max_recursion_depth = 50;
WITH RECURSIVE reach(node, hops) AS (
  SELECT 1, 0
  UNION DISTINCT
  SELECT f.dst, r.hops + 1 FROM reach r JOIN follows f ON f.src = r.node
)
SELECT COUNT(*) FROM reach;

I ran all four on MySQL 8.0.46. The first returns the five reachable people. The third produces 20 rows for those 5 people. The fourth aborts with error 3636. That last one is the gotcha the documentation does not spell out: UNION DISTINCT only stops a cycle if the carried columns repeat. The moment you add a hop counter without a cap, the rows are all different and the recursion runs until the limit.

3. The arithmetic of hops

Take a graph where each person follows d others. The number of walks of length h from one person is dh. The number of distinct people within h hops cannot exceed the size of the graph. A naive traversal produces walks; a traversal with a visited set produces people. The gap between them is the whole story.

I cross-checked this model against MySQL: for the same 2,000-person graph with 3 follows each, the JavaScript model and the recursive CTEs agree exactly. New people reached at hops 1 to 8: 3, 9, 26, 73, 184, 401, 603, 419 (the growth bends as the graph fills up). Rows produced by walk enumeration at the same hops: 3, 9, 27, 81, 243, 729, 2,187, 6,561. By hop 8 the naive query has produced 6,561 rows describing a 2,000-person graph.

What to notice

  1. Fan-out compounds. At 30 follows each, three hops is already 27,000 walks, more than the whole 20,000-person graph. “Friends of friends of friends” is most of the network.
  2. The answer saturates; the naive work does not. The distinct-people column levels off while the walks column keeps multiplying by about d.
  3. This is true in any engine. A dedicated graph database expands each person once, as a visited set does, but if the answer is 15,000 people, the answer is 15,000 people.

4. What a graph database buys and costs

Stonebraker and Pavlo’s 2024 survey is the sharpest published view, from authors with a stake in the relational model. They argue that graph queries can be run on relational systems, report results where graph simulation on a relational engine matched or beat specialized graph systems, and note that SQL/PGQ was standardized to narrow the gap, with one engine’s SQL/PGQ implementation reported to be up to 10× faster than a leading graph database in one comparison.[3] Treat those as the authors’ reading of a contested area, not a settled ranking. A balanced list of trade-offs:

What a dedicated graph engine can offerWhat it costs you
Path patterns with variable length, far more readable than recursive SQLA second query language and a second system to learn and run
Traversal machinery built for it (and tuning that goes with it)A copy of your data that must be kept in sync, which is Lesson 2’s dual-write problem again (use an outbox or change capture)
Expressing graph algorithms (shortest path, connected components) directlyAnother failure mode and another consistency story

A reasonable default: model relationships as tables, use recursive CTEs while the queries are occasional and the depth is bounded, and reach for a graph engine when variable-depth traversal is core to the product. Either way, put a hop limit on user-facing queries.

5. Check yourself

Optional: bound a traversal (15 minutes)

If you have a self-referencing table (an org chart, a category tree, a dependency list), write the reachability query with a hop cap. Then run it with the cap removed on a copy that contains a deliberate cycle and watch error 3636. Knowing what that failure looks like is worth more than knowing the syntax.
