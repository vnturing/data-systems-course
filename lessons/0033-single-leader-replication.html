Module 5 · Lesson 33

Single-leader replication and the reply boundary

One source orders writes. The hard question is which other copies exist when the client receives success.

~35 min1 interactive4-question check
What you can do after this lessonTrace a write through local durability, remote receipt and remote apply; state exactly which failure the acknowledgement can survive.

1. Replication is a pipeline

client → source commit/log → replica receive/relay log → replica apply → replica read

A single leader establishes an order for accepted writes. Followers copy that history. They can receive log records before executing the changes, so “the replica has it” is ambiguous. Separate received, durably received and applied. Local durability itself still depends on the persistence contract from Lesson 24.

MySQL exposes receiver and applier roles rather than one indivisible replication action.[1] This explains an otherwise surprising observation: the source can finish a replicated commit while a read on a replica returns the previous value.

2. Define what the reply waits for

ContractWhat success establishesWhat can still be missing
Asynchronous, local durableThe source has its local durable writeEvery remote copy
One remote durable receiptA selected remote log also holds the changeRemote application; another candidate’s copy
Both followers applied, in this labAll configured followers applied before replyAvailability when a required follower cannot respond

“Synchronous” is incomplete without the required members and the stage they acknowledge. A remote durable receipt can protect data without making it immediately readable. Waiting for every required follower can put a slow or unavailable follower on the reply path. None of these phrases by itself specifies a safe leader-election protocol.

Try: inspect at tick 4 under the one-remote policy. B has a durable copy but has not applied it. Destroying A does not destroy every copy, but serving B still needs recovery/apply. Make both followers unreachable, then enable fallback. A successful reply after fallback has a weaker contract.

3. What real MySQL semi-sync acknowledged

MySQL 8.4 semi-synchronous replication acknowledges a replica’s flushed relay-log receipt, not execution of its SQL changes. It can revert to asynchronous behavior after a configured timeout.[2] Therefore configuration intent and actual runtime status are separate evidence.

We ran MySQL 8.4.13 with one source and two followers on an internal Docker network. We enabled semi-sync on the source and B, verified one semi-sync client, then stopped only B’s SQL applier. A source insert returned, its successful semi-sync acknowledgement counter increased by 1, and B’s visible matching-row count remained 0. Starting the applier and waiting for the source GTID made the row visible. Recorded results and reproduction preserve the boundary tested.

This is not a power-loss test, a latency measurement or evidence that any arbitrary follower is a safe failover candidate. Source binlog and InnoDB flush settings were both 1. The model’s tick schedule is illustrative, not calibrated to the experiment’s wall-clock time.

4. Copies are useful for different purposes

Read scaling, failover and backup are different requirements. An asynchronous follower may improve read capacity while returning stale data. A synchronous standby can support availability without being a query endpoint: RDS’s single-standby Multi-AZ DB instance design documents exactly that distinction.[3] Do not generalize it to every RDS topology or assume every copy can serve reads.

A destructive application update can replicate successfully to every follower. That does not make replication a point-in-time recovery strategy. Define a backup/recovery history separately.

A useful design-doc sentence“We acknowledge after the source commit and one remote durable receipt; reads on followers may lag; failover must choose and recover a replica that contains the required history.” Replace each clause with your actual product’s verified contract.
