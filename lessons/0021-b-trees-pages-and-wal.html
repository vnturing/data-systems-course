Module 3 · Lesson 21

B-trees, pages, and the write-ahead log

The B-tree updates pages in place. That makes reads predictable and writes dependent on one thing: whether the page you need is already in memory.

~60 min2 interactivesreal InnoDB measurements4-question check
What you can do after this lesson Predict a B-tree’s height from its size, explain why a lookup touches exactly that many pages, explain why random-key inserts get dramatically more expensive once the tree outgrows the buffer pool, and explain what the write-ahead log and the doublewrite buffer each protect against.

1. A tree of pages

Bayer and McCreight’s 1972 paper introduced B-trees as a way to organize large ordered indexes, with each node a disk page holding many keys, so that the tree is shallow and the cost of finding a key is the number of levels.[1] Databases use the variant with all records in the leaf level and internal pages holding only keys and child pointers (the B+-tree; Comer’s 1979 survey, “The Ubiquitous B-Tree”, is the classic overview[2]). In InnoDB, indexes are B-trees whose records live in leaf pages, and the default page size is 16 KB.[3] The table itself is the clustered primary-key index.

I measured a real InnoDB 8.0.46 by reading the page headers directly out of the table’s .ibd file, for tables of an INT key and a 100-byte column loaded in key order:

Two facts follow. A lookup touches exactly as many pages as the tree is tall (measured on 10 different keys per table: always 2, 2, 2, 3). And the tree is very shallow: each internal page here has about a thousand children, so height 2 holds on the order of 105 rows and height 3 on the order of 108. That is arithmetic from the measured per-page numbers, bracketed by the two measurements above; longer keys mean fewer children per page and a taller tree sooner. My B+tree model reproduces every leaf count and height in the table exactly (tools/test-btree.js).

The manual describes how full pages end up: about 15/16 full when records arrive in key order, between 1/2 and 15/16 when they arrive randomly.[3] Measured: 93% sequential, 66% random (85 records per leaf instead of 123, so about 1.4× as many leaf pages for the same rows (2,363 against 1,682 for 200,000 rows)).

2. What a write costs depends on the buffer pool

Inserting a record modifies one leaf page in memory. The page reaches disk when it is evicted or flushed. If the same leaf absorbs many inserts before being written, the write cost per record is tiny. If every insert touches a different leaf that is not in memory, each one drags in a page and pushes out a dirty one.

I measured exactly this on InnoDB: insert 200,000 rows with random keys into a table of about 37 MB while varying the buffer pool. “Physical” counts everything written to disk (data pages, doublewrite pages, and redo log) relative to the 21.6 MB of row data:

Same data, same query, a 26-fold difference in bytes written, set entirely by whether the leaves fit in cache. With keys in order the pool barely matters (3.0 to 3.8× at 128 MB, 4.3 to 4.6× at 8 MB), because inserts only ever touch the rightmost leaf. At the large pool the 5.4× is made of about 2.2× data pages, 0.75× doublewrite pages, and 2.5× redo log: the log is the largest single component.

The lab’s model reproduces the shape and the sequential behavior, but it underestimates real InnoDB by 11% to 63% (ratios 0.89, 0.74, 0.37 and 0.80 at the four sizes). It is an ideal LRU cache; InnoDB also flushes dirty pages in the background and loses some pool to other uses, which I did not model. Treat the model as a lower bound.

A measurement mistake worth learning from My first “random key” experiment used n × 2654435761 mod 232 to scramble sequential numbers. It looks random but is a low-discrepancy sequence: successive keys land evenly spread across the key space, so leaves fill and split in lockstep and the cache is swept cyclically, which LRU handles pathologically. It gave 76% leaf fill and 223× at 8 MB, flattering to neither theory nor reality. Replacing it with a hash (the first 12 hex digits of MD5) gave the numbers above (66% and 141×). The model had agreed with the flawed experiment because it used the same sequence, which is exactly why agreement alone proves little. The course’s tests include the pitfall (tools/test-btree.js).

3. Why a B-tree needs a log

A page split changes three pages: the new leaf, the shortened old leaf, and the parent. Disks do not write three pages atomically. The drill below crashes a split after each write, and also in the middle of a write (a torn page), under three regimes.

What to notice

  1. With no log the damage depends on write order, and both orders are bad. Writing the new leaf first leaves the tree corrupt at 3 of 8 crash points; writing the parent first, 5 of 8 (dangling pointers or lost keys).
  2. A write-ahead log fixes ordering. The ARIES paper’s core rule is that a log record describing a change must reach stable storage before the changed page is written, and a transaction is committed only once its log records are durable; combined with a steal/no-force buffer policy this lets pages be written lazily.[4] After a crash, recovery re-applies (“redoes”) the logged change, so every untorn crash point recovers to a complete tree or an untouched one.
  3. But the log alone cannot repair a torn page. Redo describes a change to a page; it needs an intact page to start from. A page half-written when the power failed has no valid starting point: 3 of 8 crash points are unrecoverable.
  4. The doublewrite buffer closes that gap. The MySQL manual describes it: pages are written to a doublewrite area and flushed before being written to their final location, so if a crash tears the final write, a good copy can be found there during recovery.[5] With both, none of the 8 crash points is bad. It also explains the measured doublewrite pages above: it is a real write cost paid for this safety.

The drill is a model, not InnoDB’s code, and it covers one kind of operation. It is Lesson 2’s crash-point reasoning applied inside a single storage engine.

4. Look at your own server

These statements read the same counters I used. Take a reading, run a workload, read again, and subtract.

SELECT @@innodb_page_size AS page_bytes,
       @@innodb_buffer_pool_size / 1048576 AS pool_mb,
       @@innodb_doublewrite AS doublewrite;
SHOW GLOBAL STATUS LIKE 'Innodb_pages_written';
SHOW GLOBAL STATUS LIKE 'Innodb_dblwr_pages_written';
SHOW GLOBAL STATUS LIKE 'Innodb_os_log_written';
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read_requests';
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_reads';

Innodb_buffer_pool_read_requests counts page requests (what I used for pages-per-lookup); Innodb_buffer_pool_reads counts the ones that missed the pool and went to disk. The ratio of the two is your cache miss rate, which, as above, decides what random writes cost you.

Optional: find your miss rate (10 minutes)

On a server you can safely read, compute Innodb_buffer_pool_reads ÷ Innodb_buffer_pool_read_requests over an hour of normal traffic, and compare your working set (hot data size) with the pool. If the miss rate is high and writes are random, you are on the left of the table above.
