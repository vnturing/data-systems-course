Module 7 · Lesson 51

Write skew and phantoms

Your code checks the rule, updates its row, and commits. A second transaction does the same to another row. Both checks were reasonable; the committed combination breaks the rule.

~35 min2 interactives4-question check
What you can do after this lessonConstruct a write-skew witness, identify predicate dependencies including absent rows, and choose a repair that protects the invariant’s whole decision set.

1. The two-doctor roster

Doctors 1 and 2 are both on call. The rule is SUM(on_call) >= 1. A reads the sum as 2 and decides doctor 1 can leave. B reads 2 and decides doctor 2 can leave. A writes row 1 off-call; B writes row 2 off-call. Both commit, leaving nobody.

2Read both: count=2
3Set doctor 1 off-call
4Set doctor 2 off-call
5COMMITCOMMIT

The writes target different rows. Same-row conflict detection therefore cannot by itself reject this schedule. Our MySQL repeatable-read and PostgreSQL repeatable-read runs both reproduced the zero-doctor result. The rule was not represented by either row’s individual validity.

Try: lock only the doctor being changed. The outcome stays broken because each writer still protects a different record. Then use a common guard or serializable dependency checking. Explain what forces a decision to be re-evaluated.

2. Read/write anti-dependencies

A read doctor 2 as on-call before B changed that row. For those observations to make sense in a serial order, A needs to come before B. Symmetrically, B read doctor 1 before A changed it, requiring B before A. These requirements form A → B → A. Both transactions cannot occupy the required position in one serial ordering.

This is an anti-dependency: a reader saw an earlier version than a concurrent writer installed. It differs from one transaction reading another’s committed output. Naming the edges helps distinguish “the same rows were written” from “one decision’s inputs were invalidated.”

3. A common guard turns the logical conflict into a real one

SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT id FROM roster_guard WHERE id=? FOR UPDATE;
SELECT SUM(on_call) FROM doctors WHERE roster_id=?;
-- Require count > 1 before setting this doctor off-call.
-- Every change affecting roster membership/on_call uses this guard.
UPDATE doctors SET on_call=0 WHERE id=? AND roster_id=?;
COMMIT;

This protocol assumes the application checks the count and skips the UPDATE when it is insufficient. A guard row exists for each roster. All writers, including imports and administrative paths, must acquire it before validation. The scope of the guard matches the scope of the invariant.

Read committed is deliberate: after B waits for A’s guard lock, its count must use a fresh view containing A’s commit. A stale earlier snapshot followed by a newly acquired lock can still validate old facts. Our corrected server schedule read counts 2 then 1 and left one doctor on call. Locking all participating rows can also work if the membership and absence cases are properly protected; the guard makes the shared coordination point explicit.

4. Phantoms concern sets, not just changed values

Suppose a transaction checks that no booking overlaps a proposed interval. Another inserts a matching booking. A repeat of the predicate can now return an additional row: a phantom. But an old snapshot can continue returning zero while both transactions insert different booking IDs. Hiding the new row from rereads does not prevent the admission race.

The dependency is on the predicate’s answer, including rows that did not yet exist. Locking the rows returned by an empty query protects no existing row at all unless the engine also protects the searched range or predicate. You must examine the actual locking semantics.

5. Match the repair to the rule

For a fixed discrete room/slot pair, UNIQUE(room_id, slot_id) can make at most one claim commit. Both callers may initially see absence, but one insert loses the uniqueness race. Treat it as a business conflict. This is not enough for arbitrary interval overlaps: different starts can still overlap.

For an indexed InnoDB locking range at repeatable read, next-key/gap locking can prevent relevant insertions until the reader ends. Lock coverage depends on the index and predicate, and can include more than the exact logical condition. A shared room guard plus fresh overlap validation is another protocol if every booking path uses it. Serializable transactions can cover the broader dependency when all participating paths obey their contract.

6. A schedule is the review artifact

Write the invariant, read set/predicate, write set and transaction end for each participant. Produce the smallest interleaving that breaks it. Then identify the exact statement, constraint or abort rule that rejects that interleaving after the repair. “Wrapped in a transaction” and “we lock the record” are incomplete arguments until you show which shared decision they protect.

Optional: apply the mechanism (20 minutes)

Choose an at-most-N or at-least-one rule. Write two concurrent transactions with disjoint write sets. Identify the shared predicate, then show a constraint, guard or serializable abort that prevents the violating combination.

Ask the course agent about any unclear schedule. Include the engine/version, isolation level, exact SQL, transaction boundaries and observed responses.
