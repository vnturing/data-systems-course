Module 6 · Lesson 45

Rebalancing and consistent hashing

Changing a placement function is easy. Moving its bytes and write authority while requests continue is a separate protocol.

~35 min2 interactives4-question check
What you can do after this lessonCompare remapping under modulo, fixed slots and stable ring tokens; explain virtual-node limits; audit snapshot, catch-up and ownership cutover separately.

1. Why modulo can move most keys

With hash(key) mod N, changing N changes the divisor for every key. Under a well-spread hash, growing from three to four owners changes roughly three quarters of assignments, not only the quarter needed by the new node. Many keys move between old nodes too.

The following model uses 10,000 fixed keys. Its default results are 7,480 changed owners for modulo, 2,504 for the chosen fixed-slot policy, and 2,083 for its 64-token ring. These are computed placement counts, not disk/network measurements or universal ratios.

2. Two ways to preserve most assignments

Fixed logical partitions: hash into a stable slot space, then use a separate slot→node map. The model has 256 slots. On growth it assigns one chosen quarter to D, leaving other slot owners alone. Redis Cluster uses 16,384 logical hash slots and explicitly moves slot ownership between nodes.[1] Our slot map is illustrative, not a Redis rebalance algorithm.

Stable ring tokens: map both keys and node tokens into an ordered hash space. A key belongs to the first token at or after its hash, wrapping around. Add D’s tokens while keeping old token positions: only intervals now owned by D change owner. Karger et al. introduced consistent hashing’s limited-remapping goal; Dynamo describes virtual-node use in a storage design.[2]

Try: compare one token per node with 64 and 128. Additional tokens can distribute ownership more finely and support capacity weighting. They do not guarantee perfect finite-sample balance, equal object sizes or balanced traffic. An exceptionally hot key remains at one logical owner.

Virtual tokens on the same physical server also do not create independent replica failure domains. Module 5’s distinct-durable-holder assumptions still concern actual copies on the relevant nodes.

3. Placement is not live migration

identify data boundary → copy snapshot → capture/replay changes
+ validate catch-up → establish new write authority → change routing
+ reconcile retries / old readers → retire old copy when safe

A copied snapshot can already be stale when it finishes. A concurrent update may be missing; a concurrent delete may leave a record at the target that should no longer exist. The boundary between snapshot and change capture must avoid both gaps and incorrectly repeated effects.

Try: cut over with neither protection. The old snapshot retains the deleted record, and both owners can accept later writes. Enable complete ordered change capture, then exclusive write authority. Those controls stand for required mechanisms; the widget does not implement them.

4. The moving partition has two histories

Track a data-copy progress boundary and an ownership/configuration boundary separately. Knowing “B has the bytes” does not prove A stopped writing. Updating a directory does not prove every cached client has refreshed. The serving nodes need a protocol for stale requests, epochs or redirection as appropriate.

The actual Redis experiment moves one quiescent key, checks ASK/ASKING during import, then installs the new slot owner. It establishes those routing behaviors and value preservation for that controlled sequence. It does not establish correctness under concurrent writes, controller crashes or arbitrary resharding workloads.

Rollback is also a migration: after B accepts new writes, pointing clients back to A’s old snapshot can lose acknowledged work. A safe plan retains enough history, versioning and control to reconcile the chosen rollback path.

5. Budget bytes and operational headroom

A placement count assumes equal-size keys; real transfer cost depends on bytes, indexes, replicas, mutation rate and cache warming. A busy source may generate changes faster than the target catches up. Migration traffic can also overload the old owner before any capacity has been relieved.

Choose movement rate, cutover criteria, abort behavior and observability before assuming the rebalance will finish. Smaller units can make moves easier but increase metadata and operational bookkeeping. Splitting a sequentially hot range can leave the newest tail hot again; use the workload diagnosis from Lesson 43.
