Lost updates and five ways to prevent them

Two writers can politely wait for the same row lock and still lose one computation. The question is whether the second write uses current data or an old value calculated in the application.

~35 min1 interactive4-question check
What you can do after this lessonReproduce a lost update, compare five prevention protocols, and handle zero affected rows and serialization failures without reusing a stale decision.

1. The row is locked; the computation is not protected

A counter starts at 100. A reads 100; B reads 100. Each handler calculates 110. A updates the row to 110 and commits. B then updates it to 110 and commits. The intended effect was two additions, so 120 was required. A row lock serialized the assignments, but B’s assignment carried a stale computation.

-- Both transactions previously ran SELECT v and received 100.
-- A:
UPDATE counter SET v=110 WHERE id=1;
COMMIT;
-- B, after A commits:
UPDATE counter SET v=110 WHERE id=1;
COMMIT;  -- Both commits succeed; the final value is only 110.

This schedule succeeded in our MySQL 8.4.13 repeatable-read experiment. B’s second assignment changed zero rows because 110 was already stored. That is still an application failure: two successful requests were meant to add twenty. An affected-row count of zero is not automatically an SQL exception.

Try: change only the protocol. Follow exactly which step makes B use 110 as its input rather than 100. The model retries a detected stale attempt once; the corresponding real CAS fixture deliberately stops at the failed attempt so you can see its zero-row result.

2. Prevention 1: make the operation a database expression

UPDATE counter SET v = v + 10 WHERE id = 1;

The database evaluates the addition while applying the row update. In our MySQL schedule both updates affected a row and the final value was 120. This is a strong fit for increments and conditional decrements that can be expressed in one statement. It does not automatically compose a rule across an unrelated row set.

For stock, UPDATE stock SET available=available-1 WHERE id=? AND available>0 combines the admission predicate with the decrement. Require one affected row before accepting the reservation. A zero-row result means the requested admission was not made.

3. Prevention 2: lock before reading

START TRANSACTION;
SELECT v FROM counter WHERE id=1 FOR UPDATE;
-- Compute using that returned value while retaining the row lock.
UPDATE counter SET v=? WHERE id=1;
COMMIT;

Every competing path must acquire the lock before reading the value used in its decision. Locking after a plain read does not retroactively freshen an already computed assignment. Keep the whole sequence on one connection and keep the transaction short. A timeout or deadlock needs explicit error handling; a lock is not a reservation beyond transaction end.

4. Prevention 3: compare-and-set with an explicit version

UPDATE counter SET v=?, version=version+1
WHERE id=? AND version=?;
-- Exactly one row: this version was replaced.
-- Zero rows: ROLLBACK; re-read and recompute in a new transaction.

A and B can both read version 1, but after A increments it, B’s version-1 predicate fails. Our real fixture records affected counts [1,0], with v=110 after just the first accepted update. A proper retry can then produce 120. The zero-row result detects a stale attempt; it does not perform the missing business operation.

Use a version changed by every relevant writer. Comparing only the previous value can miss an ABA sequence, where the value changes away and back. Also a reread inside an old repeatable-read view can remain stale, so begin a new attempt with a fresh transaction boundary.

5. Prevention 4: engine conflict detection and whole retry

A snapshot-isolation same-row conflict rule can abort the stale writer. The PostgreSQL repeatable-read schedule in the lab illustrates that protection; the MySQL named-level counterexample shows why you must verify it. Recompute the entire transaction from its fresh inputs after the abort, not just the final UPDATE with the old 110.

Serializable execution can protect wider dependencies as well, but still requires correct transaction boundaries and an abort policy. A read performed before BEGIN is not made serializable by wrapping only the subsequent write.

6. Prevention 5: design a mergeable operation

Sometimes the feature permits an operation log or mergeable state. Two distinct contribution records of +10 can both survive; their sum is 20. Operation identity must make replay harmless, and the derived total needs a defined freshness contract. A CRDT counter can likewise preserve concurrent contributions under its assumptions from Lesson 40.

This changes the representation and often the read contract. It is useful for accumulation, but it does not establish a bounded inventory rule: merging two admitted decrements after the fact cannot undo overselling. Last-write-wins choosing one replacement also does not preserve two intended additions. Choose a protocol that preserves the operation’s meaning.

Optional: apply the mechanism (20 minutes)

Find a handler that loads a record, mutates an object in memory, and saves it. Name its lost-update defense, then show how every writer participates and what happens when the defense rejects an attempt.

Ask the course agent about any unclear schedule. Include the engine/version, isolation level, exact SQL, transaction boundaries and observed responses.
