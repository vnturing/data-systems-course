Module 5 · Lesson 35

What actually travels in a replication log

Followers need a description of changes. Replaying a SQL expression, reproducing a row image and replaying a storage-page operation are different contracts.

~35 min1 interactive4-question check
What you can do after this lessonDistinguish statement, row and physical logging; explain transaction identity and why replay does not automatically detect pre-existing drift.

1. Three representations

RepresentationWhat crosses the boundaryImportant coupling
StatementThe operation to execute, plus required contextExecution semantics and relevant state
Row / logical changeWhich logical rows changed and their logged imagesSchema, keys and row-image rules
Physical / physiologicalStorage structures such as pages and log recordsEngine recovery rules and storage layout

These are families, not one universal wire format. MySQL’s binary log supports statement, row and mixed formats; InnoDB’s local redo log serves a different recovery purpose.[1] Do not call every log the WAL and assume interchangeable consumers.

2. The input state is part of a statement

source balance = 100
replica balance = 90        // already drifted
UPDATE account SET balance = balance + 10;

Re-executing this expression produces 110 on the source and 100 on the replica. The expression is deterministic, yet the input states differ. Nondeterministic functions, session settings and statement context introduce further concerns; MySQL documents which statements are unsafe and how row logging avoids some statement-reexecution hazards.[2] That does not mean every function is naively reevaluated without context.

Try: remove the initial drift and compare formats. Restore the drift. Then deliver twice and toggle transaction identity recognition. The toy row event assigns one full after-image. A real format can use different row-image settings and can encounter errors rather than silently repairing a mismatched row.

3. Actual events, not just SQL text

Our MySQL servers ran row-format binlogging. The source’s event inventory includes Gtid, Query, Table_map, Write_rows and Xid entries. Row-format logging still includes metadata and transaction framing; it does not mean that every event is a row image.

We used the server’s SHOW BINLOG EVENTS because the container image lacks mysqlbinlog. This inventory identifies event types and positions; it does not decode every column value. The source/replica query checks separately establish that the inserted rows were applied.

4. Identity, order and transaction boundaries

A replay stream needs a way to know what is already applied. In MySQL’s GTID setup, transactions have identifiers and the executed set can be inspected or waited on.[3] Positions and identities answer “where am I?”; they do not decide which divergent history should win.

Order and transaction boundaries also matter. If two row changes belong to one transaction, exposing half to an ordinary read can break its invariant. A parallel applier may execute work concurrently while preserving configured commit-order constraints; do not infer an implementation’s complete visibility semantics from a sequential toy.

Replaying an after-image assignment twice happens to be harmless in our one-cell example. Replaying an insert can hit a duplicate key; replaying a delete or a more elaborate update needs its actual semantics. Log-level deduplication and application-level exactly-once effects remain distinct.

5. Logs are not an integrity proof

The widget leaves an unrelated bad row unchanged: source 70, replica 60. A perfectly delivered stream of future changes can leave untouched historical divergence undetected. Initial bootstrap must connect a consistent snapshot with the right log boundary; later integrity checks and repair are additional mechanisms.

Module 4’s schema-evolution work applies here too: a logical log consumer needs the schema that describes the event and a valid mapping into its current model. Physical recovery formats introduce different engine/version coupling. A replication-log choice changes which assumptions must match, not whether assumptions exist.
