Module 0 · Lesson 2

What if it dies right here?

A review technique for any handler that touches two systems. Your MySQL-plus-Kafka service is the textbook case.

~40 min1 interactive4-question checkBuilds on Lesson 1
What you can do after this lesson Take any handler that writes to more than one system, list every point where a crash changes the outcome, classify each as clean, lost, phantom or duplicate, and fix the dangerous ones with a transactional outbox plus idempotent consumers.

1. Two systems, two commits

Your order service does this, probably in a dozen places:

BEGIN;
INSERT INTO orders (...) VALUES (...);
COMMIT;                                   -- MySQL now has the order
producer.send("orders.created", event);   -- Kafka now has the event
return 201;

There is no single commit that covers both stores. Between any two lines the process can disappear: a deploy replaces the pod, the kernel OOM-kills it, a spot instance is reclaimed, a host dies. Each of those is a crash-recovery event (the process loses memory, the disks survive; Lesson 3 names this precisely). And from the caller's side each one looks like Lesson 1's timeout.

Engineers usually describe this problem as dual writes: changing data in two systems, such as a database and a Kafka topic, so that if one operation fails you end up inconsistent, in ways that are hard to detect and fix.[7]

2. The drill

The technique is mechanical on purpose. It works at 5 p.m. on a Friday design review.

  1. List every externally visible effect the handler performs, in order. Count the COMMIT as its own effect: before it, nobody else can see the row; after it, everybody can.
  2. Draw a line before the first effect, between each pair, and after the last.
  3. At each line ask: if the process is killed here and never resumes, what does each system contain?
  4. Classify the answer into one of four buckets (below).
  5. Repeat for the non-crash faults: the second effect returns an error; the reply to the client is lost.
OutcomeMeaningTypical damage
CleanNothing happened anywhere, or everything didNone (client may retry)
LostChange committed, never announcedShipping never starts; search index stale; billing misses it, silently
PhantomAnnounced, but the change never committedDownstream acts on something that does not exist
DuplicateAnnounced more than onceHarmless only if consumers are idempotent (Lesson 1)

These are consequences of two stores not sharing a commit. They are not bugs in MySQL or Kafka.

3. Reading the table

Design A (commit, then publish)

The lost event lives in the gap between COMMIT and PRODUCE. It is a few milliseconds wide, but a width times a volume is a rate: at a million orders a day, a few-millisecond window gets hit by routine deploys. And lost events are the quiet kind. Nothing errors; a downstream system just never hears about an order.

Design B (publish, then commit)

Swapping the order merely trades lost events for phantom events, which are usually worse because consumers have already acted. B has a second, subtler problem visible in the last row of the table: it breaks without any crash at all. A deadlock or constraint violation at COMMIT, a perfectly ordinary error, leaves a published event for a transaction that rolled back.

Design C (outbox)

The order row and an outbox row commit in one MySQL transaction. A separate relay reads committed outbox rows and publishes them. This is the pattern Debezium's authors describe for letting a service update its own store and notify others safely, giving the writer read-your-own-writes behavior and reliable but eventually consistent exchange with other services.[1] Look at what remains in the table: no loss, no phantom. Only duplicates, and only when the relay dies between publishing a row and recording that it did so.

That residue is not an accident. The relay has the same two-system problem in miniature (publish, then mark sent), but the outbox arranges for it to fail in the safe direction: at-least-once. You moved the hazard from a place where it loses information to a place where it repeats it, and repetition is something Lesson 1 taught you to absorb.

4. "Can't I use Kafka transactions for this?"

Kafka's transactions make read-process-write cycles atomic and fence out zombie producers, which gives exactly-once processing between Kafka topics.[2] The idempotent producer protects against duplicates created by a producer's own retries.[3] Neither makes a MySQL write a participant. One practitioner guide states the boundary plainly: idempotence and transactions do not automatically make a database write, API call or other external side effect exactly once.[6] Distributed commit protocols that do span stores exist; Module 9 covers two-phase commit and why teams usually avoid it here.

5. The outbox in practice (MySQL + Kafka)

BEGIN;
INSERT INTO orders (id, idempotency_key, ...) VALUES (...);   -- UNIQUE(idempotency_key)
INSERT INTO outbox (event_id, type, payload) VALUES (UUID(), 'order.created', ?);
COMMIT;

Two relay styles, with real trade-offs:

  • Polling relay. A small process queries for unsent rows, publishes them, and marks them sent. It is easy to reason about and easy to explain, but it costs a query on every interval, an update for each event, and extra coordination once you run several publishers.[5] If it stops after Kafka acknowledges but before marking the row, it publishes the same event again.[5]
  • Change data capture. Debezium reads the database's transaction log and publishes outbox rows via a ready-made event router (an SMT, a Kafka Connect transform).[1] Secondary sources report the MySQL connector supports the same router; confirm against the Debezium documentation for your version.[4] You trade polling load for an extra moving part to operate.

Both deliver at-least-once. Debezium commits its progress after writing events to Kafka, so a crash between the two re-emits events on restart: protection against loss at the price of possible duplicates.[4] The fix is exactly Lesson 1's: give every event a stable id (the outbox row's event_id) and have consumers record processed ids in the same transaction as their side effect. The event id is the idempotency key for the consumer.

6. The gap that is still open

Return to the table's “timeout” rows. Even with a perfect outbox, the client may have seen a timeout after the order committed, and a blind retry creates a second order. That is why the sketch above carries UNIQUE(idempotency_key) on the order itself: a retry hits the unique constraint, and the handler returns the existing order instead of inserting another. (This combination is a synthesis of Lesson 1's key design and this lesson's outbox, not a quote from a source.) Two different duplicate problems, two idempotency keys: one from the client, one for the event.

7. Check yourself

Optional: apply it to a real handler (about 20 minutes)

Pick one handler of yours that writes to MySQL and also publishes to Kafka (or SQS, or calls another service). Write its effects in order, draw the lines, and fill in a four-bucket outcome for each. Then answer: which row would you least like to explain to a customer? Nothing in the course depends on you doing this; it simply turns the lesson into a review habit.
