Module 7 · Lesson 55

Choosing isolation for a real feature

Choose an isolation protocol by proving the feature’s invariant under concurrency, then measure its operational cost. A level name is one part of that protocol.

~35 min1 interactive4-question check
What you can do after this lessonTurn a feature into an invariant, dependency set and failure schedule; select a defensible protocol and specify retries, side effects and operational evidence.

1. Begin with a sentence that can be false

“The feature is consistent” is hard to test. “For every roster, at least one doctor remains on call after each committed change” is a useful invariant. “No two active bookings claim the same discrete room/slot” is another. A report’s contract can instead be “all exported tables reflect the same committed view.” These are different requirements.

List all writers, including jobs, import tools and administrative SQL. Then list the reads and predicates used to decide each write. Include absence, sums, related records and external decisions. The invariant’s scope determines what must be coordinated; the row you happen to update may be smaller than that scope.

Try: protect the roster with a stable snapshot, then a guard and then serializable transactions. Change the feature to a report. The snapshot becomes a useful fit because the requirement changed from concurrent admission to consistent observation.

2. Four features, four concrete arguments

FeatureCandidate protocolArgument and boundary
Accumulating a counterUPDATE v=v+deltaThe update expression preserves both additions; an app-side replacement does not
One exact room/slot claimUNIQUE(room_id,slot_id)The database rejects a second exact-key claim; arbitrary interval overlap is a different rule
At least one doctor remainsCommon roster guard + fresh countAll admissions serialize at that roster; every writer participates
Multi-query consistent reportOne transaction snapshotThe report reads one view; this need not be the latest global state

Serializable transactions can also protect correctly expressed transactional decisions, with full retries and verified engine semantics. They do not replace constraints, business validation or transaction boundaries. For a simple single-row update, a narrower protocol may be easier to measure and explain. For a complex evolving cross-row rule, a serializable contract may reduce application-specific locking reasoning.

3. Worked feature: roster changes

Start with the counterexample from Lesson 51: both transactions read 2, each writes a different row, both commit 0. Choose a pre-existing guard row per roster. Begin a read-committed transaction; lock the guard; count current on-call doctors; admit an off-call transition only if another remains; write the change and an outbox row; commit.

Every membership mutation uses the same guard: removing a doctor, moving them to another roster, changing status, bulk imports and direct administrative tools. A multi-roster change needs a consistent guard acquisition order. The operation identity is unique and records a result in the same transactional domain so retrying the request can recover it.

The proof has two steps. First, at most one relevant decision for a roster is inside validation/write at a time. Second, after acquiring the lock, a fresh committed count includes the preceding holder’s change. A decision with count 1 refuses removal. Therefore each accepted transition preserves the minimum. The proof fails if a writer bypasses the guard, uses a stale earlier snapshot, or sends a success response before commit.

4. Worked feature: bounded stock

START TRANSACTION;
-- Claim an operation key here; a repeated request recovers its stored result.
UPDATE stock SET available=available-1
  WHERE sku_id=? AND available>0;
-- Require affected rows = 1; otherwise store/reply sold out appropriately.
-- Insert the reservation and outbox intent only for an admitted request.
COMMIT;

The predicate and decrement execute together under the row’s write protection. This can establish a one-row nonnegative bound, provided every stock-reducing path obeys it and related records commit atomically. A reservation that spans several SKUs needs a whole multi-row protocol; handle partial failure by rollback and choose an acquisition order. The one-line update alone is not a complete checkout design.

5. Retry policy is part of feature behavior

Separate a sold-out or duplicate-slot business rejection from a retryable concurrency abort. On a known abort, roll back the attempt, recompute its reads and decisions in a new transaction, and use bounded backoff. On uncertain COMMIT, query by durable operation identity. Do not repeat an external charge just because an SQL retry was safe.

For MySQL, inspect rollback scope for lock-wait timeouts versus deadlocks. For PostgreSQL serialization failures, retry the complete transaction, including the logic that chooses SQL values. Set a deadline for the caller’s operation as well as limits for individual attempts. A correct but unbounded retry storm is an operational failure.

6. Measure the cost of the correct protocol

Exercise representative hot keys, transaction duration and conflict rates. Observe lock-wait time, deadlock frequency, serialization aborts, retry count, queueing, tail latency and snapshot history pressure. Broad scans and changed indexes can alter both locks and read tracking. Record engine/version, level, SQL and plan alongside the measurement.

The module’s fixtures measure outcomes, not production throughput. Use them as correctness examples, then benchmark the actual feature in a controlled environment. A lack of failures in a load test does not replace the invariant argument; a single violating history can still invalidate that argument.

7. The review you should be able to deliver

Invariant: exactly what must remain true?
Decision inputs: rows, predicates, absence and external state
Boundary: engine/version, connection, isolation, transaction start/end
Counterexample: minimal concurrent history that would break the rule
Defense: constraint / atomic expression / locks / version / serializable
Participation: every writer and relevant read uses the protocol
Failure: rollback scope, bounded retries, uncertain commit recovery
Effects: operation identity, outbox, downstream deduplication
Evidence: observed schedules, documented contract, workload measurements

Use the Module 7 review sheet for a design review. Module 8 will make the environment less cooperative: unreliable networks, clocks and process pauses. The transaction boundary remains useful, but you will need to say which facts and side effects lie beyond it.
