Module 5 · Lesson 39

Version vectors: concurrency without a clock

Two versions can be concurrent even when one was written later by a wall clock. Preserve what each writer had observed.

~35 min2 interactives4-question check
What you can do after this lessonCompare version vectors componentwise, retain concurrent siblings, and explain why reconciliation and deletion need causal context.

1. A scalar version is not enough for a fork

base:                  {A:1}
A updates that base:    {A:2}       value Alice
B updates that base:    {A:1,B:1}   value Alicia

A’s branch knows more A updates; B’s branch knows a B update absent from A. Neither includes all the other’s history. Picking the larger sum would discard this distinction: both sums are 2. Sorting actor names would create an arbitrary order, not a causal fact.

Dynamo associates per-object version context with reads and later writes so that a subsequent update can say which versions it observed.[1] Our version vectors use small stable actor IDs to expose that mechanism; they are not a byte-for-byte implementation of Dynamo’s metadata.

2. Compare every component

Treat a missing component as zero. Vector x is strictly before y when every component of x is ≤ y and at least one is smaller. If each vector has a component larger than the other’s, they are incomparable: concurrent. Equal vectors are equal context, not two independent branches.

Try: begin with both clients updating the old base. Then let B observe A before updating: B’s context becomes {A:2,B:1}, which dominates A’s {A:2}. Finally choose the resolver case. It joins both branches componentwise and advances a fresh resolver component C.

3. Merge context separately from values

join({A:2}, {A:1,B:1}) = {A:2,B:1}
resolver writes after seeing both = {A:2,B:1,C:1}

The resolver’s context dominates both inputs. That establishes that it is a subsequent version incorporating observation of both branches. It does not prove its chosen value is the correct business resolution. The example’s confirmed name is an explicit application choice, not a mathematical merge of spellings.

A version store can keep the undominated versions as siblings. Ancestors need not remain as active alternatives when a descendant supersedes them. If a client reads only one sibling and writes with only that context, it has not resolved the sibling it never observed. Carrying context is part of the API contract.

4. Metadata has operational assumptions

Actor identity and counters must be managed correctly. Reusing an actor ID with a reset counter can make a new update look old or equal. Our arithmetic helper advances a supplied context; a production allocator must also prevent reusing an already-issued actor/version dot. Unbounded actor creation grows metadata; truncating context without a justified protocol can change concurrency detection.

Version vectors for object histories and vector clocks for general process events are related techniques, but their component identities and update rules depend on the system. Do not copy a few lines of componentwise comparison and assume the surrounding context-generation protocol is solved.

5. A delete is a version too

The deletion at {A:2} supersedes an old value at {A:1}. If the deletion evidence disappears before an old replica rejoins, an ordinary “merge whatever exists” can resurrect the value. Tombstones or equivalent causal metadata must remain until the system can establish that obsolete state cannot validly return.

The widget toggles an intentionally unsafe deletion of all evidence. It does not assert that every real garbage collector has this flaw, nor prescribe a fixed waiting period. Membership, repair, backup restore and permanently retired actors all affect safe reclamation.

The next lesson uses similar per-actor metadata for a different purpose: constructing merges whose algebra tolerates reordered and duplicate state delivery.
