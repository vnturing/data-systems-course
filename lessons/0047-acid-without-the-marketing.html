Module 7 · Lesson 47

ACID without the marketing

A transaction is a boundary around failure and interference. The letters ACID are useful only after you say what is inside that boundary, what concurrency is allowed, and which failures the commit survives.

~35 min1 interactive4-question check
What you can do after this lessonAudit a transaction’s atomicity, invariants, isolation and durability independently, including a lost COMMIT reply and an external side effect.

1. Begin with a transfer, not the acronym

Two accounts start at 100 each. Moving 30 from A to B should leave 70 and 130. Write the invariant before the SQL: the total remains 200, neither balance becomes negative, and one operation identity corresponds to one transfer. A debit followed by a crash is a different failure from two concurrent overdraft decisions; “we use transactions” does not answer either one by itself.

START TRANSACTION;
UPDATE accounts SET balance = balance - 30
  WHERE id = 1 AND balance >= 30;
-- Application: require exactly one affected row, otherwise ROLLBACK.
UPDATE accounts SET balance = balance + 30 WHERE id = 2;
-- Application: require exactly one affected row again.
COMMIT;

Assume InnoDB tables, one connection and existing distinct account IDs. An SQL transaction does not make a zero-row update an error. Checking the debit result matters: without it, a failed debit could still be followed by a credit. Checking the credit matters too. This is a transfer sketch; durable operation identity and response recovery still need designing.

2. A: abort the group

Atomicity lets the database discard an uncommitted group of changes. It prevents the durable half-transfer when the group aborts under the stated recovery contract. It does not imply each instruction runs at once or that other transactions cannot interleave. Undo, redo and recovery are implementation mechanisms, connected to Lesson 21.

Autocommit instead makes each update its own transaction. Both updates can individually be atomic while the pair is incomplete. In our real lab, an explicit rollback restores a changed counter from 70 to 100. That is an abort observation, not a power-loss experiment.

Try: crash after only the debit, first with one transaction and then with autocommit. Next crash after COMMIT but before its reply. Finally choose volatile persistence after a success reply. The first changes grouping, the second changes client knowledge, and the third changes the assumed durability contract.

3. C: state the invariant and who enforces it

Consistency here means preserving declared application rules. The database can enforce a primary key, a foreign key or a supported check constraint; it cannot infer that your roster must keep one doctor on call. Correct single-transaction code and sufficient isolation are both necessary for rules involving concurrent decisions.

A transaction that credits the wrong account can commit perfectly. A transaction that checks a sum and then updates a different row can race another equally reasonable transaction. Later lessons use those failures to separate programmer intent from guarantees the database actually implements.

4. I: which interleavings may commit?

Isolation constrains what concurrent transactions may observe and change. Serializable isolation asks whether the committed execution is equivalent to some one-at-a-time ordering. Weaker levels deliberately admit additional histories. A stable snapshot is valuable for a report, but does not by itself protect a decision spanning several rows.

We will use MySQL 8.4’s named levels precisely, and compare selected PostgreSQL 18 behaviors. The names are not a portable substitute for an engine/version, read type and SQL schedule. This module begins on a single server so that replication lag and routing do not hide the concurrency mechanism.

5. D: which failure survives?

A commit contract must specify persistence settings and the failure domain. InnoDB’s commit-flush configuration, the binary log, storage behavior and replica acknowledgement are separate pieces. The MySQL experiment records its flush settings. It does not simulate host loss or claim that a local commit survives loss of the whole replica group. See the acknowledgement boundary in Lesson 33.

A dropped connection during COMMIT is uncertainty. The commit may already exist. Blindly running the transfer again can duplicate it. Use an operation key with durable outcome lookup; do not classify every transport error as an abort.

6. Boundaries that escape

A Kafka publish, HTTP call or email sent between SQL statements is not rolled back by the database. An outbox can record the intended event in the same database transaction, followed by retryable publication and consumer deduplication. That is the boundary from Lesson 2, now with explicit isolation requirements.

Also inspect implicit boundaries. MySQL DDL can commit an existing transaction; wrapping schema changes in START TRANSACTION is not a general rollback strategy. Transactional data changes, schema operations and nontransactional tables need their documented contracts checked separately.
