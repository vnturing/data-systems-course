Module 2 · Lesson 17

Lab: model one workload three ways

The module so far gave you costs. This lab makes you use them: one workload, a relational design, a hybrid, a DynamoDB sketch and a graph query, and a workbook that shows the workload picking the winner.

~60 min1 interactivecapstone of Module 24-question check
What you can do after this lesson Start a design from the access patterns and their frequencies, price the candidate models with the numbers you now have, name the patterns the numbers do not cover, and defend a choice in a design review.

1. The workload

A professional-network product. Entities: people, companies, positions (a person at a company), educations. These are the access patterns, in the form you would put in a design doc:

#Access patternShape
P1Load a person’s full profile pageone entity, its parts
P2Show a person’s name in a listone field
P3A company changes its nameshared fact
P4Everyone who worked at company Xreverse lookup
P5A person adds a positionsmall write
P6People who share a company with metwo hops
P7Is there a path between two people within three hops?variable-depth traversal

2. Price the first five

P1 to P5 are exactly the operations in Lesson 12’s layout lab, which was calibrated on MySQL. Set how often each occurs per day and see what the workload favors.

Things to try

  1. Leave the defaults (profile views dominate). Which layout has the least total work, and by how much?
  2. Raise renames to the top setting and drop profile loads to the bottom. Does the answer flip? Then untick atomic multi-document commits and watch the torn-state flag appear on the embedded layout.
  3. Untick reverse lookups are indexed and raise reverse lookups. Which layouts are hit hardest?
  4. Find a weighting where the referenced-companies layout wins. What does that tell you about it?

The point is not that one layout is better. It is that the workload chose the layout, and that three of the five inputs (rename frequency, reverse-lookup frequency, profile frequency) are numbers someone has to know. If nobody does, measuring them is the first task.

3. The designs

Relational

Lesson 12’s tables. Pattern P6 is a self-join through the position table, and it uses the index on company_id:

CREATE TABLE company  (id INT PRIMARY KEY, name VARCHAR(40) NOT NULL);
CREATE TABLE person   (id INT PRIMARY KEY, name VARCHAR(40) NOT NULL);
CREATE TABLE position (
  id INT PRIMARY KEY AUTO_INCREMENT, person_id INT NOT NULL, company_id INT NOT NULL, title VARCHAR(30) NOT NULL,
  FOREIGN KEY (person_id)  REFERENCES person(id),
  FOREIGN KEY (company_id) REFERENCES company(id),
  KEY idx_company (company_id, person_id)
);
INSERT INTO company VALUES (7,'Acme'),(8,'Globex');
INSERT INTO person  VALUES (1,'Ada'),(2,'Grace'),(3,'Linus');
INSERT INTO position (person_id,company_id,title) VALUES (1,7,'engineer'),(2,7,'lead'),(2,8,'advisor'),(3,8,'engineer');
-- P6: people who share at least one company with person 1
SELECT DISTINCT p2.person_id
FROM position p1
JOIN position p2 ON p2.company_id = p1.company_id AND p2.person_id <> p1.person_id
WHERE p1.person_id = 1;

Hybrid: relational core plus a JSON column

Keep identity and relationships relational (so foreign keys, joins and rename stay cheap), and put variable, display-only attributes in JSON. Promote the one field you filter on:

CREATE TABLE member (
  id       INT PRIMARY KEY,
  name     VARCHAR(40) NOT NULL,
  attrs    JSON NOT NULL DEFAULT (JSON_OBJECT()),            -- variable, display-only attributes
  country  VARCHAR(2) GENERATED ALWAYS AS (attrs->>'$.country') VIRTUAL,
  KEY idx_country (country)                                  -- the one field queries filter on
);
INSERT INTO member (id, name, attrs) VALUES (1,'Ada','{"country":"GB","interests":["maths","engines"]}');
SELECT id FROM member WHERE country = 'GB';

DynamoDB (a sketch, not validated here)

Start from the access patterns, not the entities, as the AWS guidance instructs.[1] A single-table layout in the style that guidance describes might look like this (key layout only; I have not run it on DynamoDB, and the exact design should follow the AWS pages):

PKSKAttributesServes
PERSON#7PROFILEname, headlineP1 (query PK), P2
PERSON#7POS#2019#COMPANY#42title, company name (copied)P1, P5
COMPANY#42PROFILEnameP3 (but copies elsewhere go stale)

P1 is a single query on PK = PERSON#7 that returns the profile and its positions together: the locality benefit. P4 needs a second access path (a global secondary index with company as the key). P3 now has the Lesson 12 problem: the copied name must be updated wherever it appears, and DynamoDB has no join to avoid the copy. That cost is visible in the table before you write a line of code.

Graph, for P7

“Is there a path within three hops?” is Lesson 15’s variable-depth question. With people connected through companies as edges, use a bounded recursive query (or a graph engine if this is core to the product). Whatever you use, bound the hops and use a visited set, because fan-out will dominate the cost.

4. A design review you could defend

PatternWhat the numbers sayRecommendation (my judgment)
P1, P2Hot, read-heavy, one entity: a document is 1 read versus 13Serve profile pages from a document-shaped layout (a JSON column, a cache, or a precomputed document)
P3Shared fact: 1 row versus hundreds of documentsKeep company as its own entity; copy the name only if a snapshot is what you want
P4Reverse lookup: 401 reads indexed versus 20,003 notIndex it, or keep a junction table
P5One write either wayEither
P6Not in the cost model; a two-hop join through a shared entityRelational self-join with the composite index; measure at your data size
P7Fan-out compounds per hopBounded traversal; graph engine only if core

Notice the shape of that answer. It is not “use a document database” or “use SQL”. It is different structures for different patterns, joined by a way of keeping them consistent, which brings you back to Lesson 2: derived or duplicated copies (a profile document, a graph store, a search index) are fed from the source of truth through an outbox or change capture, and the consumers must tolerate duplicates.

5. Three questions before you choose

  1. What are the access patterns, and how often does each run? (If you do not know, measure before designing.)
  2. Which facts are shared and must change everywhere at once, and which are snapshots?
  3. Where does each rule live (Lesson 14), and what plan will the data be read with (Lesson 16): chosen by an optimizer, or by you?

6. Check yourself

Optional: write the pattern table for your own system (30 minutes)

For one service, write its access patterns in the table form above with a rough frequency for each. For the two most frequent, price the layouts you are considering using this module’s numbers as a guide. Where the table has a pattern you cannot price, that is your first measurement.
