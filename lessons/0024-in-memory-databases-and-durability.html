In-memory databases: when is a reply durable?

Memory can serve the reads while disk protects the writes. “In memory” tells you little about what survives a failure.

What you can do after this lessonDistinguish a process crash from loss of the host’s volatile state, trace an acknowledgement through memory and persistence, and state a recovery promise with a failure model attached.

1. Four different places a write can be

application memory → kernel write cache → durable storage
        reply?              reply?             reply?

recovery: load a snapshot, then replay a durable log suffix

InnoDB from Lesson 21 already uses memory aggressively. An engine designed around memory can choose data structures without making disk pages its main read unit. It can still use a log and snapshots for recovery. Neither a memory-resident dataset nor a successful reply proves durability.

A process can die while the operating system keeps cached file writes alive. Losing the host’s RAM also loses that cache. On Linux, write() and fsync() address different boundaries: successful fsync waits for modified file data and metadata to reach the storage device. File creation or replacement can require directory synchronization too.[2] These promises still rely on the OS and storage honoring them. We do not test firmware or power-loss protection here.

2. Redis makes the trade visible

Redis documents two persistence mechanisms: RDB snapshots capture a dataset at a point in time; an AOF records mutations for replay. With both enabled, Redis uses the AOF on restart because it normally contains the more complete history.[1]

ChoiceRecovery questionCost or limit
No persistenceCan another authority rebuild it?This process’s memory is the only local copy.
RDB snapshotsWhat was in the last completed snapshot?Later acknowledged changes may disappear.
AOF, everysecWhat reached a completed synchronization?Recent replies can precede durable storage.
AOF, alwaysWas the append synchronized before the reply?Synchronization lies on the reply path; batching can share its cost.
AOF, no explicit fsyncWhat did the OS happen to flush?The application has not established a per-write durable boundary.

Everysec targets roughly a second of exposure under ordinary operation; it is not a real-time scheduling theorem. Slow storage and stalled synchronization matter. Snapshot intervals, fork overhead, copy-on-write memory, and AOF rewriting also belong in a capacity review. Persistence settings are a performance and failure trade, not a toggle labeled “safe”.

3. Crash at the acknowledgement boundary

At the default crash time below, five SETs have been acknowledged. A completed synchronization at 1,000 ms includes only the first three. Predict the recovered counter for a process-only crash, then for loss of the host’s volatile state.

Try: keep everysec selected and switch the failure. Then compare always with a snapshot. Move the crash across 2,000 ms. In this model an event at the crash time completes before the crash. All scheduled flushes and snapshots are idealized and instantaneous; the lab measures no latency.

4. What we actually crashed

The reproduction script used two disposable Redis containers. One started with AOF/everysec. The other started with AOF off and automatic snapshots disabled, then took an explicit SAVE. We sent SIGKILL to the Redis process and restarted the same container with its files intact.

Before process killAfter restart
AOF/everysec: SET returns OKThe acknowledged value survived.
RDB: SAVE snapshot-value; SET newer-acknowledged-valuesnapshot-value returned; the later reply did not survive.

The recorded observations establish those process-crash outcomes only. An AOF write can survive SIGKILL in the OS cache even before fsync. We did not pull power or crash the kernel, so this is no evidence that everysec has zero host-failure loss. Nor does one restart measure the largest possible loss window.

A mistake the experiment caughtChanging appendonly at runtime did not change the container’s startup command. Restarting brought AOF back on and loaded its older history instead of testing RDB alone. Separate startup configurations fixed the experiment. A recovery test must verify the configuration used after restart, not just before the crash.

5. Write the promise you need

For a recomputable cache, “rebuild after process loss” may be enough. For the only record of a payment, an acknowledged-write loss budget of zero demands a much stronger persistence and recovery design. Replication can add copies, but acknowledgement and common failure domains still matter; Lesson 6 already showed why copies are not automatically independent.

Record four things: the failure being tolerated, the maximum acceptable loss of acknowledged data, how long recovery can take, and which authority can rebuild the state. Snapshot size and replay length affect recovery time even when no committed data is lost. Also separate eviction, a deliberate memory policy, from crash recovery. A durable engine can still intentionally expire or evict data under its configured rules.

6. Check yourself

Optional: write a recovery contract (15 minutes)

Choose a cache or primary store. State its tolerated failure, acknowledged-data loss budget and recovery-time budget. Find the configured persistence mode and startup configuration. Design a scratch recovery drill that tests exactly that failure; name what it cannot establish.

Ask the course agent if the acknowledgement or failure boundary is unclear; it is the central question of this lesson.
