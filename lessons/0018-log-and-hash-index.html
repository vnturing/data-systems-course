Module 3 · Lesson 18

The world’s simplest database: an append-only log and a hash index

Before B-trees and LSM-trees, there is a design small enough to hold in your head, and every later structure is a response to one of its limits.

~40 min1 interactive1,400 randomized crash tests4-question check
What you can do after this lesson Explain how a log-structured hash store works, what it makes cheap (writes and point reads), what it costs (space until a merge, memory for every key, no range queries), and exactly how it recovers from a crash in the middle of a write.

1. Start with a file you only append to

Suppose storing a key means appending a line to a file, and updating a key means appending a newer line. Writing is as cheap as it gets: no seeking, no in-place edits. Reading is the problem. To find a key you scan from the end of the file until you hit it, which takes time proportional to the file.

The fix is one extra structure: an in-memory hash table mapping each key to the byte offset of its latest record. This is the whole design of Bitcask, the storage engine described in a short paper from Basho for its Riak database: writes append to an active data file, an in-memory hash table (the keydir) maps each key to the file, offset and size of its latest value, and a read needs at most one disk seek.[1] A delete appends a tombstone, a special record meaning “this key is gone”.[1]

2. Real bytes, so recovery is real

I built this in the browser with actual bytes rather than a diagram. Each record is laid out as a checksum, a type, the key and value lengths, the key, and the value. A read looks up the offset and decodes the record. A write appends one. Nothing else.

What to notice

  1. Overwrites pile up. With 6 writes per key the log is about 6× larger than the live data (space amplification). Old versions are dead but still on disk.
  2. A merge fixes it. Click Merge: only live records are rewritten into a fresh log, space amplification drops to 1.0, and tombstones disappear because the whole log was rewritten. The merge itself costs I/O: it reads the entire old log and writes the live data. Reclaiming space is not free, and the “write amplification” figure rises after it.
  3. The index costs memory per key. The memory column uses a placeholder of ~47 bytes per entry (my parameter, not a measurement of any real engine). Whatever the constant, the design needs memory proportional to the number of keys, which the Bitcask paper states as its main constraint.[1]
  4. Now crash it. Drag the crash slider. It keeps only the first n bytes of the log, as if the machine died mid-append. Recovery scans from the start, checks each record’s checksum, and stops at the first incomplete or corrupt record.

3. Why recovery stops where it stops

Records are variable-length: where record n+1 begins is read from the header of record n. If a record is torn (only part of it reached the disk) or damaged, nothing after it can be trusted, because you cannot know where the next one starts. So recovery accepts the longest valid prefix and discards the rest. The guarantee is exactly that: after a crash at any byte, the recovered state equals the state after the last complete record.

That claim is easy to state and easy to get subtly wrong, so I tested it rather than trusting it. The course’s test truncates the log at random byte offsets and flips random bits inside random records, then checks the recovered state against a reference. It ran 1,400 randomized trials across 40 random operation sequences, and every one recovered correctly (tools/test-log.js). This is the same crash-point thinking as Lesson 2, applied to a single file.

4. What this design is good and bad at

CheapExpensive or impossible
Writes: one sequential appendSpace: dead versions accumulate until a merge
Point reads: one hash lookup + one seekMemory: every live key must be in RAM
Crash recovery: the log is the commit recordRange queries: a hash table has no order
Simplicity: a few hundred linesStartup: rebuilding the index means scanning the data (Bitcask uses hint files to speed this up[1])

Why append instead of updating in place? The motivating idea behind log-structured designs is that sequential writes are cheaper than scattered ones. The LSM-tree paper, which Lessons 19 and 20 build on, was written for the case of a high rate of inserts over a long period, and its trick is to defer and batch index changes so that disk writes are efficient.[2] How big the sequential-versus-random gap is depends on the device, and I did not measure disk speeds here: this sandbox’s storage is not representative of yours. Everything in this module is measured in bytes and operations, not seconds.

Every structure in the rest of this module is an answer to one of the limits in the right-hand column. The LSM-tree keeps appending but sorts the data to get range scans and to remove the all-keys-in-memory limit. The B-tree gives up appending to update pages in place.

5. Check yourself

Optional: build the smallest version yourself (30 minutes)

In any language: append key,value lines to a file, keep a dictionary of key → byte offset, and implement get by seeking. Then truncate the file at a random byte and rebuild the dictionary by scanning. Without a checksum, can you tell a torn last line from a complete one? That question is why the record has a CRC.
