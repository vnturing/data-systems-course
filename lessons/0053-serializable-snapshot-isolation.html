Module 7 · Lesson 53

Serializable snapshot isolation and actual serial execution

Serializability is a property of the committed history. Blocking locks, dependency checks with aborts, and actually running transactions one at a time can all establish that property through different mechanisms.

~35 min1 interactive4-question check
What you can do after this lessonExplain how SSI detects unsafe dependency patterns, distinguish its read markers from blocking locks, and compare its costs with actual serial execution.

1. The specification does not prescribe the scheduler

A serializable execution has effects equivalent to some complete one-at-a-time order of the committed transactions. The transactions may overlap physically, as long as the committed observations and effects admit that order. Actual serial execution is one implementation; two-phase locking and serializable snapshot isolation are others.

Serializability does not by itself specify a wall-clock freshness order across replicas, HTTP requests or external side effects. A transaction can also faithfully serialize incorrect business logic. Keep the isolation property distinct from the invariant and the end-to-end response contract.

2. Start with snapshots, add dependency checking

The roster has two anti-dependencies: A read doctor 2 before B’s change, and B read doctor 1 before A’s change. Letting both transactions commit would require A before B and B before A. Snapshot isolation alone checks overlapping writes and misses this disjoint-write cycle. SSI tracks additional read/write relationships and rejects unsafe combinations.

Predict first: snapshots alone let both doctors leave. With SSI, one attempt aborts and its full retry sees only one doctor left. With actual serial execution, the second decision starts after the first finishes. The invariant holds through different scheduling behavior.

3. SSI does not run a complete cycle detector for every history

The Ports–Grittner paper describes an efficient check for dangerous structures involving consecutive read/write anti-dependencies, refined by commit-order information. Such a structure can indicate a possible serialization anomaly without being a complete cycle. Conservative aborts are therefore possible.

Our two-transaction widget shows one concrete cycle, not that production detector. It cannot predict every PostgreSQL abort, victim choice, safe read-only view or memory-management case. The real server fixture separately records the roster failure under repeatable read and a serialization failure under serializable isolation.

Do not teach the rule as “abort whenever two transactions share a read” or “every anti-dependency is unsafe.” Harmless overlap exists. SSI’s value is permitting useful concurrency while preventing unsafe histories from fully committing.

4. Predicate markers are evidence, not an ordinary S lock

PostgreSQL’s SIReadLock markers record read coverage for dependency detection; they do not block a writer merely because it changes something an older snapshot read. Write/write conflicts and other locks can still block. Marker granularity can be tuple, page or relation, and coarser tracking can cause more conservative conflicts.

The query plan can therefore affect abort rates as well as execution cost. A wide scan may record broader read evidence than a selective indexed access. This is different from InnoDB range locks that can physically stop an insertion while a locking read remains open.

5. Retrying is part of the contract

repeat up to the operation's bounded retry budget:
    begin a fresh serializable transaction
    read the complete decision inputs
    validate the business rule
    write the changes and any outbox intent
    attempt commit
    on a known retryable abort:
        rollback/close the failed attempt
        back off; recompute from fresh reads
    on uncertain commit outcome:
        recover using the durable operation identity

A serialization failure can happen at a statement or at commit; do not acknowledge success before commit. Do not reuse the doomed attempt’s read results or send irreversible notifications on every attempt. SQLSTATE 40001 identifies PostgreSQL serialization failures; other error classes require their own handling. Idempotency is still needed for uncertain execution and client retries.

6. Actual serial execution changes the resource trade

If each transaction runs completely before the next begins, there is no concurrent decision interleaving inside that execution domain. The second doctor sees the first doctor’s committed change. A short in-memory procedure that accesses local data can avoid concurrency-control overhead in such a design.

But one slow procedure can delay everything behind it. Blocking on an HTTP response while occupying the serial executor turns network latency into the service time for queued transactions. Prepare outside the executor, then perform a short atomic decision with revalidation. CPU, storage, logging, replication and input validation do not disappear merely because concurrency scheduling is simpler.

H-Store is a primary research example of partitioned, serial transaction execution for suitable workloads. Parallel partitions can run independently; a transaction spanning them needs an additional coordination contract. “One thread per partition” alone does not prove serializable cross-partition transactions. Our browser model covers one roster on one execution domain, and measures no throughput advantage.

7. Choose the mechanism with evidence

Compare representative contention, lock waits, abort/retry rates, tail latency, long-reader overhead and transaction duration. An optimistic scheme can waste work on aborts; a blocking scheme can wait before doing it; a serial executor can queue work behind an outlier. None is universally fastest. First establish the invariant, then measure the cost of a correct implementation.
