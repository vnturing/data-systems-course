Module 6 · Lesson 46

Request routing and service discovery

A server address is not a partition map. After ownership moves, a correct client must discover where the key belongs without inventing a second write authority.

~35 min1 interactive4-question check
What you can do after this lessonSeparate membership discovery from key ownership, handle stale routing evidence, and explain Redis MOVED versus ASK using real protocol observations.

1. Two maps and a serving rule

key → logical partition / slot → current node endpoint
+ which replica or authority may serve this operation?

DNS or service discovery can locate a live service endpoint. It does not necessarily say which key ranges or slots that node currently owns. Nor does an owner address alone establish that a chosen replica is sufficiently fresh for a session read.

Common architectures place routing knowledge in a client library, a proxy/coordinator, or servers that forward or redirect stale requests. Each moves metadata caching, extra hops and availability dependencies to a different place. Google Cloud Bigtable’s documented frontend path is one concrete topology; Redis Cluster clients maintain slot maps and handle redirection.[1] Neither architecture is universal.

2. Stale metadata is expected

Clients can keep an older ownership map during a split, rebalance, failover or reconnect. The system needs an explicit response: refresh, forward, redirect, reject, or safely wait. Allowing any old node to keep accepting writes is not a routing repair; it can create the split-brain histories from Lesson 34.

Ownership epochs and node-side checks can make stale requests detectable under a particular protocol. This course does not implement election or fencing through its routing widget. It assumes the advertised authorities enforce the selected phase.

Try: during movement, stop at the redirect, then follow it without ASKING. Finally handle it correctly. After cutover, observe why MOVED changes the cached owner while the temporary ASK exception did not.

3. Real Redis hash slots and hash tags

Redis Cluster hashes key bytes with CRC16-XMODEM into 16,384 slots, with a defined nonempty-brace hash-tag rule.[2] The browser calculation matches 49 independently queried key examples, including non-ASCII text, empty braces and unmatched braces.

In Redis 7.4.12, customer:42 hashes to slot 4672. Both orders:{42}:a and orders:{42}:b hash to 8000; orders:{99}:a hashes to 6263. The same tag can co-locate related keys for supported same-slot operations. It also deliberately concentrates those keys, so it is not a hot-tenant mitigation by itself.

Our cross-slot MSET was rejected with CROSSSLOT. That is a real command constraint, not an assertion that every operation on multiple partitions in every database is impossible.

4. MOVED changes the route; ASK is one request

A query sent to a non-owner received MOVED with the slot and current destination. During controlled migration, after the selected key had moved from A to importing B, GET at A returned ASK. GET at B without ASKING returned MOVED back to A. Sending ASKING then GET on the same connection returned the value.

After the slot-owner update, A returned MOVED to B, and GET at B succeeded without ASKING. These are recorded observations from a three-master internal cluster. The value after cutover remained value-before-move.

The Redis specification distinguishes a one-request ASK exception from the ownership-map update prompted by MOVED.[2] MOVED is not a promise that ownership will never change again. Clients still need bounded refresh/retry behavior and the protocol’s other responses; this toy is not a complete client.

5. Routing errors and uncertain execution are different

The experiment follows GET redirects. It does not prove exactly-once writes under timeouts. If a request might have executed before the connection failed, changing endpoints and retrying can duplicate an application effect. Keep operation identity, idempotency and retry budgets from Lesson 1.

Likewise, a global query during movement can need a consistent metadata/data boundary, merging and deduplication. Per-key redirection alone does not establish an atomic global scan. Directory availability, cache staleness, migration progress and request correctness should have separate metrics.

6. Finish the partitioning review

Use the Module 6 checklist to connect the key, actual load, index placement, movement protocol and route ownership. Module 7 adds transactions: what multiple reads and writes may observe and commit together, whether they run on one partition or several.
