Module 6 · Lesson 43

Skew and hot keys: find the indivisible work

Adding nodes helps only when overloaded work can move or split. A billion quiet keys do not dilute one key receiving most of the requests.

~35 min1 interactive4-question check
What you can do after this lessonDiagnose data, traffic and single-key skew separately; choose salting, caching or admission changes with the read and correctness costs attached.

1. Count work, not only keys

Three different imbalances can look like “one shard is full”: too many bytes, too many requests, or disproportionately expensive operations. A fourth problem is one indivisible item whose serialized work exceeds an owner’s capacity. Moving the item changes which node is overloaded; it does not divide the work.

A key-count histogram is therefore insufficient. Record bytes, request rate, operation mix and service demand per partition and per heavy key. DynamoDB’s partition-key guidance likewise asks for uniform activity across keys and indexes, accounting for item sizes.[1] The widget’s capacity numbers are illustrative, not DynamoDB limits.

Try: begin with independent appended items and one bucket. Increase physical nodes while keeping one bucket. Then use sixteen salt buckets. Switch to repeated reads and try the cache. Finally select a conditional update: the same salting control no longer changes the effective ownership unit.

2. Salting changes a logical access pattern

one tenant bucket:   tenant:42
salted append keys:  tenant:42:0, tenant:42:1, ... tenant:42:15
item route:          stable item-derived suffix or explicitly recorded bucket

If independent appended items can be assigned across buckets, the hot tenant’s work can reach multiple owners. Logical buckets can still collide on the same physical node. More suffixes are not a theorem that every node receives identical load.

The cost appears on reads. “All items for tenant 42 today” now requires the relevant bucket queries and a merge. Ordered pagination must account for progress on each stream; a single cursor for one bucket is not automatically a global continuation token. DynamoDB documents both random and calculated write sharding and the accompanying read fan-out.[2]

A random suffix needs a way to find an individual item later, or a fan-out lookup. A deterministic suffix can route an exact item when its inputs are known. Either strategy requires stable rules or migration metadata when bucket counts change; recomputing against today’s count can hide old items.

3. A cache helps a different operation

Repeated reads of the same value can be served by a cache or, under an appropriate contract, multiple read replicas. The model applies the declared cache hit rate only to the read case. It does not pretend the cache removes authoritative writes, or supply a freshness/invalidation guarantee.

If the value changes often, cache misses may synchronize into a stampede. Versioning, invalidation, request coalescing and freshness requirements belong to that design. Refer back to the retry and admission lessons when a surge makes every miss expensive.

4. An authoritative condition cannot simply be salted away

Consider “decrement stock only if positive.” Splitting one counter into independent bucket counters changes which invariant each operation can inspect. As Lesson 40 showed, merging two correctly recorded local sales can still oversell one shared unit.

The widget keeps a serialized conditional update at one owner. Alternatives include changing the business operation, allocating disjoint rights, coordinating admission, or accepting a weaker promise. Those are explicit semantic choices, not a hashing optimization.

5. A mitigation decision tree

  1. Many keys landed badly? Rebalance or split the ownership ranges, then measure the new distribution.
  2. One read-heavy value? Evaluate caching or read replicas with a freshness contract.
  3. Independent items share one logical key? Consider stable sub-buckets and account for read merge cost.
  4. One serialized invariant is overloaded? Change its admission/ownership design or capacity; do not quietly change correctness.

The model keeps total background work fixed as nodes are added and uses equal request costs. It does not measure CPU, queues, I/O, adaptive capacity or production latency. In particular, salting a partition key is a logical layout choice; a cloud service controls its own physical placement and split behavior.

Check yourself

Optional: apply the mechanism (20 minutes)

Choose a hot partition. Identify whether bytes, traffic, cost or a single serialized key dominates. Propose one mitigation and state the read fan-out, freshness or correctness cost it introduces.

Ask the course agent about any unclear result. Include the partition key, access pattern, ownership map and exact failure or workload.
