JSON, XML and CSV are contracts too

A successful parse can silently change an identifier. Encoding is a boundary between two programs, each with its own types and assumptions.

~30 min2 interactivesreal parser behavior4-question check
What you can do after this lessonWrite a boundary contract that preserves identifiers, money, missing values and binary data across languages, and test the receiver rather than trusting the appearance of the payload.

1. The identifier that parses incorrectly

{"id":9007199254740993}

A producer with arbitrary-precision integers can write this exact token. JavaScript’s ordinary JSON parser turns it into the Number 9007199254740992. Nothing throws. A lookup, dedupe key or signature based on the parsed ID can now refer to something else.

JSON permits numeric syntax; it does not require every receiver to implement arbitrary precision. RFC 8259 identifies integers from −(253−1) through 253−1 as interoperable with common binary64 implementations.[1] That is an interoperability bound, not a rule that every integer above it is unrepresentable.

Try: predict the received value for the numeric ID, then the quoted ID. Compare null with a missing field. Finally try duplicate keys and decimal arithmetic. These run the browser’s JSON parser, not a simulation of it. The independent Python experiment retains the large integer exactly, demonstrating why a same-language round trip can miss the problem.

2. Put meaning next to the type

For this course’s payment example, a useful contract is:

{"id":"9007199254740993","amount_minor":1200,"currency":"USD"}

id: decimal digits, exact text identity; do not convert through Number
amount_minor: integer minor units, bounded to the agreed safe range
currency: explicit code; amount 1200 USD means USD 12.00 here

This is our application design, not a property of JSON. An integer amount still needs a unit, range, sign policy and currency. A decimal string can preserve a decimal value, but the receiving code still needs appropriate arithmetic. Quoting 0.1 does not make a later conversion to binary floating point exact.

Likewise, a PATCH API might define an absent name as “leave unchanged” and null as “clear it”. Another API may reject null. Decide and test that distinction. Duplicate object names need an explicit rejection policy if ambiguity matters: this browser keeps the last tier, while RFC 8259 describes differing parser behavior.[1]

3. Text length is not wire length

The name Zoë is three Unicode code points and four UTF-8 bytes. JavaScript string length counts UTF-16 code units; an emoji can occupy two such units. When a binary format prefixes a string length, you must know whether it counts bytes or characters.

JSON has no separate arbitrary-bytes type. A common contract represents bytes using Base64, identifying which alphabet and padding rules apply. Base64 encodes each three input bytes as four characters, with padding for a partial final group; its padded length is 4 × ceil(bytes/3).[2] Zoë’s four UTF-8 bytes become eight Base64 characters, before JSON quotes or a field name. This is encoding overhead, not compression.

4. XML has richer types when you use a schema

<payment><id>9007199254740993</id><amount>12.00</amount></payment>

Reading element text alone gives strings. XML Schema can declare decimal, integer and binary datatypes, including base64Binary.[3] “XML only has strings” overlooks that layer. Conversely, a schema declaration does not prove the application uses a validating reader or an exact decimal representation. Inspect the actual parser, binding and application conversion.

The decision is where the contract lives and who enforces it. JSON can also have an external schema; CSV can have a documented typed import contract. A human-readable format does not remove the schema assumptions from the programs.

5. CSV records are not necessarily lines

150,"Doe, Jane","line one
line two"

This is one record with three fields. Splitting on commas gives four pieces; splitting on newlines gives fragments of a record. RFC 4180 documents quoting commas, line breaks and embedded double quotes.[4] Our Python experiment parses this with the standard CSV reader and records both correct and naive results.

CSV also needs agreement on headers, delimiter dialect, encoding, null versus empty, dates and numeric interpretation. If an import turns a leading-zero account number into a number, the CSV parser may have worked while the import contract failed. Test the complete path into the destination type.

6. Check yourself

Optional: audit one payload (15 minutes)

Take a boundary you own. List identifier type/range, amount units, missing/null behavior, binary representation and receiver library. Test a large integer, a leading-zero ID, non-ASCII text and a multiline CSV field where applicable. Use scratch data.

Ask the course agent about any unexpected received value. Include the literal bytes and both language types.
