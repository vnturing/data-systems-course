Module 4 · Lesson 32

Lab: three versions, nine compatibility pairs

The latest producer and consumer work together. The deployment can still fail when someone replays history or rolls back.

~40 min1 migration workbookreal Avro cross-checksmodule capstone
What you can do after this lessonAudit a three-version migration against live traffic, retained data and rollback, then separate decode compatibility from the correctness of the interpreted amount.

1. Declare the workload before inspecting the matrix

Each sample payment represents USD 12.00. Version 1 has an id and an integer amount measured in cents: 1,200. All historical payments in this exercise are USD. The reader’s job is to recover that amount correctly. We deliberately keep the workload small enough to inspect every pair.

Rows in the matrix are writer versions; columns are reader versions. A cell runs a writer encoder followed by a reader resolving the actual writer schema. It reports whether decoding succeeds, which fields were defaulted or ignored, and the amount interpreted in cents.

The independent Python experiment runs all nine pairs in each of six scenarios with Apache Avro 1.12.0. The browser covers flat records with int, long and string fields; it is not a registry compatibility engine or a proof for arbitrary schemas.

2. Establish a safe baseline

Start with Add fields with defaults. Version 2 adds currency with default USD. Version 3 adds note with default empty string while retaining currency’s default.

v1: id long, amount int
v2: id long, amount int, currency string default "USD"
v3: id long, amount int, currency string default "USD", note string default ""

Before looking: predict v1→v3, v3→v1 and v2→v3. Then inspect those cells. Explain why the old reader can produce the right amount while ignoring note. That success is specific to the declared workload; it does not show that an old consumer implements every newly introduced feature.

3. Break replay without breaking the adjacent check

Choose Add default; later remove it. Version 2 still adds currency with default USD. Version 3 keeps the field but removes its reader default. Answer these before selecting the cells:

  1. Can a v2 reader read v1? It must supply a currency.
  2. Can a v3 reader read v2? The writer included currency in the bytes.
  3. Can a v3 reader read v1? The writer did not include currency, and the reader has no default.

The first two work. The third fails. A check of v3 against v2 alone misses a retained v1 record. Set both live roles to v3: live traffic works. Keep retained v1 records required and inspect the audit failure.

Confluent distinguishes checking the latest schema from transitive checks against all earlier registered versions. Its documented BACKWARD policy is non-transitive; BACKWARD_TRANSITIVE extends that history check.[1] AWS Glue uses its own compatibility modes, including BACKWARD_ALL.[2] Verify the actual registry, format, subject or checkpoint scope and configuration rather than transferring names between products.

A replay repairIf every historical missing currency really means USD, retaining that reader default preserves the interpretation. Otherwise migrate the old data or introduce an explicit unknown state and corresponding business handling. Unchecking the history box does not migrate anything; it only removes a requirement from this toy audit.

4. Make all parsers happy and the money wrong

Choose Keep integer; change money units. Version 1 writes 1,200 cents. Versions 2 and 3 write 12 dollars into the same amount field, with the same Avro integer type. The unit property shown in the schema inspector is application metadata; Avro does not enforce its meaning.

Every matrix cell decodes. A v1 reader interprets a new writer’s 12 as twelve cents. A v3 reader interprets an old writer’s 1,200 as 1,200 dollars. Both are wrong by a factor of 100. The diagonal cells remain correct because those writers and readers share a unit assumption.

With both live roles at v3, turn history and rollback requirements off, then back on. The live-only result is not evidence that historical replay or rollback is safe. This is why a green schema check is evidence about representation rules, not a complete application correctness argument.

A safer design gives the new representation an explicit identity, such as a new amount_minor field with documented currency and bounds, or a versioned amount structure. Transitional readers can distinguish forms. Do not silently reinterpret an existing field or reuse a Protobuf tag. Any fallback must preserve the historical meaning.

5. Write the migration proof

For one proposed migration, write six short statements before reading the worked example:

  1. The invariant the reader must preserve.
  2. The old writer versions that retained data can contain.
  3. The live mixed-version pairs during deployment.
  4. The reader version used by rollback.
  5. The evidence for every required pair, including interpreted values.
  6. The condition that permits retiring old handling.
Worked example: additive USD currency field

Invariant: recover USD 12.00 from every sample. Retained writers: v1–v3. Prepare readers with the historical USD default, then activate writers that emit currency. Keep a compatible prepared rollback reader. Execute all nine writer/reader pairs, and assert amount semantics in addition to decode success. Test each rewriting intermediary as in Lesson 31. Retire the old form only after its live, replay, backup and rollback obligations are discharged.

The default works because the historical USD premise is declared. If old records could be EUR, the same default would silently invent a currency. Structural success would not repair missing information.

Avro’s specification defines reader defaults and writer/reader resolution.[3] The dollar invariant, migration audit and repairs here are original course exercises. No application or registry has been deployed by this workbook.

6. Check yourself

Optional: transfer the proof to work (25 minutes)

Pick a small schema change. Fill the six statements above and add a new→old updater→new preservation test. Use actual serializers and historical samples on a scratch path. List anything your test cannot establish.

Ask the course agent to challenge your migration proof. Use the Module 4 checklist when reviewing a deployment. Module 5 moves from evolving representations to keeping copies on different machines.
