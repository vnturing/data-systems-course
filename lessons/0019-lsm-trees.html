Module 3 · Lesson 19

Memtables, sorted runs, and the LSM-tree

Keep the log, but sort it. That one change removes the memory limit and brings back range scans, and it creates a new problem (compaction) that fills the next lesson.

~50 min1 interactivecalibrated on real RocksDB4-question check
What you can do after this lesson Trace a write and a read through a memtable, a write-ahead log and sorted runs; explain tombstones and bloom filters; and predict how write amplification grows with the number of levels.

1. From a log to sorted runs

Lesson 18’s log is fast to write but unsorted, so it needs an index of every key in memory. The LSM-tree paper’s idea is to sort in memory, write sorted batches to disk, and merge them later like a merge sort. Its abstract describes it as a disk-based structure designed for high insert rates, which defers and batches index changes, cascading them from a memory component through one or more disk components; it also says plainly that indexed finds needing immediate response can lose I/O efficiency in some cases.[1] That honest caveat is the theme of Lesson 22.

The terms most engines use come from Google’s Bigtable paper. A write goes to a commit log (for durability) and to an in-memory sorted structure, the memtable. When the memtable reaches a threshold it is frozen and written out as an immutable sorted file, an SSTable, which Bigtable calls a minor compaction; merging compactions bound how many SSTables exist, and a major compaction rewrites them all into one that contains no deletion information.[2] LevelDB’s implementation notes describe the same flow: a log file plus a memtable, with a full memtable flushed into a level-0 file, and level-0 files may overlap each other.[3]

2. The write path and the read path

  1. Write: append to the write-ahead log (so the memtable survives a crash), insert into the memtable. That is all the user waits for.
  2. Flush: when the memtable is full, write it out as a sorted, immutable file.
  3. Compact: in the background, merge files so the number of places a key can hide stays bounded.
  4. Read: look in the memtable, then in each sorted run from newest to oldest, stopping at the first version of the key. A run whose key range does not cover the key is skipped for free, and a bloom filter (a compact bit array that can say “definitely not here”) lets most remaining runs be skipped too. Bigtable lists bloom filters as a way to reduce disk accesses for lookups.[2]
  5. Delete: write a tombstone. Older copies of the key sit in immutable files the delete cannot touch, so the tombstone hides them until compaction removes both.

3. Watch it run

The lab below is a real miniature LSM-tree: it keeps real sorted runs, performs real merges, and counts what it does. (It stores keys and version numbers rather than values, which does not change the counts.) I calibrated it against RocksDB, running a real RocksDB through its Python binding on the same ratios (a 4 MB memtable, an 8 MB first level, ratio 10, no compression).

What to notice

  1. Write amplification grows with the number of levels. Real RocksDB, leveled, random keys: 2.27 at 6 memtables of data, about 5.0 to 5.3 at 26, 5.3 to 5.8 at 52, and 6.7 to 6.8 at 103. The model gives 1.6, 4.3 to 4.5, 5.8 and 7.2: within about 8% at the two largest sizes, and 12 to 28% low at the two smallest (small runs are dominated by details the model omits). Each level a record passes through means rewriting it again.
  2. Keys in order are almost free. Switch to “Keys in order”. Write amplification falls to about 1 (real: 1.06), and the “moves without rewriting” counter rises, because files with disjoint key ranges can simply be moved down a level.
  3. The ratio T barely matters here. Between ratio 4 and 10 the real measurements overlap (5.5 to 6.0 vs 5.3 to 5.8 at 52 memtables, across repeated runs). A bigger ratio means fewer levels but more rewriting per level, and the two roughly cancel at this scale. Do not assume the ratio is a strong knob without measuring your own workload.
  4. The write-ahead log is a second write. Everything above counts only the sorted files. Adding the log adds about 1 to the total (the model reports it as waTotal).
Measurement noise is real RocksDB’s background compaction timing makes repeated runs differ even with fixed random seeds. The same configuration at 26 memtables gave 4.98 in one run and 5.34 in another, and the number of sorted runs left at the end varied between 4 and 5. I report ranges for that reason, and a single published number for leveled write amplification (secondary articles quote anything from about 5 to 30×) should make you ask: at what data size, ratio, and workload?

4. Check yourself

Optional: look at your own engine (20 minutes)

If you run RocksDB, LevelDB, or anything built on them, find its memtable size, level ratio, and compaction trigger, and the statistics it keeps about compaction bytes written versus bytes the application wrote. The ratio of the two is your write amplification.
