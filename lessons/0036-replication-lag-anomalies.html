Module 5 · Lesson 36

Replication lag: name the broken guarantee

“Eventual consistency” does not name the user-visible problem. Trace what a particular session saw, then ask which guarantee it needed.

~35 min1 interactive4-question check
What you can do after this lessonDistinguish read-your-writes, monotonic reads and an ordered prefix; design a read route or barrier that protects the required history.

1. Three observations that look like “stale”

  • Read your writes: you update your avatar to v2, then read v1 from a lagging follower.
  • Monotonic reads: you read v2, then a later read returns v1, even though you did not write either value.
  • Ordered prefix: you observe an order confirmation without the earlier order creation it depends on.

The first two are session guarantees developed in the Bayou work: restrict reads to replicas containing the session’s required writes or already observed history.[1] They do not require every other client to see the same latest state.

The prefix example concerns visibility of an ordered/dependent history. A follower applying one sequential committed log prefix cannot expose entry 2 while omitting entry 1 from that same prefix. With separate streams, shards or read paths, “every stream is ordered” does not establish the combined dependency. Causal consistency explicitly addresses visibility of causal predecessors.[2]

Try: reproduce each anomaly. Staying at A repairs the first two toy traces, but it is not a general causal protocol. For the cross-stream example, require the missing dependency: the correct result may be a wait or an unavailable response rather than a fabricated complete view.

2. A version barrier is evidence; a delay is a guess

A write response can carry a position or transaction token. A later read is eligible only on a server that has applied the required history. The service can wait, route to another eligible node or return a bounded failure. Sleeping for 500 ms cannot prove replication completed during an outage.

write at source → capture required committed transaction context
read candidate → wait for that context to be applied
success → read using a fresh suitable snapshot
wait timeout → route elsewhere or return an explicit failure

In the real MySQL drill, B had received the source’s GTID set but its SQL applier was paused. The row count was 0 and WAIT_FOR_EXECUTED_GTID_SET timed out with 1. After apply resumed, the wait returned 0 and the row count became 1. Those are function return codes, not seconds of lag.[3]

The experiment obtains the whole source executed set as a simple barrier. A production application needs a trustworthy token associated with its own committed operation; the whole global set can include unrelated work and overconstrain reads. A successful wait also does not refresh a snapshot that was already opened before the change. Transaction visibility and replication eligibility both matter.

3. Sticky sessions have a failure case

Keeping a session on one sufficiently fresh replica can prevent it moving backward in the simple history. But a restarted session, another device or failover may choose another node. If the service silently routes to any available stale copy, its session guarantee ends at exactly the failure users notice most.

Track the required history across the scope of the promised session, and name how it is propagated. A per-device cookie does not automatically create a cross-device guarantee. A new primary selected without all acknowledged writes can also break an assumption that “read from the leader” alone fixes everything.

4. Vendor contracts are specific

DynamoDB documents eventually consistent and strongly consistent reads for tables and local secondary indexes, while global secondary indexes and streams have different read options.[4] A strong table read does not turn a GSI query into the same operation. This modern DynamoDB contract is not the 2007 Dynamo paper’s interface.

For any product, ask which resource, region, consistency setting and session scope the guarantee covers. Do not equate a label such as “consistent prefix” with every cross-partition causal guarantee. The lab’s examples specify their histories directly rather than claiming to emulate a vendor consistency mode.
