Module 3 · Lesson 26

Column storage, compression and vectorized execution

Read fewer columns. Skip irrelevant groups. Encode repeated values. Process values in batches. These are four separate mechanisms; measure them separately.

~40 min2 linked interactivesreal Parquet files4-question check
What you can do after this lessonExplain each source of scan savings, distinguish physical layout from execution strategy, and interpret file metadata without mistaking it for measured I/O or query speed.

1. Row layout and column layout answer different reads

row layout:    [id, day, region, amount, payload...] [id, day, region, amount, payload...]
column layout: [id, id, ...] [day, day, ...] [region, region, ...] [amount, amount, ...]

A scan summing amount for recent dates needs day and amount. With separate columns, it can leave unrelated payload behind. C-Store describes column-oriented projections and compact encodings as parts of a read-optimized design.[1] A row lookup needing all twelve columns has a different access pattern: assembling values across columns can add work. Column layout does not repeal the workload trade-off.

2. Group pruning depends on order

A columnar file can store minimum and maximum values per group. If a group’s maximum date is below the query’s lower date bound, it cannot match. If recent dates are scattered across every group, the same predicate excludes none. DuckDB documents projection and filter pushdown for Parquet scans.[4] Projection and group pruning multiply savings only when both apply.

Try: increase needed columns from two to twelve, then unsort the filter column. Keep those settings while changing the batch size. Bytes should stay fixed when only the batch changes. Finally, switch the encoding order: repeated values are not necessarily long runs.

3. What real Parquet files show

The experiment writes 200,000 rows, twelve columns and twenty 10,000-row groups with PyArrow 22.0.0. Eight columns contain hash-derived payload strings. Both files contain the same rows; one is sorted by day, the other shuffled with seed 42. DuckDB 1.4.2 runs:

SELECT COUNT(*), SUM(amount)
FROM read_parquet('sorted.parquet') WHERE day >= 95;

Both return 10,000 rows and sum 5,982,595. Their metadata reports:

These are sums of recorded compressed chunk sizes, excluding file metadata. The last row is the size of eligible chunks calculated from min/max statistics. It is not a disk-read trace: filesystem caching, metadata requests, page-level decisions and reader behavior can change actual I/O. We verify query results and preserve the raw metadata results; we make no latency comparison with MySQL.

4. Dictionary encoding, runs and compression

A dictionary replaces repeated values with small IDs. Bit packing stores those IDs in the bits their range requires. Run-length encoding represents repeated adjacent values with a value and a count. Delta encoding represents differences between successive values. Parquet specifies these encodings, including a hybrid of run-length and bit-packed dictionary IDs; general compression such as Zstandard is a separate layer.[2]

We isolated one 200,000-value INT32 status column with four equally frequent values. With no general compression, plain Parquet used 800,061 bytes in its column chunk. Dictionary encoding used 104 bytes sorted into four runs, or 50,490 bytes shuffled. Enabling Zstandard on the tiny sorted dictionary chunk increased it to 122 bytes: codec framing can cost more than it saves. These are measured chunk sizes, including encoding/page overhead, not the toy encoding’s formulas.

The toy intentionally uses a simpler RLE: a one-byte ID and four-byte count per run. Alternating values make that larger than plain INT32. Real hybrid encoders can choose packed runs instead. Never transfer the toy’s byte counts to Parquet.

5. Vectorized execution is another axis

A tuple-at-a-time executor repeatedly calls operators for individual rows. A vectorized executor passes batches of values, amortizing dispatch and exposing tight loops. MonetDB/X100 develops this execution strategy and examines its CPU effects.[3] The widget counts only batch dispatches: 10,000 values in batches of 2,048 need five batches. That does not imply a 2,000-fold speedup; arithmetic, decoding and memory access still happen.

Vectorized execution is not synonymous with SIMD. SIMD means one CPU instruction acts on multiple lanes. A batch loop may use SIMD, scalar instructions, or a mix. Conversely a row-oriented engine can batch some operations. Layout, encoding and execution strategy are separable decisions.

A filter can produce positions or a selection mask; later operators can process only those positions rather than reconstructing complete rows immediately. This avoids hauling payload through a pipeline that only needs a sum. Point updates, concurrent visibility and maintaining sorted groups still cost work; this lesson models none of them.

6. Check yourself

Optional: explain one scan (20 minutes)

For a report, list its required columns, filter column order, expected group overlap, distinct-value counts and execution strategy. Reproduce the files on a scratch machine. If reporting I/O or latency, add actual instrumentation rather than relabeling metadata bytes.

Ask the course agent to separate any confusing performance claim into projection, pruning, encoding and execution.
