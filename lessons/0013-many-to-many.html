Module 2 · Lesson 13

Many-to-many, and why documents drift toward relations

A tree is easy to store in one record. A web of relationships is not, and the way data acquires relationships over time is the strongest argument in this whole module.

~45 min1 interactivebuilds on Lessons 2 and 124-question check
What you can do after this lesson Choose a representation for a many-to-many relationship, name the crash-point hazards of each, and recognize the signs that an embedded design is turning into a relational one.

1. One-to-many is a tree; many-to-many is a graph

A person’s positions are one-to-many: each position belongs to one person. But each position also points at a company, and a company has many people. That is many-to-many: people ↔ companies. The same shape appears as students and courses, articles and tags, users and groups, products and categories. In Lesson 12 the second relationship hid inside the first. This lesson pulls it out.

2. Three representations

  • One-sided array. Each article has tag_ids: [3, 7, 9]. Reading an article’s tags is one read. The reverse question, “which articles have tag 7?”, needs an index on the array or a full scan.
  • Two-sided arrays. The tag also keeps article_ids, so both directions are one read. The price is that every link is written in two places that must agree.
  • Junction table (or collection). One row per link, (article_id, tag_id), indexed in both directions. Each direction costs about the size of the answer; a link is one write.

What to notice

  1. Two-sided arrays buy cheap reads with a consistency problem. Attaching a tag is two document writes. Untick “multi-document atomic commits available” and the drill shows the state after the first write: the article lists the tag and the tag does not list the article. This is exactly Lesson 2, inside a single database.
  2. Deleting a tag is the stress test. In both array designs it means rewriting every article that mentions it (250 at the default), and without atomic multi-document commit, being interrupted leaves dangling ids. With a junction table it is one statement.
  3. The junction table makes every question cost about the size of its answer (see the reads columns) and removes the half-written states.
  4. Atomic multi-document commit changes the story but not the shape. With transactions (always the case for rows in MySQL), the torn states vanish, but the array designs still pay the fan-out writes. MongoDB documents multi-document atomicity via distributed transactions rather than as the default.[1]

3. In MySQL

The junction table with cascading foreign keys is the plain-relational answer. The array alternative uses the multi-valued index you met in Lesson 12.

CREATE TABLE article (id INT PRIMARY KEY, title VARCHAR(80) NOT NULL);
CREATE TABLE tag     (id INT PRIMARY KEY, name  VARCHAR(40) NOT NULL UNIQUE);
CREATE TABLE article_tag (
  article_id INT NOT NULL,
  tag_id     INT NOT NULL,
  PRIMARY KEY (article_id, tag_id),          -- tags of an article
  KEY idx_tag (tag_id, article_id),          -- articles with a tag
  FOREIGN KEY (article_id) REFERENCES article(id) ON DELETE CASCADE,
  FOREIGN KEY (tag_id)     REFERENCES tag(id)     ON DELETE CASCADE
);
INSERT INTO article VALUES (1,'Retries'),(2,'Queues'),(3,'Joins');
INSERT INTO tag     VALUES (1,'reliability'),(2,'performance');
INSERT INTO article_tag VALUES (1,1),(2,1),(2,2),(3,2);
-- articles with tag 2, and the tags of article 2: each uses an index, cost ~ size of the answer
SELECT a.title FROM article_tag at JOIN article a ON a.id = at.article_id WHERE at.tag_id = 2;
SELECT t.name  FROM article_tag at JOIN tag t     ON t.id = at.tag_id     WHERE at.article_id = 2;
-- delete a tag everywhere: one statement, one transaction, no half-deleted state
DELETE FROM tag WHERE id = 2;
SELECT COUNT(*) AS links_left_for_tag_2 FROM article_tag WHERE tag_id = 2;
-- the array alternative: one-sided ids with a multi-valued index for the reverse question
CREATE TABLE article_doc (
  id  INT PRIMARY KEY,
  doc JSON NOT NULL,
  KEY idx_tags ((CAST(doc->'$.tag_ids' AS UNSIGNED ARRAY)))
);
INSERT INTO article_doc VALUES (1,'{"title":"Retries","tag_ids":[1]}'),(2,'{"title":"Queues","tag_ids":[1,2]}');
SELECT id FROM article_doc WHERE 2 MEMBER OF (doc->'$.tag_ids');

DynamoDB

DynamoDB has no joins, and AWS’s guidance says to start from the access patterns: list the questions the application asks before choosing keys.[2][3] The AWS compute blog works the same many-to-many case, contrasting the three-table SQL design with a single-table design built from the access patterns and noting the trade-off of having no joins.[3] The pattern AWS documents for this is commonly called an adjacency list (I did not fetch that specific page; see the guidance for key layouts). In effect it is the junction table, stored as items keyed so that each direction can be queried.

4. Why documents drift toward relations

Here is how the drift usually goes, using the numbers you have measured:

  1. Embed everything. The profile page is one read.
  2. A new feature needs the reverse question. You add an index on the embedded array (401 reads instead of 20,003).
  3. A shared fact changes. You discover it is copied into hundreds of documents and either live with stale copies or write a fan-out job (400 writes).
  4. You move the shared entity into its own collection and store a reference. The rename is cheap again; the profile page now costs a second trip.
  5. Now the page needs the company’s industry for each position. The application does a join in code: fetch the document, collect the ids, batch-fetch the companies, stitch. You have reinvented the join, without a planner (Lesson 16).

This is not a flaw of document databases. It is what happens when data with relationships acquires new questions over time. Stonebraker and Pavlo make the stronger claim that the two families are converging, with relational systems taking JSON and document systems taking relational features.[4] The practical rule I would carry from it: when a relationship is genuinely many-to-many and the related thing has its own lifecycle, give the relationship a first-class home (a junction table, or its own collection with keys) before you need it, and embed only what is truly part of the parent.

5. Check yourself

Optional: find a hidden many-to-many (10 minutes)

Look at a document or JSON column you own and find an array of ids. Which question can you not answer without scanning? If a reverse lookup, an index; if a shared update, a reference or a junction; and if neither exists yet, note which feature would force it.
