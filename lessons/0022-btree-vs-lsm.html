Module 3 · Lesson 22

B-tree or LSM? A decision framework you can test

Neither structure is better. They put the cost in different places, and which one hurts depends on your keys, your memory, and what you read. This lesson ends in a test, not a verdict.

~55 min1 interactiveengine comparison4-question check
What you can do after this lesson Compare the two families on write, read and space cost using measured numbers, name the workload features that decide between them, list what this module did not measure, and follow a procedure that ends in a test of your own workload.

1. The measured anchors

These come from real engines (InnoDB 8.0.46 and RocksDB through its Python binding) in a small sandbox. They are not a head-to-head benchmark: the engines differ, and the write figures count different things (InnoDB’s include the redo log and doublewrite pages; RocksDB’s count sorted-file bytes and exclude its write-ahead log, which adds about 1×). 2. Same workload, three engines

The workbook inserts 100,000 records into the model B-tree and into the two LSM policies, then reads them back. “Memory” buys a buffer pool for the B-tree and a block cache for the LSM-trees. Move the slider and change the key order.

What to notice (the figures are what the workbook computes)

  1. Random keys, little memory: the B-tree writes far more. At 2% memory it writes about 139× the inserted bytes (pages only) against 5.6× for leveled and 2.9× for size-tiered. At 10% memory it is still about 102×.
  2. Memory rescues the B-tree, not the LSM. At 100% memory the B-tree writes each page once (1.66×, equal to its space overhead) and beats both LSM policies. The LSM write cost barely moves with memory in this model, because its memtable is fixed at 2% and cache only helps reads. (In real LSM engines a larger memtable also reduces write amplification by flattening the tree; I did not model that.)
  3. Keys in order flatten everything. At 10% memory with in-order keys: B-tree 1.24×, leveled 1.00×, and the textbook size-tiered policy 2.9× because it keeps merging disjoint runs (a property of that policy, not measured on real universal).
  4. Absent keys expose the real difference in reads. A B-tree must reach a leaf to learn a key is absent: 0.9 reads at 10% memory, the same as a present key. With bloom filters the LSM-trees need about 0.02 to 0.04. Untick the filters and they pay 1.6 (leveled) and 3.0 (tiered) at the same memory.
  5. Space tells the other half. Random-key B-tree pages cost 1.66× the data; the LSM-trees, with no overwrites, about 1.0×.

3. The RUM view

The RUM conjecture from Lesson 20 predicts exactly this picture: no structure wins all three overheads.[1] The B-tree spends memory (a buffer pool big enough for the leaves you touch) to make updates cheap, and has predictable reads. The LSM-tree spends read and space overhead (more runs, dead versions) to make updates cheap without needing the memory, and recovers read cost with filters and caches, which are memory again. The lab shows memory moving a B-tree along that trade-off.

4. What I did not measure

  • Latency. Everything here is bytes and counts. Compaction stalls, checkpoint stalls and tail latency (Lesson 7) were not measured, and they often decide real choices.
  • Range scans. A B-tree reads a range from adjacent leaves; an LSM-tree merges across runs. Not measured.
  • Concurrency, transactions, secondary indexes. InnoDB’s clustered index, MVCC and locking are far more than the page tree modeled here.
  • Devices. SSD behavior, write endurance (write amplification matters for flash wear), and the sequential-versus-random gap on your hardware.
  • Tuning. Compression, larger memtables, parallel compactions, partitioned filters. A tuned engine can differ widely from these defaults.

5. A decision procedure (my synthesis)

  1. Does the data you write to fit in memory? If the hot leaves fit in the buffer pool, B-tree writes are cheap and reads are the simplest to reason about.
  2. Are keys written in order? (time-series, auto-increment ids.) Both structures are cheap; the choice moves to other criteria.
  3. Random-key writes much larger than memory? This is where an LSM-tree’s write advantage is largest in these measurements.
  4. Are absent-key or point reads latency-critical? The B-tree has no surprises; an LSM-tree needs filters and a cache sized to the hot data.
  5. Disk tight, or flash endurance a concern? Compare space and write amplification in your measurements, not mine.
  6. Then test. Replay a sample of your real workload against both and measure bytes written, bytes stored, and disk reads per lookup and latency. The scripts in experiments/storage/ are templates.

Where your own stack sits: MySQL’s InnoDB is the B-tree in this module. A Kafka partition is stored as an append-only log, the family of Lesson 18 (see Kafka’s documentation for its segment and index layout; I did not verify those details here). MySQL can also be built with RocksDB as a storage engine (MyRocks), which I did not verify or test.

6. Check yourself

Optional: sketch the test (20 minutes)

For one write-heavy table you own, write down: key pattern (ordered or random), data size versus memory, the read mix (present, absent, range), and the three numbers to record on each engine (bytes written, bytes stored, disk reads per lookup) plus a latency percentile. That one page is more valuable than any ranking.
