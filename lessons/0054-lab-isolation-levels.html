Module 7 · Lesson 54

Lab: test isolation against real databases

Names such as repeatable read hide implementation differences. Run a controlled two-session schedule, record each response, and explain exactly what the observation establishes.

~40 min1 interactive4-question check
What you can do after this lessonReproduce the module’s isolation witnesses in disposable MySQL and PostgreSQL instances, inspect ordered transcripts, and separate observation, mechanism and untested guarantee.

1. Predict, execute, explain

This lab follows the useful Hermitage idea: small histories differentiate isolation behavior more clearly than a list of level names. The schedules here are original, deliberately limited examples. They are not the full Hermitage suite, a Jepsen test, or a proof about every SQL program.

You can work entirely from the recorded tables and interactive below. Reproduction is optional and does not gate the next lesson. The site and CI require only Node and Python’s standard library; Docker is needed solely to rerun the independent server observations.

2. Run owned, isolated databases

# From the repository root, with Docker running:
python3 experiments/transactions/isolation.py /tmp/dsc-transactions-run
# Read mysql-results.json and postgres-results.json in that directory.
# The matching *-transcript.json files contain the exact ordered SQL.

The script creates uniquely named MySQL 8.4 and PostgreSQL 18 containers with networking disabled and no published ports. It connects using the bundled command-line clients, preserves A and B as separate persistent sessions, records versions/settings and image IDs, and removes its containers and anonymous volumes in a finally block. It does not connect to an existing database or require your application credentials. Image tags can advance; the results record what actually ran.

The MySQL client needs force mode so an expected error does not terminate the session before the response marker. PostgreSQL’s client receives an explicit verbosity setting so SQLSTATEs are recorded. The harness checks readiness of the final TCP server rather than the image’s temporary initialization server.

3. Establish the baseline

Before opening the results, predict each row of this table. A read test needs an actual reader kept open across the other session’s commit. A lost-update test needs both original reads before either replacement commits. A range-lock test must issue the competing insert while the first transaction still holds its lock.

4. Compare conflict rules, not just read stability

The PostgreSQL schedules use repeatable read and serializable isolation on the same two-doctor decision. Repeatable read allows the disjoint-write skew. Serializable prevents both decisions from committing, with one serialization failure and one doctor remaining. The same-row stale-replacement test separately shows PostgreSQL repeatable read rejecting a conflicting update, unlike the MySQL schedule.

Exercise: select write_skew for MySQL, then the PostgreSQL repeatable-read and serializable cases. Point to the read responses, the transaction that failed, and the final count in the transcript. A model agreeing with its own prediction would be weak evidence; these outputs come from the actual engines.

5. Extend one witness without turning it into a timing test

Change one dimension at a time in a disposable copy: the isolation level, a plain read to FOR UPDATE, the index, or an absolute assignment to an expression. Keep the SQL and transaction boundary explicit. Require the other session’s commit or a directly observed lock wait before advancing. A sleep is not proof that the other transaction reached the intended point.

The deadlock schedule polls the lock-wait table before completing the cycle. Timeout tests intentionally stop at a lock-wait error; they do not claim that a waiter was allowed through. Victim selection and incidental transaction IDs can vary and are not correctness assertions. Record a changed outcome rather than adjusting the model until it agrees.

6. Bound the conclusion

One observed forbidden history is a counterexample to a claimed guarantee. Not finding it in a handful of histories is not proof of the guarantee. The fixture establishes these schedules for these versions/settings, while the engine documentation explains the intended general contract.

No crash, disk loss, network partition, replication failover, multi-shard commit, production load or latency distribution is tested. The guard example validates the ordered decisions; its success is not proof that all future application writers will acquire the guard. The browser’s retry examples recompute idealized decisions and do not run your application callback.

Write your lab result in three sentences: the exact observed history; the mechanism that explains it; the additional assumption needed before relying on it for a feature. That habit is the point of the lab.
