Module 5 · Lesson 40

CRDTs: design the merge before the outage

A good replicated data type defines how states combine before messages are delayed, duplicated or reordered.

~35 min2 interactives4-question check
What you can do after this lessonExplain state-based merge laws, operate a PN-counter and observed-remove set, and separate convergence from application admission invariants.

1. The merge laws do work

For a state-based CRDT, design a merge that is commutative (order does not matter), associative (grouping does not matter) and idempotent (repeated state has no extra effect). Local updates must advance state in the appropriate partial order. With the required state eventually disseminated, those properties support convergence.[1]

This is a delivery contract plus a data type, not permission to lose updates forever. Operation-based CRDTs have different delivery requirements: a plain “increment by one” message repeated twice increments twice unless its protocol prevents duplicate application. State-based idempotence does not transfer to every operation stream.

2. A single total loses information

If A and B each increment their local total from 0 to 1, max(1,1) loses one increment. Adding their totals gets 2 initially, then double-counts when the same states are delivered again. Keep per-actor accumulated contributions instead.

A state: {A:1}     B state: {B:1}
merge:   {A:1,B:1}     value = 2
merge that same B state again: value remains 2

Each actor owns its monotone component. Merge takes the maximum for each actor; the displayed total is the sum. To support decrements, keep separate monotone positive and negative components: value = sum(P) − sum(N). A decrement increases a negative component; it does not move a stored component backward.

Try: increment A and B independently, merge both ways, then repeat a merge. Decrement on one side and exchange state again. These are actual state operations; the tests check merge laws and delivery orders on bounded cases, not a production network.

3. Set removal needs an observed target

A simple union of ordinary sets preserves additions, but cannot represent a removal once an old state containing the item returns. Our observed-remove example gives each addition a unique tag, and records the specific tags a removal saw.

A removes the shared old book tag S:1. Concurrently, B adds a new book tag B:1 that A did not observe. Merging retains B:1, so book remains present: the example declares add-wins semantics for this concurrent add/remove. If both only remove the old tag, book disappears.

The tag identifies an addition, not merely the element name. The toy retains all removed tags forever; optimized causal set designs can use other metadata, but cannot arbitrarily forget the evidence. A unique tag must not later be reused for a different addition.

4. Convergent is not automatically acceptable

The PN-counter happily merges two decrements against one starting stock unit into −1. It preserved the updates correctly; the application admitted two sales against insufficient rights. CRDT convergence alone does not enforce stock ≥ 0, global uniqueness, or an arbitrary cross-record constraint.

Choose a type whose concurrent semantics match the feature. Add-wins may be right for one collaborative collection and wrong for a security revocation rule. A deterministic result is valuable only when it is the result the application intended to permit.

5. State the assumptions around the algebra

  • Stable actor identities and monotone durable components; no counter reset masquerading as the same actor.
  • Unique addition tags and a justified metadata reclamation protocol.
  • Eventual dissemination of the necessary state, with recovery preserving the type’s assumptions.
  • Numeric representation without overflow in the range being claimed.
  • A domain invariant compatible with independently accepted operations.

The browser has two actors, small exact integer counts, no persistent storage, no optimized garbage collection and no operation-based transport. It demonstrates the data structures and their limits rather than certifying a distributed service.
