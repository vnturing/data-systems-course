Module 3 · Lesson 27

Materialized views and data cubes

The cheapest repeated aggregation can be the one already computed. Its cost moves to keeping the answer correct.

~35 min1 maintenance labreal roll-up resultsmodule capstone
What you can do after this lessonMaintain a grouped sum through inserts, updates, deletes and duplicate delivery; explain the freshness contract; and decide which aggregate state can answer a coarser question.

1. Store the answer, then own its maintenance

A normal view defines a query. A materialized view stores its result. PostgreSQL’s documentation illustrates the distinction and explicit refresh: reads can be quicker while the stored result can be stale.[1] In this lesson, a “materialized view” includes a summary table maintained by your application; it does not imply that MySQL has PostgreSQL’s CREATE MATERIALIZED VIEW command.

For a repeated revenue-by-region report, store (region, sum_amount, count_orders). Instead of rescanning every order on every request, read a few group rows. A full refresh recomputes from the base data. Incremental maintenance applies the change to the answer. Gupta and Mumick’s survey develops the maintenance problem and its trade-offs.[2]

2. An update is a retraction plus an insertion

insert EU/100:                  EU.sum += 100; EU.count += 1
update EU/300 to US/500:        EU.sum -= 300; EU.count -= 1
                               US.sum += 500; US.count += 1
delete EU/100:                  EU.sum -= 100; EU.count -= 1

An update can change both the measure and its grouping key. An after-image alone saying US/500 does not tell you to retract EU/300. You need the before-image or maintained per-order state from which to recover it. Deletes need the old contribution too.

Try: predict the replayed update’s error, then enable deduplication. Uncheck atomic commit. Finally select lag. A stale but internally correct view and a corrupted view require different repairs.

After all five distinct events, only two US orders remain: 500 and 900, for sum 1,400 and count 2. Replaying the move without protection subtracts EU/300 and adds US/500 again. A negative EU count is a symptom of corruption, not useful business data.

3. The crash-point drill returns

Deduplication needs a stable event identity. It also needs the marker and view delta to commit together. If the consumer changes the summary, crashes before recording the event ID, then retries, the delta is applied twice. This is Lesson 2’s drill at a different boundary.

BEGIN
  insert unique event ID into processed_events
  if newly inserted: retract old contribution; add new contribution
COMMIT
acknowledge delivery only after commit

This is a transaction sketch, not runnable SQL. Handle the duplicate insert so the transaction skips the delta; use transactional tables, atomic arithmetic and suitable locking for concurrent group updates. If the marker and view live in different systems, the local transaction shown does not span them. Atomic source mutation plus summary maintenance in one database is another option, with extra work on the source write path.

The widget injects a crash after the first e4 delta and before its marker in the broken variant. Its events are ordered. It does not solve concurrent consumers, missing events or out-of-order updates. Those require a protocol with enough identity, version and prior-state information to decide which change belongs next.

4. A cube is a family of grouping questions

Group daily sales by region. You may also want daily totals across all regions, regional totals across all days, and the grand total. The data cube operator generalizes these related aggregations.[3] For two dimensions:

Grouping setQuestion
(day, region)Each day and region
(day)Each day, all regions
(region)Each region, all days
()Grand total

CUBE(day, region) includes all four. ROLLUP(day, region) includes the first, second and fourth: it follows one hierarchy, so it omits region-only totals. For d dimensions there are 2d grouping sets in the full cube, not merely d output rows. Actual cells depend on cardinality; full precomputation can grow quickly.

-- Executed on DuckDB 1.4.2 by experiments/storage/analytics.py:
SELECT day, region, SUM(amount), COUNT(*)
FROM facts GROUP BY ROLLUP(day, region);

-- MySQL 8.4 spelling for the same hierarchy:
SELECT day, region, SUM(amount), COUNT(*)
FROM facts GROUP BY day, region WITH ROLLUP;

For facts (day 1, EU, 100), (day 1, EU, 300), (day 2, US, 900), the recorded DuckDB roll-up has five rows, including grand sum 1,300 and count 3. Its CUBE has seven rows. These operators compute grouping results; they do not themselves make a permanently maintained materialized cube. Subtotal NULLs need distinguishing from real NULL dimension values using grouping metadata.

5. Keep sufficient state

Sums and counts roll up by addition. An average needs both: EU has mean 200 over two orders; US has mean 900 over one. Averaging the means gives 550; the correct overall mean is 1,300/3, about 433.33.

MIN is cheap to extend on insertion, but deleting the minimum needs the next candidate, which the minimum alone does not retain. Exact distinct counts do not add across overlapping groups. A daily distinct-user count cannot generally answer monthly distinct users. Keep enough underlying state, recompute, or choose an approximation with an explicit error contract.

Module 3’s closing design questionA secondary index is a maintained alternate access path. A column projection is a maintained layout for selected values. A materialized view is a maintained answer. For each, ask: which reads become cheaper, what do writes maintain, how does recovery rebuild it, and which source defines truth?

6. Check yourself

Optional: review a stored answer (20 minutes)

Pick a counter, dashboard or summary table. Name the base grain, maintenance mode, dedupe identity, crash boundary, freshness contract and rebuild procedure. Try an update that changes the grouping key and a deletion of an extreme value. Explain what state each repair needs.
