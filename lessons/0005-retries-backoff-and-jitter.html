Module 0 · Lesson 5

Retries done right: timeouts, backoff, jitter, budgets

Lesson 1 said a retry is only safe if repeating the work is harmless. This lesson is about the other half: even a harmless retry can take down the service it is trying to reach.

~45 min2 interactives4-question checkBuilds on Lessons 1 to 4
What you can do after this lesson Choose a timeout from a latency percentile instead of a guess, configure backoff with jitter and a cap on retries, explain why layered retries multiply, and decide which of your operations may be retried at all.

1. Retries are selfish

The Amazon Builders’ Library article on this topic opens from a simple premise: whenever one service calls another, failures happen, so systems need three tools: timeouts, retries and backoff.[1] It then makes the observation that organizes this whole lesson: retries are “selfish.” When a client retries it spends more of the server’s time to raise its own chance of success.[1] That is fine when the server is healthy and failures are rare. When the server is struggling, every client doing the same thing makes the struggle worse, and unlike most load there is almost no way to coordinate clients to retry the right amount.[1]

2. Start with the timeout

Every retry begins with a timeout (Lesson 1: a timeout is a guess). The Library’s recommended practice is to set a timeout on all remote calls, covering both connecting and waiting for the response.[1] The hard part is the value. Too high, and the timeout stops helping, because resources stay tied up while the client waits. Too low, and you create extra backend traffic and latency from retries, and a small latency bump can turn into a full outage because every request starts retrying.[1]

Their method is to choose an acceptable false-timeout rate (for example 0.1%) and set the timeout to the matching percentile of the downstream service’s latency (p99.9 in that example).[1] Worked example: if the dependency’s p99.9 latency is 800 ms, a timeout near 800 ms means about one in a thousand calls will be abandoned while actually still succeeding. That is the useful way to read “false timeout”: it is the Lesson 1 world where the server did the work and you did not wait. The rate you accept is the rate at which your retry logic runs on calls that already worked, which is exactly why Lessons 1 and 2 had to come first.

3. Backoff and jitter

Capped exponential backoff multiplies the wait after each attempt by a constant, up to a maximum.[2] It slows clients down, but it has a subtle flaw: clients that failed at the same moment also retry at the same moments. Jitter adds randomness to the wait so they spread out. In the “full jitter” variant the sleep is a random value between zero and the capped exponential delay (Brooker’s preferred form, as one summary writes it: random(0, base * 2^attempt), capped).[2][3]

Isolate the effect. The lab below throws 1,000 clients that all failed at the same instant at a server that can handle 100 attempts per tick.

What to notice

  1. With free failures (slider at 0%), immediate retry finishes first but makes about 5.5 calls per client. Speed bought by burning server work.
  2. Unjittered backoff makes the same number of calls and finishes last. The clients stay synchronized: peaks of 1,000 at every retry instant, with idle gaps in between.
  3. Full jitter cuts calls per client by almost half and finishes several times sooner than unjittered backoff. This reproduces, in spirit, AWS’s own experiment, where the unjittered approach was the clear loser on both work and time and jittered approaches substantially reduced client work and server load.[2] (Their experiment was optimistic concurrency control with many contending clients, a different workload from this toy; the qualitative result is what carries over.)
  4. Now raise the slider. At 10% or more, a rejected attempt costs the server enough that a 1,000-strong synchronized wave leaves it with nothing to spare for useful work. Immediate and unjittered retries never finish; jitter still does. The threshold depends on herd size relative to capacity: the bigger the herd, the lower the cost needed to cause this.

The Library adds a point that is easy to miss: jitter is not only for retries. Periodic work such as timers and cron jobs benefits too, because it removes synchronized spikes.[1] The AWS Architecture Blog’s summary of the experiment is blunt: the return on the small complexity of jittered backoff is huge, and it should be standard for remote clients.[2]

4. Amplification, layers and budgets

Backoff and jitter shape when retries arrive. They do not limit how many. The second lab models a longer story: a service handling 100 requests per tick with capacity 150 goes fully down for a few ticks, then returns, with a steady stream of new requests the whole time.

What to notice (and what not to conclude)

  1. Immediate retries with a generous retry limit never recover. Set max retries to 10 with the default outage and watch the stuck backlog. A modest number of requests that the server cannot serve right away becomes a standing overload.
  2. Jitter helps against immediate retry, but not enough on its own. Lengthen the outage and raise max retries until the jittered row fails to recover too.
  3. A retry budget bounds amplification regardless of settings. The last row caps retries with a token bucket: each retry spends a token and successes refill tokens slowly, so when the service is struggling, retries stop. Amplification stays near 1.0× and recovery is immediate, at the price of giving up on some requests.
  4. Do not conclude anything about backoff versus jitter from this lab. This toy deliberately leaves unjittered backoff out of the table because the ordering of those two flips with parameters here. The herd lab and the AWS experiment are the right evidence for jitter. The lab’s own assumption, a rejected attempt costing 20% of a real request, is made up to show the mechanism, not measured from anything.

Token-bucket retry limiting is how, according to a secondary summary of the Library article, Amazon prefers to bound retries (over circuit breakers, which the summary says the author finds modal and hard to test), and that summary says AWS’s SDKs have shipped a version of it since 2016.[4] Treat that as a pointer to the primary article, not a settled fact.

Layers multiply

The Library lists layered systems among the other problems with retries.[1] The arithmetic is simple and unforgiving (this calculation is mine): if a user-facing service, an API tier and a data service each make 3 attempts against the layer below, one failing user request can reach the bottom as up to 3 × 3 × 3 = 27 calls. One secondary summary of the Library article gives the guidance as: retry at one layer only and let the others fail fast.[4] In an AWS-based service, count the retry loops that stack up before a request reaches a database: SDK, your own wrapper, the gateway, the client app. Defaults vary by SDK and version, so read the effective configuration rather than trusting memory.

5. Which calls may be retried at all

All of the above assumes the retried operation is safe to repeat. The Library names the issue directly: some remote calls have side effects.[1] Lesson 1’s answer is idempotency, and the services you use have their own versions, each with a window that your retry policy must fit inside:

MechanismWhat it dedupesWindow to respect
Stripe Idempotency-KeyRepeated API requestsKeys can be pruned after at least 24 hours (Lesson 1)
SQS FIFO MessageDeduplicationIdRepeated sends to a queueA 5-minute deduplication interval. A resend with the same id after the interval can create another message.[5][6] SQS tracks the id even after the message was received and deleted.[6]
Kafka idempotent producerDuplicates from the producer’s own retriesDoes not cover your database write (Lesson 2)
SQS standard queueNothing: at-least-once delivery, best-effort orderingConsumers must be idempotent[7]

The rule that falls out: the longest period over which anything can still retry must be shorter than the shortest dedupe window it relies on. A retry that lands after the window is, as far as the service is concerned, a brand-new request.

As for SDK behavior: most AWS SDKs support exponential backoff and jitter as part of their standard and adaptive retry modes.[2] Before layering your own loop on top of that, find out what the SDK already does.

6. Check yourself

Optional: inventory your retry layers (15 minutes)

For one request path in a system you run, list every place a failed call can be retried (client app, gateway, service SDK, your own wrapper, queue redelivery) and multiply the attempt counts. Then list which of those paths include a non-idempotent write. The product and that list together are your retry risk.
