Dirty reads, dirty writes and read committed

Read committed removes uncommitted values from ordinary reads. It still permits two statements in one transaction to see different committed worlds.

~35 min1 interactive4-question check
What you can do after this lessonDraw dirty-read and dirty-write schedules, explain statement-level committed views, and identify a read-skew failure that survives a transaction wrapper.

1. A value that never existed in a committed database

Let x=100. A starts a transaction and writes x=900 without committing. B reads 900. A rolls back. B has now based a decision on a value that was never committed: a dirty read. Even if B only generates a report, an uncommitted intermediate state can become an externally visible claim.

Our InnoDB experiment reproduced this with B at READ UNCOMMITTED: B read 900 during A’s transaction and 100 after rollback. At READ COMMITTED, the same nonlocking read returned the older committed 100 while A’s write remained open. The reader did not need to wait for A just to retrieve that older version.

2. Dirty writes are a different prohibition

A dirty write would let B overwrite x while A’s change is still uncommitted. If A later aborts, which value should its undo restore without destroying B’s work? Write locks keep this particular interference out of InnoDB’s update path, even when a reader requests READ UNCOMMITTED. A read setting is not permission to overwrite somebody else’s open write.

In the lab, A held the updated counter row and B’s conflicting UPDATE waited until error 1205, under an intentionally short lock-wait timeout. The timeout demonstrates that the write was not allowed through. It does not measure the normal wait duration or establish a deadlock: a single wait need not contain a cycle.

Predict first: choose read committed, then repeatable read. Both avoid the first dirty value. Only the repeated committed read policy changes the last observation after C commits 110. The widget combines these events for teaching; the server lab tests the mechanisms in separate schedules.

3. Read committed is a statement boundary

Under MySQL’s read committed level, each ordinary consistent SELECT obtains a fresh committed view. Keeping BEGIN open does not freeze that view across statements. If A commits between B’s two reads of x, B can read 100 and then 110. This is a nonrepeatable read. Our server fixture records exactly those two values.

-- Session B
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT v FROM counter WHERE id=1; -- 100
-- Session A now updates v to 110 and commits.
SELECT v FROM counter WHERE id=1; -- 110
ROLLBACK;

The comments are scheduling instructions: pause B until A has committed. Running both statements in a single batch without controlling A’s progress is not the same experiment.

4. A committed value can still mislead a report

Accounts A and B start at 100 each. A report reads A=100. A concurrent transfer commits A=70 and B=130 together. The report next reads B=130. Every individual value was committed, but its sum is 230. No committed complete state of those two accounts had that total. This is read skew across the report’s statements.

A single consistent query for the sum can keep this particular report on one statement view. A multi-query export can need one stable transaction snapshot. Neither repair establishes that a later business decision may safely act on the report; that is a separate requirement.

5. Writers evaluate more than the plain-read view

Do not infer UPDATE semantics from what an earlier SELECT returned. InnoDB’s updating and locking paths acquire locks and can examine newer records. A plain read followed by UPDATE x=110 is not an atomic “add ten,” even if each writer waits its turn. Lesson 50 makes the lost computation visible.

Nor should you use SKIP LOCKED to make a report “faster.” Skipping a locked row changes the set you inspect. That can be appropriate for queue workers claiming available jobs; it is unsuitable when the report or invariant requires all matching rows.

6. Connection and error discipline

The level belongs to a transaction/session, not to the indentation of your application code. Verify that a connection pool pins all statements to the same transaction connection. Set the intended level before starting the transaction, and avoid leaking session settings into another borrower.

On an InnoDB lock-wait timeout, the default rollback scope is the waiting statement, while a detected deadlock rolls back the victim transaction. A handler that treats all SQL errors as “everything was undone” can accidentally commit earlier work. A conservative application policy is to explicitly roll back the whole feature transaction on a concurrency error, then retry the complete operation only where appropriate.
