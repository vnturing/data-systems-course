Module 5 · Lesson 41

Lab: break a quorum on purpose

Keep the headline counts fixed at N=3, W=2, R=2. Change one hidden assumption and see which guarantee actually survives.

~40 min1 interactive4-question check
What you can do after this lessonConstruct concrete quorum counterexamples, distinguish a stale read from an unavailable read, and repair the failed premise instead of treating the formula as a proof.

1. Write the claim before running the trace

The home set is {A,B,C}. Initial value is v0. A new value v1 is ordered after v0 for this one key; there are no concurrent writers in the lab. Acknowledgement requires two holders, and a read collects two responses. We deliberately make version choice easy so that membership and partial effects remain visible.

First choose the completed home write {A,B}. Predict the result from read responders {B,C}. Write down the actual overlapping member, not just R+W=4. Then compare that baseline with the two failure traces.

2. Counterexample: acknowledged sloppy write

Choose the sloppy case. A and fallback D hold v1; the write succeeds under this scenario’s two-holder policy. B and C still hold v0. Reading {B,C} returns v0. The counts are unchanged, but {A,D} ∩ {B,C} is empty.

Enable read repair first. Both responders agree on v0, so repair has no evidence of D’s unseen v1. It cannot invent the missing version. Next recover B and deliver D’s saved hint before the read. B now provides v1. Optional read repair can carry that evidence onward to C.

The Dynamo paper describes sloppy membership and hinted handoff as availability mechanisms.[1] Our exact holder sets are a course counterexample, not a claim that every Dynamo read follows this injected route. A hint also needs a surviving holder, valid destination and eventual delivery; its existence is not instantaneous convergence.

3. Counterexample: a failed write becomes visible

Choose the partial-write case with repair off. Only A stores v1, so the write does not reach W=2 and receives no success acknowledgement. A first read from {A,B} observes v1. A later read from {B,C} returns v0. Both reads have two responders.

The completed-write intersection argument does not cover a value stored on only one node. “Write failed” did not erase its effect. A retry also needs an identity and suitable semantics; otherwise a caller may repeat an already partly executed operation.

Enable blocking read repair. The first read updates B to v1 before returning; the second read now intersects that repaired set. This illustrates the specific monotonic-quorum-read scenario explained by Cassandra’s documentation.[2] It is not a general proof of every Cassandra consistency property or a substitute for its configured protocol.

4. Prefer an honest unavailable answer to an invented guarantee

One response to unavailable home replicas is to refuse a write that cannot reach the required fixed set. That gives up some availability but preserves the premise used by the intersection argument. Another design accepts substitutes and promises weaker immediate reads with durable deferred handoff. Neither should be advertised using the other’s proof.

Similarly, a read barrier in Lesson 36 can wait or fail when no eligible replica exists. Returning an arbitrary stale result is a different contract. State which one the product chooses and what the user sees.

5. The module’s review procedure

  1. Authority: who may accept writes, and how are former writers fenced?
  2. Acknowledgement: which durable holders or apply stages precede success, including timeout fallback?
  3. History: how are bootstrap, received/applied positions and failover candidates checked?
  4. Reads: which freshness, session or dependency guarantee is needed?
  5. Concurrency: which versions can coexist, and which merge preserves the domain contract?
  6. Repair: how do unseen, partial, deleted and long-cold records eventually reconcile?

Use the real MySQL fixtures to anchor receipt/apply, stale promotion and dual-writer claims. Use exhaustive set enumeration and merge-law tests for the bounded mathematical models. Neither substitutes for fault tests against the production product and configuration.

Finish with the replication checklist. Module 6 adds partitioning: the membership universe and hot-key distribution that this module mostly held fixed.

Check yourself

Optional: apply the mechanism (20 minutes)

Take one replication claim from a design review. Write a minimal failing trace that changes one premise: stale promotion, missing dependency, sloppy membership, partial write or concurrent update. State the repair and its availability cost.

Ask the course agent about any unclear result. Include the topology, acknowledgement contract and exact failure or message sequence.
