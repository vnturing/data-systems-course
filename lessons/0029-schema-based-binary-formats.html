Module 4 · Lesson 29

Field tags or writer schemas?

Protobuf and Avro both move names out of the record bytes. They make different promises about what a reader needs in order to understand what remains.

~35 min1 byte inspectorreal library cross-checks4-question check
What you can do after this lessonWalk through a small Protobuf and Avro record, explain how unfamiliar fields are handled, and name the schema information the receiving system must retain.

1. Start with one logical record

{"id":150,"name":"Zoë"}

// Protobuf (proto3, explicit presence)
message Account {
  optional uint32 id = 1;
  optional string name = 2;
}

// Avro
{"type":"record","name":"Account","fields":[
  {"name":"id","type":"long"},
  {"name":"name","type":"string"}
]}

We choose a nonnegative ID that fits both types. Protobuf uint32 and Avro long are not equivalent integer domains. Their common sample makes their encodings comparable without implying identical type systems.

2. Protobuf carries a field number and a wire type

08 96 01 12 04 5a 6f c3 ab
|  |     |  |  |-----------|
|  150   |  4  UTF-8 Zoë
tag 1    tag 2, length-delimited

The key is (field number << 3) | wire type. 08 identifies field 1 using varint representation. The payload 96 01 stores 150 in seven-bit groups with continuation bits. 12 identifies field 2 using length-delimited representation; 04 is its byte count.[1]

The wire type is a coarse structural hint. Length-delimited bytes could be a string, nested message or other data. Field numbers and a schema give those bytes their meaning. Tags do not make Protobuf fully self-describing.

An old reader can skip the structure of an unfamiliar field. Modern proto3 binary messages also retain unknown fields for reserialization, but field-by-field reconstruction or JSON conversion can lose them.[2] We will test that full round trip in Lesson 31.

3. Avro uses the writer schema to locate values

ac 02 08 5a 6f c3 ab
|----| |  |-----------|
 150   4   UTF-8 Zoë
zigzag integer encoding also applies to the string's byte length

The record bytes contain neither field names nor per-field tags. The writer schema establishes field order and types. Avro encodes signed integers with zigzag plus variable-length encoding: nonnegative 150 maps to unsigned 300, or ac 02. A four-byte string length maps to 8, or 08.[3]

The reader can then resolve the writer schema against its own schema: matching named fields, ignoring unwanted writer fields, and supplying reader defaults where permitted. The two schemas serve different roles. You cannot generally decode old bytes by substituting today’s schema for the actual writer schema.

Try: move the ID from 127 to 128, change the name to an emoji, then add currency. Watch what the old readers expose. The default bare sizes are JSON 24, Protobuf 9 and Avro 7 bytes. These exact bytes match independently executed Python libraries, including explicit zero/empty values and non-ASCII text.

4. Evolution rules follow the identity mechanism

For Protobuf binary, a field’s number identifies it across versions. Renaming the source field while retaining its tag can preserve the binary mapping, but JSON names are another boundary. Reusing a deleted number for a new meaning can make old bytes look valid under the new interpretation. Reserve deleted numbers and names instead of recycling them.[2] Our real-library probe reuses name’s tag for email and reads Zoë as an email value without a wire error.

Avro instead resolves field names using the two schemas, with alias rules available in the format. Reordering fields is not permission to read bytes in the new order: the actual writer schema still describes the old order. A reader-only field needs a suitable default to read records written without it. That default is not a value retroactively stored in old records.

5. Count the system, not only the payload

Avro object container files can carry their writer schema; messaging systems can identify schemas through a registry or another agreed envelope. Protobuf consumers normally obtain their schema through generated code or descriptors. Schema lookup, distribution and retention are part of the design even when they cost zero bytes in this tiny inspector.

The size comparison excludes those mechanisms, framing, compression and CPU work. It is not a benchmark or a recommendation to change formats. A reader that lacks the schema can fail on a seven-byte payload just as thoroughly as on a seven-megabyte one.

Our codecs cover flat Avro records with int/long/string and singular Protobuf uint32/string using wire types 0 and 2. They omit unions, nested messages, aliases, enums, most wire types and full-range int64 values. They exist to expose these mechanisms; use real libraries for applications.

6. Check yourself

Optional: inspect a small message (20 minutes)

Use a scratch schema and the reproduction script. Identify tags or writer field order, inspect non-ASCII length prefixes, and show how the receiver obtains the schema. Include envelope bytes when comparing total sizes.

Ask the course agent to walk through any unfamiliar byte. State the encoding and both schemas.
