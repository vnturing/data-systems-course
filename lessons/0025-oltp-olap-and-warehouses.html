Module 3 · Lesson 25

OLTP, OLAP, and why warehouses are separate

“Read-heavy” is not a workload description. Fetching one order and summing a year of orders both read data; almost everything else about them differs.

~30 min1 contention labworkload design4-question check
What you can do after this lessonDescribe a transactional and analytical workload using rows, columns, deadlines and freshness; choose what to isolate; and define the grain of a warehouse fact table without accidentally double-counting revenue.

1. Describe the work before choosing the engine

PropertyCheckout or order lookupRevenue report
Rows touchedA few identified rowsMillions selected by a broad interval
Columns neededOften much of each orderDate, amount, region; little else
WritesSmall concurrent changes, business invariantsOften ingestion plus large reads
DeadlineCustomer-facing tail-latency objectiveCompletion time and aggregate throughput
FreshnessMust see the state needed to confirm this actionPossibly tolerates a stated delay

Online transaction processing (OLTP) and online analytical processing (OLAP) name these workload families. Both can use SQL and relational models. “One Size Fits All” argues that different workloads justify different engine designs; it is an architectural argument, not proof that every application needs two databases.[1]

From Lesson 23, a covering index can make a particular report cheaper. It still reads every relevant entry. Ten million amount values remain ten million amount values unless another structure has already aggregated them.

2. A low average load can still hurt checkout

The model below has 200 one-millisecond checkouts each second. Add one 200-millisecond report: total requested work is only about 40% of one resource. Yet checkouts arriving behind the report wait. Predict whether average utilization alone protects the checkout deadline.

Try: compare 0, 200 and 1,000 ms of report work, then give reports a separate resource. This is Lesson 9’s queueing applied to a workload mix. The FIFO model runs exactly ten seconds, including its startup and final backlog; its percentiles are for that finite trace, not steady-state database predictions.

The model has no locks, buffer pool, parallel execution or disks. Real reports can also consume memory bandwidth, displace hot pages, use connections, and compete for I/O. Those are hypotheses to measure. Moving a report to another process on the same saturated device may not isolate the resource that matters.

3. A warehouse buys a different read layout

MySQL authority → snapshot + ordered changes → analytical store → report
      |                       |                       |
   checkout             ingestion position      report as-of point

This is a design sketch, not a configured CDC recipe. The analytical copy can have another physical layout, different retention, and resources sized for scans. C-Store is a primary example of a read-optimized architecture: it combines compressed column-oriented projections with a write-oriented component, because arriving changes and large reads want different layouts.[2] The next lesson measures the column side.

The copy also creates obligations. An initial snapshot and its change stream must join at a consistent boundary without gaps or unintended duplicates. Lag needs a measurable position or as-of point. Reprocessing and schema changes need a plan. A report that completed at 12:00 can still describe data only through 11:40.

Specify freshness as part of correctnessFor a daily trend, data through the previous hour may be acceptable. An inventory reservation must consult the authority enforcing inventory, or another mechanism with an explicit correctness guarantee. A recent-looking warehouse timestamp does not prove that every relevant transaction has arrived.

A read replica can be an intermediate option when its layout and queries are adequate. It still needs capacity and a lag contract. This lesson does not configure MySQL replication or assume a particular consistency guarantee; those belong to Module 5.

4. The first warehouse decision is the grain

Say exactly what one fact row represents. For a sales model, choose one order line at purchase time. Its measures might be quantity and line revenue in integer minor units; its dimension keys might identify purchase date, product and customer region. A star schema places the fact table at the center and descriptive dimension tables around it. Here is our example, not a universal schema:

sales_line(order_id, line_no, purchased_day, product_key, region_key,
           quantity, line_revenue_minor)
product(product_key, category, ...)
region(region_key, name, ...)

Two concrete traps follow from ignoring that sentence:

  • Grain mismatch: copying a 1,000-unit order total into each of three order-line rows makes SUM report 3,000. Store a line measure or keep order totals at their own grain.
  • History mismatch: joining old sales to today’s product price recomputes history at today’s price. Capture the purchase amount. If region changes, decide whether the report means region at purchase or current region; those are different questions.

Also name the currency and refund convention before adding money. SUM across USD and EUR is arithmetic without a coherent business meaning. These modeling choices survive any engine migration.

5. A decision you can defend

  1. Measure rows examined, columns read and tail latency for both workloads.
  2. Try a suitable index and schedule or limit broad queries if those satisfy the requirements.
  3. If resource competition or layout remains the bottleneck, isolate the identified resource.
  4. If a second store is justified, define ingestion, freshness, reconciliation and the authority for decisions.

Isolation trades contention for operating another dataflow. The choice is supported when both sides of that trade have a measured requirement.

6. Check yourself

Optional: write a two-workload brief (20 minutes)

Pick a customer request and one report. State rows, columns, write pattern, deadline and freshness for each. Name their shared bottleneck, one proposed isolation boundary, and the ongoing cost of the copy. Define the fact grain in one sentence.

Ask the course agent to challenge your workload description or grain; both are easier to fix before building the pipeline.
