Module 2 · Lesson 12

Relational or document? Locality, joins, and what you give up

The question is not SQL versus NoSQL. It is what you want the unit of reading, writing and consistency to be.

~50 min1 interactivereal MySQL measurements4-question check
What you can do after this lesson For a given entity, decide what to embed and what to reference using measured costs: reading it whole, updating a fact that many records share, and looking records up from the other direction.

1. Where the models come from

Early databases forced programs to know how data was physically organized. Codd’s 1970 paper argued for a relational model largely to give data independence: programs and terminal activity should not break when the storage representation changes. He singled out three dependencies to remove: ordering dependence, indexing dependence, and access-path dependence.[1] The alternatives he was reacting to were the hierarchical (IMS-style) and network (CODASYL) models, which Stonebraker and Hellerstein’s history walks through. In a strict hierarchy, for instance, data that does not fit under a single parent (their classic example is a supplier who currently supplies no parts) is awkward to represent at all.[2]

Fast forward: document databases revived tree-shaped, self-contained records. In 2024 Stonebraker and Pavlo revisited the history and argued that document databases and relational systems are on a collision course: relational systems have absorbed JSON, and document systems keep adding relational features.[3] Read that as an argument from long-standing relational advocates, not as a neutral verdict. For your purposes what matters is the practical consequence: you can mix both models inside MySQL, so the design question is local to each entity.

2. One entity, two layouts

A professional-profile page has a person, several positions, several educations, and each position refers to a company. As a tree it is a natural single document:

{ "name": "Ada",
  "positions":  [ {"company_id": 7, "company_name": "Acme", "title": "engineer"}, ... ],
  "educations": [ {"school": "Analytical College"}, ... ] }

In the normalized layout the same data is four tables. I loaded identical data into both on a real MySQL 8.0.46: 20,000 people, 4 positions and 2 educations each, 200 companies (so 400 positions per company). The scripts are in experiments/mysql/. Measured by storage-engine row reads:

What to notice

  1. Locality is real. The profile page is one read from a document and a stack of reads from tables. If that page is your hottest path, the document layout deserves serious weight. (A third option, documents that reference companies by id, keeps the rename cheap but needs a second trip to fetch the names.)
  2. Locality costs duplication. The cheap read is bought by copying the company name into every position. Every shared fact copied into many documents turns an update into a fan-out: 1 row became 400 documents. Drag “people per company” up and watch it grow.
  3. Reading part of a document reads all of it. Fetching just a name from a document still loads the whole 390-byte unit; the normalized row is about 45 bytes. At this size it is noise, but documents that accumulate arrays (comments, events) get large. Document stores impose size limits; check yours.
  4. Look-ups from the other side need an index you must remember. “Everyone at company X” is the question the document was not organized around. Without the multi-valued index it examined all 20,000 documents. Untick the index box.
  5. Tearing is a property of the engine. The “torn states” row appears only when you untick atomic multi-document commit. See below.

3. Atomicity is about the engine, not the model

MongoDB’s own data-modeling guidance puts the benefit of embedding directly: a single write operation on one document is atomic, so keeping related data in one document gives atomicity for free, while duplicating data across documents costs consistency work; for atomic updates across several documents you use distributed transactions instead.[4] In MySQL a JSON column is simply a column, and updating 400 rows inside one transaction is ordinary. So the same rename that is a hazard on a single-document-atomicity store is safe on MySQL. When you do lack atomic multi-document commit, you are back in Lesson 2’s crash-point drill: after the first of 400 writes the world contains two company names.

4. A decision rule you can defend (my synthesis)

Lean toward embedding when…Lean toward separate tables or references when…
The parts are almost always read with the parent, and have no life of their ownThe parts are read, searched or updated independently
The parts are bounded in number and sizeA part can grow without bound (events, comments)
The copied facts rarely change, or each copy is meant to be a snapshotA fact is shared and must change everywhere at once (a company’s name)
One document is the natural unit of consistencySeveral parents must stay consistent with one shared thing

The company name is a good example of the difference between a shared fact and a snapshot. If the profile should show the name as it was when the person worked there, copying is correct, and the “rename” operation does not even exist. The cost model only matters for facts that must change everywhere.

5. The hybrid in MySQL

MySQL lets you keep a relational core and put variable or tree-shaped parts in a JSON column. Three things from the manual matter, and I confirmed each on 8.0.46: a JSON column cannot be indexed directly, so you index a generated column for a scalar path or a multi-valued index for an array;[5] a CHECK constraint with JSON_SCHEMA_VALID() can reject a document of the wrong shape;[5] and a comparison on an unindexed path scans the table.

CREATE TABLE company  (id INT PRIMARY KEY, name VARCHAR(40) NOT NULL);
CREATE TABLE person   (id INT PRIMARY KEY, name VARCHAR(40) NOT NULL);
CREATE TABLE position (
  id         INT PRIMARY KEY AUTO_INCREMENT,
  person_id  INT NOT NULL,
  company_id INT NOT NULL,
  title      VARCHAR(30) NOT NULL,
  FOREIGN KEY (person_id)  REFERENCES person(id),
  FOREIGN KEY (company_id) REFERENCES company(id),
  KEY idx_company (company_id)
);
CREATE TABLE education (
  id INT PRIMARY KEY AUTO_INCREMENT, person_id INT NOT NULL, school VARCHAR(40) NOT NULL,
  FOREIGN KEY (person_id) REFERENCES person(id)
);
INSERT INTO company VALUES (7,'Acme'),(8,'Globex');
INSERT INTO person  VALUES (1,'Ada');
INSERT INTO position (person_id,company_id,title) VALUES (1,7,'engineer'),(1,8,'lead');
INSERT INTO education (person_id,school) VALUES (1,'Analytical College'),(1,'Night School');
-- the join that repeats rows: 2 positions x 2 educations = 4 rows for one person
SELECT p.name, pos.title, c.name AS company, e.school
FROM person p JOIN position pos ON pos.person_id = p.id
              JOIN company  c   ON c.id = pos.company_id
              LEFT JOIN education e ON e.person_id = p.id
WHERE p.id = 1;
CREATE TABLE person_doc (
  id  INT PRIMARY KEY,
  doc JSON NOT NULL,
  CONSTRAINT doc_shape CHECK (JSON_SCHEMA_VALID(
    '{"type":"object","required":["name","positions"],"properties":{"name":{"type":"string"},"positions":{"type":"array"}}}', doc)),
  -- multi-valued index: lets MEMBER OF find people by company without scanning every document
  KEY idx_company ((CAST(doc->'$.positions[*].company_id' AS UNSIGNED ARRAY)))
);
INSERT INTO person_doc VALUES
  (1, '{"name":"Ada","positions":[{"company_id":7,"company_name":"Acme","title":"engineer"}]}');
SELECT id FROM person_doc WHERE 7 MEMBER OF (doc->'$.positions[*].company_id');
-- a document of the wrong shape is rejected by the database, not by application code
INSERT INTO person_doc VALUES (2, '{"name": 42}');
Check your version I verified these against the MySQL 8.0 manual and a MySQL 8.0.46 server. Look up your own version’s documentation (and its support status) before relying on specifics. For DynamoDB, the AWS guidance takes the opposite starting point: with a relational database you can design normalized tables without thinking about access patterns, but DynamoDB design should start by identifying them, and it recommends keeping as few tables as possible.[6] Lesson 17 compares them side by side.

6. Check yourself

Optional: find your hottest read (15 minutes)

For one entity in a system you run, list its parts and the queries that touch them. Which query would turn into several round trips if the parts were separate tables, and which shared fact would turn into a fan-out if the parts were embedded? If both exist, you have found where a hybrid earns its keep.
