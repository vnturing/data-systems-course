Local and global secondary indexes

A lookup key and a storage key often disagree. A secondary index decides where that disagreement becomes fan-out and where writes must maintain another copy.

~35 min1 interactive4-question check
What you can do after this lessonCompare document-partitioned local indexes with term-partitioned global indexes, account for base fetches, and distinguish stale candidates from missing postings.

1. Local indexes follow the documents

Suppose documents are partitioned by ID but the query asks for status=paid. A local index on each document partition can answer which of its documents match. Without a partition-key predicate, the coordinator asks every relevant partition and combines the answers.

Each individual lookup may be indexed and cheap, yet the distributed query still fans out. The real MySQL experiment from Lesson 42 makes the distinction visible inside one server: status-only access uses its index across all four partitions; adding the day key prunes to one. That is evidence about pruning and local access, not a distributed network benchmark.

2. A global index follows the lookup term

base partitioning:   document ID → document owner
index partitioning:  status term → postings / base-document references

A term-partitioned index can direct paid queries to the owner of paid postings. A write may now touch the base owner and a different index owner. Changes to an indexed term need both removal of the old posting and addition of the new one. A globally popular term can become a hot index key even when base documents are well distributed.

“Global” does not mean the whole index lives on one machine. It describes an index whose partitioning can differ from the base documents. A real engine can further split posting lists or use composite keys. The lab deliberately gives each term one index partition so the trade is inspectable.

Try: query paid before the global index catches up. Revalidate candidates: document 42 is still missing. Switch to open and observe the stale extra candidate; revalidation can remove that one. Compare the local mode, where this model assumes index/data maintenance is atomic at each base partition.

3. Projection determines the second hop

If a query needs only IDs and fields projected into the index, its result can avoid base fetches. If it needs other fields or current base validation, the returned references may lead to many base partitions. A one-partition index lookup is therefore not necessarily a one-partition end-to-end query.

The widget reports distinct base partitions, not one network call per document. Batching, pagination, projection width and candidate selectivity determine actual work. Enlarging the projection can save reads while increasing index bytes and write maintenance, the same trade as covering indexes in Lesson 23.

4. Revalidation fixes only one kind of staleness

The base has changed document 42 from open to paid. An old index can still return it for open: a false positive candidate. Fetching the current base record removes it. But an old paid index lacks the new posting: a false negative. Candidate validation cannot discover an ID that was never returned.

A promise of current, complete results therefore needs more than filtering old candidates. Options include synchronizing index maintenance with the required write, waiting on an appropriate propagation barrier, or explicitly accepting lag. If base and index updates span systems, apply the crash-point drill; a dual write is not automatically atomic.

5. Product terms have precise scopes

DynamoDB defines an LSI with the base table’s partition key and an alternate sort key. A GSI can use a different key schema and is updated asynchronously; its queries can return results not yet reflecting base changes.[1] These API definitions are related to the placement trade, but the browser’s four physical owners and single-term partitions are not a DynamoDB emulator.

Uniqueness also needs an ownership scope. Our MySQL RANGE table rejected UNIQUE(id) without event_day with error 1503; its documented partitioned-table unique-key rule requires the partitioning columns in each unique key.[2] Changing it to UNIQUE(event_day,id) changes what is unique: the same ID can exist on another day. Do not replace global identity with per-partition uniqueness accidentally.

For a distributed uniqueness claim, identify who can atomically arbitrate competing claims for the same logical value. Neither “we added a local index” nor “we named it global” supplies that protocol.
