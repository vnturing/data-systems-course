Module 5 · Lesson 37

Multi-leader replication and conflict policy

Two locations can accept writes during disconnection. When they reconnect, a merge policy must decide what those accepted writes mean together.

~35 min1 interactive4-question check
What you can do after this lessonIdentify concurrent conflicts, distinguish deterministic convergence from preserving user intent, and decide when single-writer ownership is worth the availability cost.

1. Why accept writes at more than one leader?

A disconnected editor or independently operating region may need local writes while a remote site cannot be reached. A single global writer can make that path unavailable or slow. Allowing local acceptance moves the hard question from “can I commit now?” to “how do accepted histories combine?”

This is not ordinary single-leader failover with one winner. It intentionally permits multiple writers. MySQL’s ability to receive multiple replication sources should not be mistaken for an automatic application conflict-resolution system. Our profile example is a design exercise, not a configured MySQL multi-leader deployment.

2. Conflicts can happen without touching the same field

base profile: {name: Ada,   city: Harare}
A writes:     {name: Alice, city: Harare}
B writes:     {name: Ada,   city: Mutare}

Both clients read the base. Whole-record last-write-wins selection can discard either the name change or the city change. A field-aware protocol could preserve both independent changes. If both edit the name, a field merge alone cannot determine which spelling the user intended.

Try: compare whole-record selection with independent-field/sibling preservation. Switch to same-field edits. Then move A’s clock offset: timestamp selection can prefer an earlier real-time update because its clock reads higher. Neither update observed the other, so both remain concurrent regardless of wall-clock order.

3. Last-write-wins is a resolution rule, not intent detection

A deterministic total ordering, including a tie-break rule, can make replicas select the same winner after they learn the same candidates. That is useful convergence. It does not establish that the winner was causally newer or that losing a user’s accepted edit was acceptable.

The Dynamo paper makes application-assisted reconciliation explicit rather than pretending that storage can infer every business merge.[1] Keeping siblings preserves evidence but creates a handling obligation for readers, retries and later writes. Ignoring the second branch simply moves data loss into application code.

“Merge fields” is also incomplete: representations need per-field change/causal metadata so that an unchanged old field is not confused with an intentional reset. The widget knows which fields each example changed; it does not implement that wire protocol.

4. The inventory counterexample

Choose two sales against one stock unit. Each disconnected location sees stock 1 and accepts a sale. A perfect merge that preserves both sales yields stock −1. A merge that keeps stock at zero by discarding one sale may lose a promise already made to a customer.

The problem is the admission invariant, not merely representation convergence. A single authority, coordinated reservation or preallocated spending rights can constrain acceptance. If one unit is assigned to one region, the other region cannot independently promise that same unit during disconnection. Availability must be stated per operation and right, not just per database.

CRDTs in Lesson 40 provide useful merge semantics. They do not make every arbitrary invariant safe without coordination. We keep bounded-rights allocation as a design option rather than claiming to implement it here.

5. Reduce conflicts before resolving them

  1. Partition ownership when a record can have one writer at a time.
  2. Use immutable additions or append-only facts when those match the operation.
  3. Choose explicit merge semantics for counters, sets or independently changed fields.
  4. Preserve unresolved alternatives when application judgment is required.
  5. Coordinate or allocate rights for invariants that unsafe concurrent acceptance can violate.

The correct choice depends on the mission: what user promise must survive failures? A system can be available and convergent while still violating the feature’s contract. The next lessons supply vocabulary for observing concurrency and constructing more principled merges.

Optional: apply the mechanism (20 minutes)

Name a feature that accepts writes in two places. Write its conflict unit, merge rule, acceptable lost information and any invariant that two disconnected writers could violate. Consider single-writer ownership before proposing a complex merge.

Ask the course agent about any unclear result. Include the topology, acknowledgement contract and exact failure or message sequence.
