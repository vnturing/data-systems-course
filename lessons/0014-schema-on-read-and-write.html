Module 2 · Lesson 14

Schema on read or schema on write: the schema you did not write is still there

“Schemaless” does not mean no schema. It means the schema is not in the database, which moves it somewhere you may not be looking.

~40 min1 interactivebuilds on Lessons 1 and 124-question check
What you can do after this lesson Say where each rule about your data is enforced, predict what happens when a record’s shape changes, and choose between enforcing in the database, in each reader, or both.

1. The implicit schema

Two phrases are worth defining. Schema on write means the structure is declared up front and checked when data is written, as in relational DDL. Schema on read means records are stored as they arrive and interpreted when they are read. Martin Fowler’s widely cited essay on “schemaless” data structures makes the key observation: a schemaless store still has an implicit schema, because the code that reads the data assumes a structure (it expects a field called first or a number in seats). He concludes that an explicit schema is generally preferable, with some exceptions, and that when you do have a schemaless store the schema lives in the application and is best treated as a contract defined in one place.[1]

So the honest question is never “schema or no schema?” It is “where does the schema live, and how many copies of it exist?” In a relational table there is one copy, enforced by the engine. In a schemaless store there is one copy per reader.

2. Three readers, three ages

Your records were written over a year. At first each had a name and a plan string. Then name became first and last. Then plan became an object with a tier and a seat count. Three programs read these records: the billing job (written first), the analytics export (updated once), and the search indexer (always current). Nothing in the store distinguishes them.

What to notice

  1. Each reader carries its own copy of the schema, and each copy is a different age. The billing job handles only v1, so half the records are outside its knowledge.
  2. In tolerant mode the failures are silent. The reader falls back to placeholders (Unknown, free) and reports success. Billing the wrong tier is the kind of bug found by a customer, not a test.
  3. Switch to strict mode. The same reader, on the same data, now fails loudly on exactly the records it was silently getting wrong. The loud-error percentage equals the silently-wrong percentage you just saw. A visible failure can be alerted on.
  4. Now tick every box for every reader. All three become correct, but only because three separate teams each updated their code. The database did not help, because the database never knew the shape.

3. Where can a rule live?

PlacementApplies toCan a writer bypass it?
Typed columns, NOT NULL, foreign keys, CHECKEvery write, enforced by the engineNo
JSON column with CHECK (JSON_SCHEMA_VALID(...))Every write to that columnNo
Validation in application codeWriters that call itYes: another service, a script, a migration
Tolerant reading with defaultsOne readerNot a write-time rule at all
A convention in a wikiWhoever read itYes

MySQL lets you get write-time enforcement even inside a JSON column. I ran this on 8.0.46: the first insert below is accepted; the second, a v1-shaped record, is rejected by the database with error 3819 (check constraint violated). The manual documents the validation functions and lists limitations, so check them for your version.[2]

CREATE TABLE account (
  id  INT PRIMARY KEY,
  doc JSON NOT NULL,
  CONSTRAINT account_v3 CHECK (JSON_SCHEMA_VALID(
    '{"type":"object","required":["first","last","plan"],
      "properties":{"first":{"type":"string"},"last":{"type":"string"},
                    "plan":{"type":"object","required":["tier","seats"],
                            "properties":{"tier":{"enum":["free","pro"]},"seats":{"type":"integer"}}}}}', doc))
);
INSERT INTO account VALUES (1, '{"first":"Ada","last":"Lovelace","plan":{"tier":"pro","seats":3}}');
-- an old-shape record: the database refuses it
INSERT INTO account VALUES (2, '{"name":"Grace Hopper","plan":"pro"}');
-- promote a hot field out of the document into a typed, indexed column
ALTER TABLE account
  ADD COLUMN tier VARCHAR(10) GENERATED ALWAYS AS (doc->>'$.plan.tier') VIRTUAL,
  ADD KEY idx_tier (tier);
SELECT id FROM account WHERE tier = 'pro';
-- the plain relational alternative, and the "expand" step of a migration:
-- add the new column as nullable with a default, so old writers keep working
CREATE TABLE account_rel (
  id INT PRIMARY KEY, first_name VARCHAR(40) NOT NULL, last_name VARCHAR(40) NOT NULL,
  tier ENUM('free','pro') NOT NULL DEFAULT 'free', seats INT NOT NULL DEFAULT 1);
ALTER TABLE account_rel ADD COLUMN email VARCHAR(100) NULL;
INSERT INTO account_rel (id, first_name, last_name) VALUES (1, 'Ada', 'Lovelace');
SELECT * FROM account_rel;

4. Changing shape without a flag day (my synthesis)

Because writers and readers deploy at different times (Lesson 1’s world), two shapes coexist for a while no matter how disciplined you are. A migration pattern that respects that is often called expand and contract:

  1. Expand: add the new field as optional (or add the new column with a default). Old writers keep working.
  2. Deploy readers that accept both shapes. This is where tolerance is correct, as a transition state.
  3. Switch writers to the new shape, then backfill old records.
  4. Contract: make the new field required (a constraint), make readers strict, remove the old field.

The end state is explicit and enforced. Tolerance is a tool for the middle, not a place to live. Module 4 returns to this with binary encodings, where the same compatibility rules are checked by the format itself.

5. Check yourself

Optional: count the copies of your schema (15 minutes)

Pick one table or collection. List every program that reads it. For one important field, write down what each program assumes about its type and what it does if the field is missing. The number of different answers is the number of copies of your schema.
