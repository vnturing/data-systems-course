Module 6 · Lesson 42

Key-range or hash partitioning?

Partitioning divides responsibility. The key determines both where work goes and which queries can avoid asking everyone.

~35 min1 interactive4-question check
What you can do after this lessonChoose between ordered ranges and hashing for a declared workload, distinguish data balance from traffic balance, and read a real partition-pruning plan without claiming distributed scale-out.

1. A partition is not a replica

Partitioning divides the dataset into responsibilities. Replication makes copies of a responsibility. A system might have four partitions, each replicated three ways: that is not one twelve-member quorum. The quorum and authority questions from Module 5 apply to the relevant replica group for each key.

Separate three decisions: key → logical partition, partition → serving nodes, and which copy may serve this operation. A hash can answer the first without answering current ownership or read freshness.

2. Ordered ranges preserve useful neighborhoods

P0: keys [0,2500)       P1: [2500,5000)
P2: keys [5000,7500)    P3: [7500,10000)

A query for keys 5000–7499 targets P2. An equality lookup uses one boundary interval. Neighboring keys remain together, which can help range scans and ordered pagination. The directory must know the actual boundaries; partitions need not have equal key widths or equal numbers of records.

The cost of that locality appears when neighboring keys are busy together. If the newest timestamp is the leading key and all writes go to the advancing tail, only the tail partition receives them. Bigtable’s row-key design guidance explicitly discusses ordered keys and timestamp-related hotspots.[1]

Try: compare layouts for the default interval. Next select the final-key activity burst. Then choose the single hot key. Equal record counts do not imply equal request load.

3. Hashing trades locality for dispersion

Hashing the full key can spread distinct adjacent keys across partitions. A router that knows an exact key can compute its partition. A range predicate on the original key generally does not describe one interval in hash space; this lab’s router queries all partitions for a non-point interval.

A hash does not split repeated work on the same key: identical key bytes still select the same partition under the same map. Nor does a hash guarantee perfectly equal key counts in a finite sample. Unequal object sizes and traffic weights can dominate the result even when the hash distribution looks uniform.

The lab uses a deterministic teaching hash and 10,000 equal-size records. It counts routed work and logical targets, not network latency. It does not emulate a particular database or enumerate every possible point in a hash-routed range predicate.

4. What real MySQL pruned

We created 100,000 rows across four MySQL 8.4.13 RANGE partitions: days below 25, 50, 75 and MAXVALUE. EXPLAIN FORMAT=JSON reported:

PredicatePartitionsMatching rows
day ≥ 50 and day < 75p225,000
id = 12345, with by_id indexp0, p1, p2, p31
status = paidp0, p1, p2, p310,000
paid plus the day intervalp22,500

These are executed counts and plan partition lists. The manual defines pruning as excluding partitions that cannot match the predicate.[2] The ID lookup uses an index, but the ID predicate does not identify a day partition. Index access and partition pruning are separate axes.

This is table partitioning inside one MySQL server, not a measurement of a four-machine sharded database. We measured neither network fan-out nor distributed speedup. The experiment anchors pruning; the browser separately models placement across owners.

5. Choose the partition key with the queries

For events, (tenant, time) can keep a tenant’s interval local, while time alone can concentrate the newest writes and tenant alone can concentrate a large tenant. Hashing tenant can distribute tenants without dividing one exceptionally busy tenant. A composite key’s ordering and hashed portion must be explicit.

List point lookups, range scans, joins and global reports before selecting the key. Mark which predicates identify a partition and which scatter. Then attach bytes and request weights to those partitions. The next lesson asks which overloaded unit can actually be divided without changing the operation’s meaning.
