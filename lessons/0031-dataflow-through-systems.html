Module 4 · Lesson 31

Follow the bytes through the whole dataflow

A reader can understand enough to make its own change and still erase data it never understood. Compatibility must survive the whole path.

~35 min1 round-trip labdatabase, service and broker paths4-question check
What you can do after this lessonFind every serializer, reader and rewriting intermediary in a dataflow; test unknown-field preservation; and include request, response and historical replay in a compatibility review.

1. The old writer hiding inside a read

new producer → stored bytes → old updater → rewritten bytes → new reader
  currency EUR                knows only id/name            currency ?

The producer writes an account with currency EUR. An old profile service loads it and changes the name. It never uses currency. If it constructs a new record containing only id and name, the new reader receives a record with currency absent. A fallback to USD would change the interpretation of a EUR account.

This is a data-loss path even when both parsers report success. Test new → old → new round trips, not only whether the old reader can accept a new record.

Try: compare rebuilding known fields, editing while retaining unknown binary fields, and forwarding bytes unchanged. The last preserves everything but performs no name update. Retaining unfamiliar data does not mean the old application understands its business meaning.

2. What the real libraries did

Modern Protobuf binary messages preserve unknown fields on normal parse/reserialize paths. Reconstructing field by field or passing through JSON can drop them; the official guide calls out both cases.[1] We ran those paths with Python Protobuf 6.33.5:

Old intermediary actionNew reader sees
Forward bytes unchangedZoë, currency EUR
Edit the binary message nameZoe, currency EUR
Rebuild only known fieldsZoe, currency absent
Serialize old message to ProtoJSON and backZoe, currency absent

A separate test sends new-message ProtoJSON directly to the old schema: its parser rejects the unfamiliar currency field by default. ProtoJSON’s compatibility and unknown-field behavior differs from binary Protobuf.[2] “We use Protobuf” is insufficient information if a gateway changes its representation.

3. Database paths persist both time and old assumptions

In a MySQL application storing a serialized blob or JSON document, find every read-modify-write operation. A service that rewrites the entire value from an old object model can lose new fields. A narrow update that intentionally preserves the rest is a different path, and needs its own concurrency and atomicity reasoning.

Avro resolution can ignore fields the reader does not request. That is useful for reading, but the resolved old object alone is insufficient to recreate every field of the original newer record. Preserve the original data or adopt an explicit update protocol if round-trip preservation is required. Unknown-field retention in one format is not a universal property of all serializers.

Also retain the ability to interpret long-lived bytes. A code rollout does not rewrite old rows; a restored backup can resurrect much older writer schemas. Decide which schema history and migration code the recovery plan needs.

4. Services have two compatibility arrows

request:   client writer → server reader
response:  server writer → client reader

For REST/JSON, inspect validation, generated clients, unknown-field policies, enums and missing/null handling in both directions. For RPC, inspect the serialized messages and the service interface. gRPC defines services and callable methods in addition to their request and response messages.[3] A message that decodes does not prove that an old server implements a newly introduced method.

A schema also does not erase remote failure semantics. The server can complete an action while the caller times out. Lesson 1’s idempotency contract still applies. Encoding compatibility and retry safety are separate checks.

5. Brokers extend the version overlap

For a Kafka dataflow, include the producer serializer, consumer deserializer and any service that transforms or republishes records. A replaying consumer may need records from several past producer releases. A dead-letter queue or backup archive can outlive ordinary topic retention. State those paths explicitly instead of assuming that only today’s producer matters.

Registry-backed serializers provide another dependency: consumers must identify and obtain the relevant schema. Confluent documents its supported formats and serialization framing; those are properties of that serializer ecosystem, not of every Kafka record.[4] AWS Glue likewise supplies a registry and SerDe integrations for supported streaming applications.[5] Do not assume the two use identical envelopes or policy names.

A registry can check supported structural compatibility rules. It does not automatically configure every application to use its serializer, preserve schema history forever, or detect that amount silently changed from cents to dollars.

6. A review sheet for one real path

  1. List each hop’s encoding, schema source and deployed versions.
  2. Mark every node that only reads, passes bytes through, or decodes and rewrites.
  3. Test unfamiliar fields through every rewriting path.
  4. Check both request/response arrows and every retained-history replay reader.
  5. State units, fallback semantics, rollback behavior and recovery dependencies separately.

The browser lab runs actual subset wire transformations. It does not contact MySQL, Kafka, a registry or a service, and proves no transport delivery or concurrency guarantee.

7. Check yourself

Optional: trace one field (20 minutes)

Follow a field from an API request into MySQL and a Kafka consumer. Mark all mappings and rewrites. Introduce an unfamiliar field in scratch data and inspect the final record. Include a replay and a response client in your review.

Ask the course agent to review your hop diagram, especially any intermediary that reads and writes.
