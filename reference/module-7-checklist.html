Transactions: review the invariant and the history

A transaction boundary, a visibility rule and a conflict protocol answer different questions. Name all three before relying on them.

ACID boundaries (47)

  • Atomicity: abort the database changes as a group. Check zero-row business outcomes explicitly.
  • Consistency: state the application invariant and which constraints/code preserve it.
  • Isolation: declare allowed concurrent observations and decisions, not just “inside BEGIN.”
  • Durability: name the failure domain, flush settings, replica acknowledgement and recovery assumptions.
  • A lost COMMIT reply leaves uncertainty. Recover by durable operation identity.
  • External sends escape SQL rollback. Store outbox intent transactionally and handle delivery duplicates.
  • Check transactional table engines, implicit DDL commits and one-connection ownership.

Read and version rules (48–49)

  • Dirty read: read a concurrent uncommitted write. Dirty write: overwrite one; a different failure.
  • InnoDB read committed: each plain consistent-read statement gets a fresh committed view.
  • InnoDB repeatable read: first ordinary consistent read fixes the view; BEGIN alone need not do so.
  • Locking/current reads can see newer data than a plain snapshot read inside the same transaction.
  • Visibility must exclude transactions active at the view’s boundary, even if their IDs are small.
  • Own writes are visible to the writer. Retain versions still needed by live views.
  • MVCC is a mechanism; formal snapshot isolation also has a same-row conflict rule. Do not equate it with every vendor’s “repeatable read.”

Lost updates: five defenses (50)

  1. Atomic operation: use UPDATE v=v+delta, with the admission predicate in the statement when applicable.
  2. Lock before reading: read, decide and write under the lock in one transaction.
  3. Compare-and-set: every relevant writer advances a version; zero rows means rollback and recompute.
  4. Automatic conflict detection: verify the engine rule; restart the whole transaction on a known retryable abort.
  5. Mergeable operation/state: preserve independent contributions with operation identity; convergence alone does not enforce admission bounds.

Write skew, predicates and locks (51–52)

  • Disjoint write sets can still violate a shared read predicate. Same-row conflict detection misses that case.
  • A stable empty query does not reserve absence. New matching rows can create admission races.
  • Use a matching constraint, common guard with fresh validation, protected predicate/range, or verified serializable execution.
  • A guard protects only participating writers. Include membership changes, imports and administrative paths.
  • Locking only each writer’s target row can leave the shared invariant unprotected.
  • Two-phase locking: acquire before releasing; strict variants retain write locks through transaction end. It is separate from two-phase commit.
  • A wait edge is not necessarily a deadlock; a wait-for cycle requires intervention. Use common resource order where possible.
  • InnoDB ranges and exact unique-key probes lock differently. Inspect the index/plan and actual lock evidence.

Serializable mechanisms and retries (53)

  • Serializable means some equivalent serial order of committed transactions, not necessarily physical one-at-a-time execution.
  • SSI tracks read/write anti-dependencies and can conservatively abort dangerous structures.
  • PostgreSQL SIReadLock markers record dependency evidence; they do not block writers like ordinary S locks.
  • Actual serial execution queues complete transactions; a slow/network-blocked transaction can delay all work in that domain.
  • One executor per partition does not alone establish a cross-partition transaction contract.
  • On a known abort: rollback, fresh transaction, recompute all decisions, bounded backoff.
  • On uncertain commit: recover by operation identity. Repeated external effects need their own defense.

Feature review procedure (55)

  1. Write a falsifiable invariant and its exact scope.
  2. List every decision input: rows, sums, predicates, absence and external facts.
  3. Identify all writers and actual transaction/connection boundaries.
  4. Construct a minimal violating concurrent schedule.
  5. Name the constraint, expression, lock, version check or serializable rule that rejects it.
  6. Specify failure rollback scope, retry budget, operation identity and external effects.
  7. Measure waits, aborts/retries, tail latency, transaction duration and history retention for the correct design.

Useful starting points: atomic expressions for single-row accumulation; UNIQUE(room_id,slot_id) for exact discrete claims; a shared guard plus fresh validation for a cross-row roster; one stable snapshot for a multi-query report. Arbitrary interval overlap is not exact-slot uniqueness.

Evidence and limits

Reproduce 20 original server schedules, inspect the MySQL transcript and PostgreSQL transcript. No production latency, host/power loss, replication, failover or distributed commit is tested. A passing finite schedule suite does not prove the general isolation contract or audit every application path.
