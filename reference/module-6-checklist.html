Reference sheet · Module 6 (Lessons 42 to 46)

Partitioning: keys, work, indexes and ownership

State the unit that can move, the queries that locate it, and the write authority during migration. Key-count balance alone is insufficient.

Three separate decisions (42)

key → logical partition → serving nodes
plus: which copy / authority can serve this operation?
  • Partitioning divides responsibility; replication copies it. Evaluate quorum/authority guarantees for the relevant replica group.
  • Range keys preserve neighborhoods and permit boundary pruning; adjacent busy keys or a newest-key tail can concentrate work.
  • Hashing spreads distinct keys; an exact key can route directly. A non-point interval may scatter, and one repeated key still maps to one owner.
  • Attach bytes, traffic and service demand to ownership units, not only record counts.

Real MySQL 8.4.13: day [50,75) prunes to p2 with 25,000 matches. Indexed ID lookup searches all four partitions for one match. Status-only searches four; adding day prunes to p2 with 2,500 paid matches. This is local table partitioning on one server, not distributed throughput.

  • Moving a single hot key changes its owner, not its indivisible demand.
  • Salt buckets can collide on physical nodes. A random suffix needs lookup context or fan-out; a calculated suffix needs stable inputs.
  • Changing bucket count without accounting for old data can make records hard to find.
  • Cache hit-rate arithmetic is not a consistency contract; CRDT convergence does not enforce stock bounds.

Secondary access paths (44)

  • Document-partitioned local index: easy local access/maintenance, but a non-partition-key query can contact all document partitions.
  • Term-partitioned global index: lookup follows the term, with cross-owner maintenance and potential hot posting terms.
  • Projected fields can avoid base fetches. Otherwise references can fan out to multiple base partitions; batch counts and record counts are different.
  • Revalidation can remove an old posting’s false positive. It cannot discover a missing posting’s false negative.
  • Define index freshness, completeness, update atomicity and recovery. “Global” alone does not implement global uniqueness.

DynamoDB LSI/GSI definitions have specific API scopes; the four-owner toy is not their internal implementation. Real MySQL rejected UNIQUE(id) without the partition key with error 1503. UNIQUE(day,id) guarantees the pair, not global ID uniqueness.

Default 10,000-key model, three→four nodes: 7,480 / 2,504 / 2,083 keys change owners for modulo / selected slots / 64-token ring. These are computed equal-size placement counts, not measured bytes transferred.

  • Virtual nodes improve granularity, not guaranteed perfect traffic balance. Multiple tokens on one host are not independent replicas.
  • Migration budget includes bytes, replicas, indexes, concurrent changes and cache warming.
  • Connect snapshot to complete change capture; replay updates and deletions through a valid boundary.
  • Establish exclusive write authority, update routing and handle stale requests.
  • Rollback needs new acknowledged writes too; an old snapshot is insufficient.

Routing and discovery (46)

  • Endpoint discovery locates a service; ownership metadata locates the responsible partition owner.
  • Client maps, proxies and server forwarding put caching, extra hops and availability dependencies in different places.
  • Stale maps need a protocol response and owner-side enforcement; arbitrary old writers must not remain authoritative.
  • Bound retries and metadata refresh. Uncertain write execution still needs operation identity/idempotency.

Redis evidence: CRC16-XMODEM plus the defined nonempty-brace tag rule maps into 16,384 slots. customer:42→4672; orders:{42}:a and :b→8000; orders:{99}:a→6263. Same tags co-locate and can concentrate traffic. Cross-slot MSET was rejected.

MOVED: refresh/update the ownership route, then retry appropriately. ASK: one-request import exception; ASKING and the query must share a connection. Preserve the old slot owner in the cache until ownership changes. Maps can change again.

Review procedure

  1. Declare the partition key, logical ownership units and replica groups.
  2. Map every important query to its actual index/base targets.
  3. Identify the heaviest bytes, demand and indivisible operations.
  4. Choose placement and migration boundaries with a rollback history.
  5. Verify discovery, owner enforcement and stale-route handling.
  6. State measured evidence separately from modeled assumptions.

Evidence and sources

Reproduce the MySQL plans/counts and Redis slot/redirection results. The Redis move used one quiescent key, no replicas or failover. Browser models do not implement a live migration protocol or measure WAN/production latency.
