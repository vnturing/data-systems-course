Module 0 design-review checklist

One page for design reviews. Each block names the lesson it comes from. Print-friendly.

1. The crash-point drill (Lesson 2)

  1. List every externally visible effect in order (COMMIT counts as one).
  2. Draw a line before, between and after the effects.
  3. At each line: process killed here, never resumes. What does each system contain?
  4. Classify: clean lost phantom duplicate.
  5. Repeat for: second effect errors out; reply to caller lost.

2. The model line (Lesson 3)

Put this at the top of every design doc and check each safety claim against it:

Nodes: crash-recovery (memory lost, disk survives)
Network: fair-loss; partitions possible
Timing: partially synchronous (observed pauses up to ~__ s)
  • Perfect failure detection needs synchrony. In partial synchrony a detector is eventually right and may temporarily accuse healthy nodes.
  • Every health-check threshold, promotion delay and TTL is a point on the detection-speed versus false-failover curve. Measure your longest heartbeat gaps before choosing.
  • “Lease/lock is safe” claims need an assumption about maximum pause length. Ask what happens when it is exceeded.

3. Safety / liveness pairs (Lesson 4)

Write each requirement as: “Never ___ (safety). May stall for ___ (liveness we sacrificed).” Test: can you point to a moment it went wrong (safety), or only to “not yet” (liveness)?

4. Retry rules (Lessons 1 and 5)

  1. Timeout on every remote call (connect and request). Choose it from a latency percentile: pick the false-timeout rate you accept (say 0.1%) and use the matching percentile (p99.9).
  2. Retry only operations that are safe to repeat, or that carry an idempotency key generated once per logical operation.
  3. Capped exponential backoff with jitter (full jitter: random(0, min(cap, base*2^attempt))). Jitter periodic jobs too.
  4. Bound retries with a retry budget (token bucket) and a low max attempt count.
  5. Count the layers: attempts multiply (3 x 3 x 3 = 27). Prefer retrying at one layer.
  6. Retry window must be shorter than every dedupe window it relies on.

Ten questions for any design review

  1. What is the system model? Which claims need a stronger one?
  2. Which effects span two systems? What does each crash point leave behind?
  3. What happens if the client retries after a timeout?
  4. Where is the dedupe record, and does it commit atomically with the effect?
  5. What is each safety property, and what is each liveness property we sacrificed for it?
  6. What are the timeouts, and what false-timeout rate do they imply?
  7. How many retry layers stack on this path? What bounds the total?
  8. Is there jitter on retries and periodic work?
  9. Which dedupe windows exist, and is the retry window shorter than each?
  10. What does a false failure detection cost here, and who decided the threshold?
