Timeouts, retries, idempotency

A one-page lookup for design reviews and code review. Print-friendly.

What a timeout means

Only: no reply arrived in time. Consistent worlds: request lost, server crashed before commit, server committed and reply lost, server committed and reply slow (GC, queueing, congestion). The client cannot tell them apart.

Idempotency key checklist (server side)

  1. Key is per logical operation, generated and persisted client-side before attempt 1; reused on all retries.
  2. Dedupe record and the effect commit in one atomic transaction. Never "record key, then do work".
  3. Store the response, not just the key, so a retry gets the same answer.
  4. Compare request parameters with the stored request; reject mismatches (caller bug).
  5. Handle concurrent duplicates: in-flight marker, wait, or reject with a retryable status.
  6. Retention window > longest client retry window. Document it. (SQS FIFO deduplication, for example, has a 5-minute interval; a resend with the same id after it can create another message.)
  7. Key store must be as durable as the data it protects (an in-memory-only table is forgotten on crash).
  8. Decide what to do with errors: cache them (Stripe caches even 500s) or allow re-execution. Be explicit.

Anti-patterns

Anti-patternWhy it fails
New key per attemptIdentical to a blind retry; no dedupe possible
Key = hash of payloadTwo legitimate identical purchases get merged
Key recorded before effect, separate stepCrash between them = false success, silent loss
In-memory dedupe tableLost on restart; duplicates accepted after crash
Library auto-retry on POST with no keyHidden at-least-once on a non-idempotent call
Retry with no backoff or jitterA slow server gets more load exactly when it is struggling (retry storms)

The honest limit

If the effect lives outside your transaction boundary (card network, email, physical device), key + effect cannot be atomic. Pass the downstream idempotency key through, or reconcile by querying actual state afterward.
