Reference sheet · Module 3 (Lessons 18 to 22; extended as the rest of the module lands)

Storage engines: structures, numbers and procedures

“Measured” = real InnoDB 8.0.46 or RocksDB (rocksdict 0.3.29) in a small sandbox, with ranges across repeated runs. See experiments/storage/. Shapes matter more than digits.

Three amplifications (Lesson 20)

  • Write: bytes physically written ÷ bytes the application wrote. Read: disk reads per lookup. Space: bytes on disk ÷ live bytes.
  • RUM conjecture: optimizing two of read, update and memory overhead tends to hurt the third.
  • Report peak space amplification for tiered stores: provision disks for it.

Append-only log + hash index (Lesson 18)

  • Write = append. Read = hash lookup + one seek. Delete = tombstone. Merge rewrites live records only.
  • Costs: every key in RAM, no range queries, space until merge. Recovery = scan, verify CRC, stop at the first bad record (tested on 1,400 random crash/corruption trials).

LSM-tree (Lessons 19, 20)

  • Write: WAL + memtable; flush to a sorted immutable run; compact in the background. Read: memtable, then runs newest to oldest; range check and bloom filter skip runs.
  • Tombstones hide older versions until compaction removes both.

  • A B-tree’s write cost is set by whether the leaves you touch are cached.
  • A split is three page writes. No log: corrupt at 3 of 8 crash points (new leaf first) or 5 of 8 (parent first). Log only: torn pages unrecoverable (3 of 8). Log + doublewrite: 0 of 8.
  • ARIES rules: log record durable before the page; commit once the log is durable; steal/no-force. Redo needs an intact page, so a doublewrite area keeps a good copy.
  • Read the counters yourself: Innodb_pages_written, Innodb_dblwr_pages_written, Innodb_os_log_written, Innodb_buffer_pool_read_requests, Innodb_buffer_pool_reads.

Choosing (Lesson 22)

  1. Do the leaves you write to fit in memory? Then B-tree writes are cheap.
  2. Keys in order? Both are cheap.
  3. Random-key writes far beyond memory? LSM-tree advantage is largest.
  4. Latency-critical point or absent-key reads? B-tree has no surprises; an LSM-tree needs filters and a cache.
  5. Disk or flash endurance tight? Compare space and write amplification on your data.
  6. Then replay your own workload on both and measure.

Not measured here: latency percentiles and compaction stalls, range scans, concurrency, transactions, secondary indexes, SSD behavior, tuned configurations.

Measurement hygiene (learned the hard way)

  • A multiplicative scramble (n * 2654435761 mod 2^32) is not random: it splits leaves in lockstep and sweeps caches cyclically. Hash the key.
  • Absent-key probes must fall inside the stored key range.
  • Turn compression off (or use incompressible values) when measuring physical bytes.
  • Repeat runs and report ranges; background work makes engines non-deterministic.
  • When a model agrees with an experiment, check they are not sharing the same flaw.
