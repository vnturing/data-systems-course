Reference sheet · Module 3 (Lessons 18 to 27)

Storage engines: structures, numbers and procedures

“Measured” = real InnoDB 8.0.46 or RocksDB (rocksdict 0.3.29) in a small sandbox, with ranges across repeated runs. See experiments/storage/. Shapes matter more than digits.

Three amplifications (Lesson 20)

  • Write: bytes physically written ÷ bytes the application wrote. Read: disk reads per lookup. Space: bytes on disk ÷ live bytes.
  • RUM conjecture: optimizing two of read, update and memory overhead tends to hurt the third.
  • Report peak space amplification for tiered stores: provision disks for it.

Append-only log + hash index (Lesson 18)

  • Write = append. Read = hash lookup + one seek. Delete = tombstone. Merge rewrites live records only.
  • Costs: every key in RAM, no range queries, space until merge. Recovery = scan, verify CRC, stop at the first bad record (tested on 1,400 random crash/corruption trials).

LSM-tree (Lessons 19, 20)

  • Write: WAL + memtable; flush to a sorted immutable run; compact in the background. Read: memtable, then runs newest to oldest; range check and bloom filter skip runs.
  • Tombstones hide older versions until compaction removes both.

  • A B-tree’s write cost is set by whether the leaves you touch are cached.
  • A split is three page writes. No log: corrupt at 3 of 8 crash points (new leaf first) or 5 of 8 (parent first). Log only: torn pages unrecoverable (3 of 8). Log + doublewrite: 0 of 8.
  • ARIES rules: log record durable before the page; commit once the log is durable; steal/no-force. Redo needs an intact page, so a doublewrite area keeps a good copy.
  • Read the counters yourself: Innodb_pages_written, Innodb_dblwr_pages_written, Innodb_os_log_written, Innodb_buffer_pool_read_requests, Innodb_buffer_pool_reads.

Choosing (Lesson 22)

  1. Do the leaves you write to fit in memory? Then B-tree writes are cheap.
  2. Keys in order? Both are cheap.
  3. Random-key writes far beyond memory? LSM-tree advantage is largest.
  4. Latency-critical point or absent-key reads? B-tree has no surprises; an LSM-tree needs filters and a cache.
  5. Disk or flash endurance tight? Compare space and write amplification on your data.
  6. Then replay your own workload on both and measure.

Not measured in the engine comparison: latency percentiles and compaction stalls, range scans, concurrency, transactions, secondary indexes, SSD behavior, tuned configurations. The later index experiment below addresses logical access counts, not an engine latency comparison.

Index review (Lesson 23)

  • InnoDB secondary entries contain their key columns and the primary key. Fetching other columns can require a clustered-tree lookup; wide primary keys widen secondary indexes.
  • For tenant equality, status equality and a date range, try (tenant, status, date). Add amount to cover a sum of amount; weigh the extra space and write maintenance.
  • Separate search interval, residual predicates and coverage. A column after a range can tighten a boundary without filtering the interval’s interior.
  • Using index: covering access. Using index condition: pushdown before a clustered fetch. These save different work.
  • Read actual rows and loops from leaves upward. ICP can hide rejected entries from an access node’s output count. Counts are not disk reads.

Memory and recovery (Lesson 24)

  • Trace: engine memory → OS cache → durable storage. State where the reply occurs.
  • RDB recovers the last completed snapshot. AOF recovers logged mutations; its fsync policy changes the acknowledged-write exposure.
  • Process SIGKILL leaves the OS cache alive. It cannot establish power-loss durability. The recorded Redis AOF/everysec value survived; the RDB-only test recovered the snapshot and lost its later acknowledged update.
  • The browser assumes completed synchronization each whole second. At 1,950 ms: five replies, three durable writes under everysec. This is a model, not a hard Redis deadline.
  • Write a failure model, acknowledged-data loss budget, recovery-time budget and rebuild authority. Verify startup configuration during recovery tests.

Workload and warehouse review (Lesson 25)

  • Describe rows touched, columns needed, write pattern, deadline and freshness. “Read-heavy” is insufficient.
  • A long report can queue checkouts despite low average utilization. Isolate the resource that is actually contested.
  • A second store needs a consistent snapshot/change-stream boundary, lag monitoring and reconciliation. Completion time is not a data completeness timestamp.
  • Define fact grain: e.g. one order line at purchase. Do not repeat order totals per line. Preserve purchase-time amounts and decide which historical dimension values the report means.

Stored-answer review (Lesson 27)

  • Specify full refresh vs incremental maintenance, freshness, and rebuild procedure.
  • Update = retract before-image + add after-image. A grouping-key change affects two groups; deletes need the old contribution.
  • For event dedupe, commit marker and summary delta together, then acknowledge. A crash between delta and marker makes a retry unsafe.
  • Roll up SUM and COUNT; compute AVG from both. MIN deletions and exact distinct counts need more state.
  • CUBE(day, region): (day,region), (day), (region), (). ROLLUP(day, region) omits (region). There are 2d grouping sets in a full d-dimensional cube, with cardinality determining actual cells.
  • A grouping operator computes answers; it does not automatically persist or maintain them. Distinguish subtotal NULLs using grouping metadata.

Design review: which read does each index, projection or summary accelerate; what writes maintain it; how does recovery reconstruct it; and where is the authority?

Measurement hygiene (learned the hard way)

  • A multiplicative scramble (n * 2654435761 mod 2^32) is not random: it splits leaves in lockstep and sweeps caches cyclically. Hash the key.
  • Absent-key probes must fall inside the stored key range.
  • Turn compression off (or use incompressible values) when measuring physical bytes.
  • Repeat runs and report ranges; background work makes engines non-deterministic.
  • When a model agrees with an experiment, check they are not sharing the same flaw.
  • Verify restart configuration. A runtime setting can differ from the startup command.
  • Label metadata byte sums separately from actual I/O; label finite FIFO traces separately from database benchmarks.
