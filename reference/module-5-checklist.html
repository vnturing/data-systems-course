Reference sheet · Module 5 (Lessons 33 to 41)

Replication: authority, history, reads and repair

Draw the exact failure and responders. A named replication mode or quorum formula is only part of a correctness argument.

Acknowledgement boundary (33)

source durable → replica received → replica durable → replica applied → read visible
  • State the required members and stage before success. Received is not applied; configured is not necessarily active.
  • MySQL semi-sync acknowledges flushed relay-log receipt, not completed SQL apply. Timeout fallback can weaken acknowledgement to asynchronous behavior.
  • Choose a failover candidate containing the required history; one remote acknowledgement does not make every follower eligible.
  • Replication can copy destructive writes successfully. Define backups and point-in-time recovery separately.

Failover (34)

  1. Define acknowledged-data loss and failure assumptions.
  2. Check candidate received and applied history.
  3. Establish exclusive write authority; fence former writers.
  4. Recover/apply required history before serving its reads.
  5. Move clients, handle uncertain retries, reconcile or rebuild old sources before readmission.

Missing from the new authority ≠ destroyed on every disk. Routing updates alone do not fence cached connections. A GTID or log position identifies history; it does not elect an authority.

Log representation (35)

Preserve transaction identity, order and visibility boundaries. Repeating one assignment may be harmless; arbitrary row events are not universally idempotent. Logs of future changes need not detect untouched historical drift. Bootstrap requires a consistent snapshot/log boundary.

  • Use version/transaction evidence, not a guessed sleep. If no eligible node exists, wait, route appropriately or report unavailability.
  • Sticky routing needs a failover and session-scope contract. It does not create arbitrary cross-stream causal visibility.
  • For MySQL WAIT_FOR_EXECUTED_GTID_SET: 0 = success, 1 = timeout. Obtain the correct committed context and use a suitable fresh read snapshot.

Concurrent acceptance (37)

  • Whole-record winner selection can discard independent field changes. Timestamp order is not proof of causal observation.
  • Field merging requires a protocol identifying actual changes; same-field siblings still need resolution.
  • Two isolated sales against one unit can converge correctly to stock −1. Admission invariants may need coordination or preallocated rights.
  • Consider single-writer ownership or immutable additions before a complex conflict protocol.

Quorum premise checklist (38, 41)

For the same fixed N-member universe, R+W>N gives read/write intersection. 2W>N gives write/write intersection. Neither inequality alone proves linearizability.

  • Was the write completed on the required durable holders?
  • Do actual holders and read responders belong to the same fixed universe?
  • Can the read interpret versions correctly, including concurrent versions?
  • What happens after partial writes, timeouts, reconfiguration and membership substitution?

Sloppy witness: homes {A,B,C}; write holders {A,D}; read {B,C}. W=2, R=2, but actual intersection is empty. Repairing only B/C cannot discover D’s value. Handoff can later supply evidence.

Partial-write witness: only A gets v1; W=2 fails. Read {A,B} sees v1, then {B,C} sees v0 unless the first read repairs B before returning. Failed acknowledgement is not universal rollback.

Read repair handles discovered stale responders; anti-entropy checks replicas beyond the current read workload; hinted handoff defers a delivery. Each needs its own liveness, retention and failure assumptions.

Causal context (39)

  • Missing vector components mean zero. x precedes y if all x components are ≤ y and at least one is smaller.
  • {A:2} and {A:1,B:1} are concurrent. Preserve undominated siblings when no business merge has resolved them.
  • A resolver observes both, joins context, then advances its unique actor version. Joining context does not choose the correct business value.
  • Persist actor identity/counters; do not reuse version dots. Metadata truncation and deletion reclamation need a justified protocol.
  • Dropping all tombstone evidence before an old replica returns can resurrect deleted data.

CRDT review (40)

  • State merge: commutative, associative, idempotent; local updates advance the appropriate partial order; required state eventually disseminates.
  • Counter: actor-owned accumulated components; merge componentwise max. PN value = sum(P) − sum(N); decrements increase N.
  • Observed-remove set: unique addition tags; removal records observed additions. An unobserved concurrent add survives this add-wins policy.
  • State-based duplicate tolerance is not a universal operation-message guarantee. Define transport and durable metadata assumptions.
  • Convergence does not establish stock bounds, global uniqueness or every cross-record constraint.

Independent evidence and limits

Real MySQL 8.4.13: received-but-unapplied row absent; execution wait timed out then succeeded; semi-sync acknowledged while SQL apply was stopped; stale C lacked a row retained on B; unfenced source and C accepted divergent writes. Recorded results and reproduction.

Tests enumerate 21,343 fixed-membership quorum set pairs and check bounded causal-order and merge laws. Models do not implement a vendor election, fencing, full leaderless protocol, actor allocator or metadata collector. No WAN latency, power failure or production consistency certification was measured.
